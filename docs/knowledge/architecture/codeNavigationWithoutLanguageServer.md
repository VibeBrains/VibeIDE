# Навигация по коду без языкового сервера

← [Индекс базы знаний](../README.md)

> **[решение]** 02.09.2026. Задача: «прыгать по методам» для PHP и TypeScript, **включая Windows**.
> В VibeIDEA это уперлось в стену: встроенный Phpactor на Windows не стартует — его phar требует
> расширение `posix`, которого в Windows-сборках PHP не существует.

---

## Что оказалось при разведке

| Язык | Переход к определению | Почему |
|---|---|---|
| TypeScript / JavaScript | **уже работает, и на Windows тоже** | `typescript-language-features` регистрирует `registerDefinitionProvider`; сервер — `tsserver` на Node, POSIX ему не нужен |
| PHP | **нет ни на одной ОС** | во встроенном `php-language-features` только три провайдера: completion, hover, signatureHelp |

То есть половина задачи в форке VS Code решена из коробки — расходится с VibeIDEA именно PHP.

## Ключ: грамматики tree-sitter уже в дереве

`@vscode/tree-sitter-wasm` поставляет **`tree-sitter-php.wasm`** и ещё четырнадцать грамматик: Go,
Java, Python, Ruby, Rust, C#, C++, Bash, TS/TSX/JS. Загружает их `ITreeSitterLibraryService`
(`getLanguage(languageId, ignoreSupportsCheck, reader)` — второй аргумент позволяет взять грамматику
мимо экспериментальной настройки подсветки).

**Почему это снимает стену Windows:** WASM исполняется внутри нашего Electron. Не нужен ни
установленный PHP, ни `posix`, ни WSL — то же поведение на всех трёх ОС, и никакой новой
зависимости: файлы уже лежат в сборке.

## Побочная находка: одна дыра порождает три

`repoIndexerService._extractSymbols` берёт символы через `documentSymbolProvider` — то есть через
языковые расширения. Для PHP такого провайдера нет, поэтому **PHP-символы не попадают ни в
RAG-индекс, ни в граф проекта**. Замкнутый круг: индекс не может помочь навигации, потому что сам
зависит от того, чего нет. Провайдер символов чинит сразу три поверхности: структуру файла, индекс и
граф.

## Грабля грамматики: `namespace X;` — сосед, а не родитель

Проверено на живой грамматике, а не по памяти:

| Форма | Дети узла `namespace_definition` | Поле `body` |
|---|---|---|
| `namespace App\Billing;` | `[namespace_name]` | **нет** |
| `namespace App\Billing { … }` | `[namespace_name, compound_statement]` | есть |

Первая форма — самая частая в реальных проектах — в синтаксическом дереве **не содержит** классов:
они идут следующими сиблингами. Обход, который просто спускается по детям, теряет namespace у
каждого класса, и переход к `App\Billing\Invoice` не находит ничего.

Поэтому обход несёт «действующее пространство имён», переживающее сам узел объявления, поверх
обычной вложенности. Дефект был найден прогоном по настоящему дереву — на выдуманных узлах он бы не
проявился.

## Границы, названные вслух

Это чтение **объявлений по форме дерева**, а не анализ типов. Два класса с одноимённым методом дают
два независимых объявления, и ничто здесь не решает, к какому из них относится вызов. Разрешение —
задача слоя навигации выше, и там оно должно быть названо честно, а не подразумеваться молчанием.


## Расширение на шесть языков (2026-09-03)

Механизм оказался языко-нейтральным: добавление языка — таблица «какие узлы считать объявлением»
плюс профиль (разделители FQN, оператор доступа, расширения файлов, имя файла грамматики). Ни строки
новой логики обхода.

**Таблицы снимаются пробой по живой грамматике, а не пишутся по памяти.** Имена узлов расходятся
сильнее, чем подсказывает интуиция:

| Что | Где лежит имя |
|---|---|
| Go, объявление типа | `type_declaration` → `type_spec` → поле `name` |
| Go, метод | владелец — в поле `receiver`, а не во вложенности: метод лежит на уровне файла |
| Java, поле | `field_declaration` → `variable_declarator` → `name` |
| C#, поле | на уровень глубже: `field_declaration` → `variable_declaration` → `variable_declarator` |
| Rust, `impl` | поля `name` нет вовсе — есть `type` |
| C#, грамматика | файл называется `c-sharp`, язык в редакторе — `csharp` |

**Четыре дефекта, которые не видны в коде и всплыли только на прогоне живых образцов:**

1. Ruby: `def helper` на верхнем уровне становился «методом» — базовым видом должна быть функция, а
   «метод» включаться только внутри контейнера (`kindInContainer`).
2. Rust: `impl Invoice` выдавал **второй** `Invoice` в аутлайне. Блок `impl` ничего не объявляет —
   тип объявлен в другом месте; он только открывает область (флаг `containerOnly`).
3. Go: метод при обходе по вложенности оставался без владельца — он и не вложен, владелец в ресивере.
4. Имя в `variable_declarator` не находилось без явного `nameField` — это поймал упавший тест, а не
   чтение кода.

**Оператор доступа обязан быть языковым, иначе тихо ломается PHP.** Точка — обращение к члену в Go,
Java, Python и C#, но **конкатенация строк в PHP**: универсальный разбор прочитал бы `$a . helper()`
как обращение к члену `$a` и ранжировал против владельца, которого нет. Пунктуация FQN тоже своя
(`App\Invoice::pay`, `App.Invoice.pay`, `App::Invoice#pay`) — её человек читает в аутлайне, и чужая
пунктуация делает верный ответ похожим на ошибку.

**TypeScript и JavaScript сознательно не берём:** встроенный `typescript-language-features` даёт
настоящий переход с выводом типов. Наш провайдер добавил бы вторые, менее точные варианты в тот же
список — редактор объединяет результаты всех провайдеров. По той же причине есть настройка
`vibeide.codeNavigation.languages`: если для языка стоит расширение с собственным сервером, наш
вклад можно убрать.
