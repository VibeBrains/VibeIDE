# Мост в Telegram: почему поллер в main и чем платит выбор транспорта

← [База знаний](../README.md)

**Дата:** 2026-08-06 · **Ветка:** `next` · **Область:** архитектура, внешние интеграции

## Контекст

Идея взята из разбора чужого проекта [eggent](https://github.com/eggent-ai/eggent). Из всего его набора (проекты-папки, дашборд, пайплайны, входящий API, Telegram) для нас ценным оказалось одно: **агент доступен, когда владелец не за IDE**. Остальное у нас либо есть богаче, либо требует сервера.

## Решение 1: свой бот у каждого, без нашего сервера

Telegram даёт webhook (нужен публичный HTTPS) или long polling (исходящее соединение). IDE стоит на личной машине без публичного адреса → webhook невозможен → polling. **Polling не требует посредника вообще.**

Значит наш сервер экономил бы пользователю ровно один поход к @BotFather — и взамен пропускал бы через себя переписку и куски кода, требовал аптайма, поддержки и соблюдения ToS Telegram. Решение владельца 06.08.2026: свой бот у каждого.

Дверь не закрыта: бизнес-логика моста (команды, прогресс, подтверждения) от транспорта не зависит, поэтому релей при реальном спросе добавляется вторым способом доставки. Специально абстракцию под это не закладывали — это было бы гадание.

## Решение 2: поллер живёт в главном процессе

Первая, «естественная» мысль — вести опрос из окна и координировать окна нашим `VibeMultiWindowCoordinator` (он уже есть и умеет владение через `.vibe/.window-lock.json`).

**Это неверный путь по двум причинам:**

1. Telegram отвечает `409 Conflict` второму, кто одновременно зовёт `getUpdates` по тому же боту. Симптом — мост молча замолкает; причина из UI не видна вообще.
2. Наш координатор работает **per-workspace** (лок лежит в `.vibe/` проекта), а бот у пользователя один на все проекты. Координация окон здесь не помогает — нужен процесс-одиночка.

Главный процесс Electron — ровно один на приложение. Перенос поллера туда убирает проблему целиком, а не смягчает её. Окна регистрируются в нём и получают адресованные им команды; `/use` переключает целевое окно.

Отдельно: текст `409` распознаётся и переводится человеческим языком («этот бот уже опрашивается другим приложением») — единственный случай, где родное сообщение не объясняет причину.

## Решение 3: HTML-режим вместо MarkdownV2

MarkdownV2 требует экранировать десяток знаков препинания (`_ * [ ] ( ) ~ \` > # + - = | { } . !`), которых полно в любом ответе модели. Один незаэкранированный символ в сгенерированном коде — и Telegram отвергает **сообщение целиком**: ответ не «выглядит хуже», а теряется.

HTML-режим требует экранировать три символа (`& < >`). Поэтому конвертируем нужные формы markdown в HTML сами (`common/telegram/telegramFormat.ts`).

Две неочевидности, обе закрыты тестами:

- **Содержимое code-блоков вынимается ДО применения инлайн-правил.** Иначе `**` внутри кода превратится в `<b>` и снипет будет испорчен.
- **Плейсхолдер выемки — на управляющих символах** (``), которых в сообщении Telegram быть не может. Текстовый маркер вроде ` FENCE0 ` модель может напечатать сама, и тогда чужой текст подменил бы код.

## Решение 4: свой прокси, отдельный от LLM

`api.telegram.org` и API моделей блокируются в разных местах, поэтому один адрес выхода не обязан подходить обоим. Для этого из `electron-main/llmMessage/systemCAFetch.ts` выделена `createProxyDispatcher(url, label)`: сборка диспетчера с системными CA перестала быть привязана к глобальному `_proxyUrl` LLM-канала.

**Грабля, на которую мы уже наступали (models.dev, 21.07):** голый `fetch`/undici минует и системные CA, и прокси. Любой наш исходящий канал обязан идти через диспетчер с CA, иначе он работает у нас и падает у пользователя с корпоративным CA или из-под блокировок.

**Вторая грабля, поймана при написании:** диспетчер нельзя строить на каждый запрос. При бесконечном polling это гарантированная утечка пула сокетов — кэшируем и пересоздаём только при смене адреса.

## Решение 5: привязка чата обязательна, молчание — отказ

Имя бота может узнать кто угодно, а команда боту = запуск инструментов на машине владельца. Поэтому первое сообщение от неизвестного чата **не выполняется**, а поднимает в IDE запрос на разрешение; список разрешённых чатов лежит в настройке и служит способом отозвать доступ.

Запрос подтверждения, оставшийся без ответа, по таймауту считается **отклонённым**: телефон мог лежать в кармане, и «нет ответа» не должно означать «да».

## Что вскрыл живой смоук (07.08.2026)

Компиляция, слои и 9 юнит-тестов были зелёными — все три дефекта нашлись только на живом боте.

1. **`409 Conflict` на ровном месте.** `stop()` менял поколение цикла, но не обрывал уже летящий 30-секундный `getUpdates`. Любое изменение настроек (в том числе привязка чата, которая пишет chat id в конфиг) перезапускало поллер — и на время дожития старого запроса по боту шли два опроса. Лечится `AbortController` на активный опрос; оборванный опрос при смене поколения не считается ошибкой, иначе в UI мигает ложная авария.
2. **Секрет не порождает события конфигурации.** Токен живёт в SecretStorage, поэтому его смена не приходит в `onDidChangeConfiguration`, и мост продолжал работать со старым токеном до перезагрузки окна. Подписка на `onDidChangeSecret` — обязательна для любой настройки, чьё значение хранится не в файле настроек.
3. **Диагностика была слепой.** Ошибки опроса и доставки уходили только в поле статуса. При молчащем боте лог выглядел как «всё в порядке» — худший из возможных симптомов. Теперь логируются `getUpdates failed`, результат каждой отправки и маршрут `chat → window`.

**Отдельно — ложная тревога, чтобы её не искали повторно:** ответ бота `Provider "zai" not recognized` не был дефектом моста. В проекте не было `providers.json`, а в настройках висела модель конфиг-провайдера из другого проекта; мост корректно доставил ошибку прогона. Прежде чем чинить интеграцию, проверьте, существует ли выбранный провайдер вообще.

## Решение 6: код привязки (07.08.2026)

Вопрос владельца: «если кто-то зайдёт в бота — будет доступ?». Доступа не было и до этого (нужна привязка с подтверждением), но чужой мог **бесконечно поднимать окно подтверждения** — имя бота публично.

Введён код привязки, и в нём три неочевидных решения:

- **неверный код обрабатывается точно так же, как отсутствующий** — молчанием. Любой ответ («код неверный») превращает бота в оракул для подбора;
- **групповой чат не привязывается даже с верным кодом**: там доступ принадлежит не человеку, а составу участников, который меняется без ведома владельца;
- **повтор от одного чата — не чаще раза в 10 минут**, иначе владелец кода может завалить IDE модалками.

## Решение 7: голосовые — переиспользовать конвейер `/watch`, а не писать декодер

Голосовые Telegram приходят в OGG/Opus, а офлайн-распознаватель принимает PCM16 16 кГц моно. Соблазн — вызвать ffmpeg прямо из моста. Правильный ход оказался другим: у видео-сервиса уже есть `analyze(localPath)` → `transcribe(requestId, profile)`, который делает ровно это (он же обслуживает аудио-вход `/watch`).

Что это дало, кроме экономии кода:

- **один бинарник на всё.** ffmpeg скачивается в `<userData>/video-tools`; свой путь означал бы вторую копию того же файла у пользователя;
- **готовая диагностика.** `getToolsState()` и `getBatchState(profile)` уже отвечают «готово / нет / качается» с объёмом загрузки — панель настроек строится на них, а не на самодельных проверках `existsSync`;
- **язык из одной точки.** Профиль резолвится той же `resolveVoiceProfile`, что и диктовка: иначе микрофон и голосовое сообщение распознавались бы на разных языках, и причину этого искать было бы мучительно.

Два решения про подачу, которые важнее кода:

- **расшифровка показывается до выполнения.** Бот присылает `🎧 «текст»`, и только потом запускает задачу. Распознавание неидеально; увидеть услышанное дешевле, чем разбираться, почему агент сделал не то;
- **первое голосовое при отсутствующих компонентах не молчит** — бот сразу пишет объём загрузки. Минута тишины неотличима от сломанного моста.

## Решение 8: подтверждение показывает действие, а не его номер (07.08.2026)

Запрос разрешения зеркалится из `_onStreamStateChanged`, из ветки `isRunning === 'awaiting_user'`: там же, где рисуется прогресс, и там же, где состояние однозначно означает «прогон стоит и ждёт человека». Что именно спросили, берётся из последнего сообщения треда (`role === 'tool' && type === 'tool_request'`), а ответ уходит через `approveLatestToolRequest` / `rejectLatestToolRequest`.

Четыре решения, принятые здесь:

- **Превью строится из `rawParams`, а не из описаний инструментов IDE.** Описания живут в React и требуют accessor — недостижимо ни из main-стороны окна, ни из теста. Значения показываются как есть, в code-span: пересказ shell-команды своими словами — ровно то, что нельзя одобрять не глядя. Функция чистая (`common/telegram/telegramFormat.ts`), поэтому проверяется тестом без бота.
- **Повтор ловится по id вызова инструмента, а не по состоянию.** Тред перезаходит в `awaiting_user` на каждом событии стрима, пока ждёт; сравнение состояний присылало бы одну и ту же кнопку десятками.
- **Политика зеркалирования не умеет одобрять.** `vibeide.telegram.approvals` решает только, показывать ли запрос на телефоне; незеркалированный ждёт в IDE. Автоодобрение — отдельная, осознанная настройка, и до неё не должно быть дороги через послабление настройки Telegram. Неклассифицированный инструмент считается опасным: лишний тап дешевле молча зависшего прогона.
- **Нажатие проверяется по allow-list чатов.** Кнопка — такой же входящий, как сообщение; чат, потерявший привязку, не должен рулить прогоном через старую клавиатуру. Плюс `answerCallbackQuery`: без него кнопка крутится, и владелец не понимает, дошёл ли тап.

«✏️ Поправить» — третий исход, которого нет в IDE: отказ **плюс** ожидание уточнения, которое уходит в тот же тред. Без него единственный способ развернуть неверный вызов с телефона — отклонить и продиктовать задачу заново, потеряв контекст.

### Принцип, которым проверяется любая будущая настройка подтверждений

«Доступом управляют ключи, а не промпты» (формулировка из гайда brain_ru, 08.08): «не удаляй это» — пожелание, а право только на чтение — настройка. Отсюда правило для моста: послабление любой telegram-настройки не должно открывать дорогу к выполнению действия без человека. `approvals` поэтому умеет только «показывать / не показывать», а автоодобрение живёт отдельно и включается осознанно.
