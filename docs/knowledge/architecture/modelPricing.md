# Прайс моделей: где брать цену за токен и ловушка единиц

← [Knowledge Index](../README.md)

Как посчитать ≈$ за прогон (модель, promptTokens, completionTokens); почему каталожный `cost` нельзя использовать как есть. Итог разведки 2026-07-11 (аудит Vibe Agents).

---

## [архитектура] Основной API — `getModelCapabilities().cost` (USD за 1M токенов)

**Контекст:** для субагентов понадобилось показывать ≈$ в отчёте/уведомлениях (2026-07-11).

**Суть:** единственный рабочий источник прайса — чистая функция `getModelCapabilities(providerName, modelName, overridesOfModel, catalogInfo?)` из `common/modelCapabilities.ts` (common → свободно импортируется из browser; примеры вызова — `chatThreadService.ts`, `convertToLLMMessageService.ts`; `overridesOfModel` — из `IVibeideSettingsService.state`). В результате поле `cost: { input, output, cache_read?, cache_write? }` — **USD за 1 МИЛЛИОН токенов** (подтверждение единиц: `modelRouter.ts` и `routingCapabilityRegistry.ts` считают его как `costPerM`; sonnet = 3/15). Расчёт: `usd = prompt/1e6*cost.input + completion/1e6*cost.output`. **`{input:0, output:0}` = «прайс неизвестен» (дефолт нераспознанной модели), НЕ «$0»** — не показывать как ноль. `'auto'`-selection отсечь заранее (`isValidProviderModelSelection`). Готовый хелпер для субагентов: `common/subagentCostEstimate.ts` (`subagentCostUsd` + `formatUsd`).

**Применение:** любое отображение стоимости прогона; НЕ использовать `IVibeTokenCostForecastService.getPricing` (захардкоженная таблица из 7 устаревших семейств, ключ без провайдера — слабый API).

## [баг] Каталожный `cost` — за ОДИН токен, статическая таблица — за 1M: расхождение 1e6

**Контекст:** та же разведка; влияет не только на субагентов.

**Суть:** парсеры удалённого каталога (`remoteCatalogService.ts`) кладут в `RemoteModelInfo.cost` цены **за один токен** (LiteLLM `input_cost_per_token`, OpenRouter `pricing.prompt`) без нормализации, а статическая таблица `modelCapabilities.ts` — **за 1M**. `catalogFields()` мержит каталожный cost поверх статического → у каталожных моделей `caps.cost` в единицах per-token, и **`modelRouter.costPerM` на них врёт в 1e6 раз** (пороги cost-роутинга < 1/5/15 всегда «дёшево»). Поэтому для расчёта $ вызывать `getModelCapabilities` **БЕЗ `catalogInfo`** (гарантированно per-1M) — так делает `subagentCostEstimate.ts`. Полный фикс (нормализация при парсинге каталога) — техдолг в roadmap VA.6.

**Применение:** при любом использовании `caps.cost` спросить себя, мог ли прийти каталожный override; при фиксе роутинга по цене — начать с нормализации в `remoteCatalogService`.

## [баг] Новые модели семейства проваливаются на профиль Pro с нулевой ценой (Gemini, 2026-07-25)

**Контекст:** разбор дайджеста 25.07 — релиз `gemini-3.6-flash` и `gemini-3.5-flash-lite` (21.07.2026, [latest-model guide](https://ai.google.dev/gemini-api/docs/latest-model)). В `modelCapabilities.ts` их профилей нет.

**Суть — ДВА независимых дефекта, второй нашёлся только при починке первого (оба закрыты 2026-07-25):**

1. **Широкая ветка резолва стояла без охраны узких случаев:** `lower.includes('gemini-3') → 'gemini-3-pro-preview'` (`extensiveModelOptionsFallback`). Любой новый `gemini-3.x` — Flash, Flash-Lite, что угодно — матчился ею и получал профиль **Pro**: чужой `reservedOutputTokenSpace`, чужие уровни размышления.
2. **Цену обнулял сам `toFallback`, а не профиль.** Внутри стояло `cost: { input: 0, output: 0 }` жёстко, после спреда `...opts` — то есть **любая** модель, распознанная через fallback, у **любого** провайдера получала нулевую цену; перекрыть её мог только второй аргумент `fallbackKnownValues`, а `getModelCapabilities` зовёт fallback **с одним аргументом**. Цены из профилей в этом пути не участвовали вообще. Поэтому «поставить цену в профиль» первый дефект бы не вылечило — оценщик всё равно печатал бы $0.00, а `modelRouter.costPerM` считал бы модель бесплатной и охотно её выбирал.

Почему ноль вообще там оказался: fallback обслуживает и локальные провайдеры (ollama / vLLM / LM Studio), где инференс реально бесплатен. Лечение — не убрать ноль, а **перенести его туда, где он правда**: `toFallback` берёт цену распознанного собрата (`opts.cost ?? {0,0}`), а три локальных провайдера передают явный `cost: {0,0}` через `fallbackKnownValues`, который по-прежнему выигрывает спредом.

**Применение:**
- Добавляя семейство в таблицу с подстрочным резолвом — узкие ветки **перед** широкой; широкая должна ловить только то, для чего она и писалась.
- **Ноль — это не «неизвестно», это «бесплатно».** Ни в профиле, ни в дефолте не оставлять `cost: {0,0}` как заглушку: приблизительная цена похожей модели честнее, потому что не врёт роутеру в другую сторону. Заглушку `TODO: Verify pricing` считать багом, а не пометкой. **Подтверждено кодом 26.07:** `modelRouter` (`:1153-1155`) при `preferLowCost` начисляет `costPerM === 0` **+10 к скору как «free models»** — то есть нулевая цена не просто «неточность в отчёте», она активно двигает модель наверх в выборе.
- **Комментарий рядом с ценой — тоже подозреваемый.** У профилей MiniMax семь недель стояло `cost: { input: 0, output: 0 }, // informational only; not used for routing`. Утверждение было ложным (см. выше), и именно оно мешало заметить дефект: читающий верил комментарию и шёл дальше. Проверять такие оговорки грепом по потребителю поля, а не принимать на веру.
- **«Нет ветки резолвера» — тот же дефект, что и нулевая цена.** У GLM и Kimi веток не было вовсе: любой их id падал на `defaultModelOptions` (цена ноль) — семейство, которое мы поддерживаем рецептами в `.vibe-defaults`, для роутера выглядело бесплатным. Добавляя семейство в примеры провайдеров, сразу заводить ветку и профиль с ценой.
- Гейт против рецидива — `test/common/geminiModelResolve.test.ts`: ни один профиль без `-exp-` в id не имеет нулевой цены (таблица экспортирована ради обхода **всех** записей, а не списка id руками), плюс кейсы на резолв несуществующих ещё `gemini-3.9-flash` / `gemini-3.1-flash-lite`.
- Методический вывод: заявка в roadmap описывала следствие («профиль Pro с нулевой ценой»), а причина оказалась на слой ниже и шире одного семейства. **Перед фиксом по заявке — пройти путь данных до конца**, иначе чинится симптом в одном семействе, а класс остаётся у всех.

**Связано:** [[modelQuirks]] — там же зафиксирован депрекейт sampling-параметров у новых Gemini и переход на `thinking_level`.

## [закрыто] Каталожный `cost` приходил per-token и врал в миллион раз (06.08.2026)

**Что было:** LiteLLM отдаёт `input_cost_per_token: 0.000003`, OpenRouter — `pricing.prompt: "0.000003"` (строкой!), а `getModelCapabilities().cost` и все его потребители — спенд-леджер, прогноз стоимости, тиры «дёшево/дорого» у роутера — считают в долларах за **миллион**. Сырое число уходило в поле как есть, поэтому каталожная модель выглядела в миллион раз дешевле: роутер видел почти ноль и охотно отправлял туда работу, а панель расхода показывала копейки вместо долларов.

**Второй дефект рядом:** у OpenRouter значение приходит строкой, а код брал `pricing.prompt || 0` без проверки типа — строка проникала в числовое поле, и дальше арифметика давала мусор молча, а не ошибку.

**Как закрыто:** чистый модуль `common/catalogPricing.ts` (5 тестов):

- `parseCatalogPrice` принимает число или числовую строку, всё прочее — `undefined`;
- `perMillionFromPerToken` умножает на 1e6;
- `normaliseCatalogCost` нормализует пару **целиком или никак**.

**Три решения, которые стоит помнить:**

1. **Пара цен нормализуется вместе.** Если бы уцелела половина, отчёт сказал бы «вход $3/M, выход бесплатно» — читается как выгодная модель, а не как отсутствующие данные.
2. **Ноль пропускается.** Каталог, сказавший «бесплатно», делает утверждение; локальные провайдеры (ollama, LM Studio) правда бесплатны. Отбрасывать ноль значило бы врать в другую сторону.
3. **Потолок правдоподобия $1000/M.** Значение выше означает, что каталог уже отдал цену за миллион и умножение было бы вторым, — такая цена отбрасывается. Неверная цена хуже отсутствующей: отсутствующую мы честно показываем как «неизвестно», а неверной молча доверяют.

## [архитектура] У цены есть срок годности, и хранить только текущую — значит однажды соврать (2026-09-08)

**Контекст:** дайджест 08.09.2026 — четыре объявленных подорожания подряд: GLM-5.3-Flash ×2 09.09, Upstage Solar Pro 4 ×10 10.09, Ling 3.0 Flash Fin с бесплатного 25.09, Gemini 3.6/3.7 Flash ×2 с 01.01.2027 (кэш и батч масштабируются тем же коэффициентом).

**Суть:** вендор публикует **обе половины сразу** — «$0.075 / $0.25 до 09.09, дальше вдвое», — а мы хранили только первую. Отчёт о расходе продолжает считать по акции после её конца, и пользователь узнаёт настоящую сумму из счёта вендора, то есть там, где мы её уже не исправим. Появились `costValidUntil` / `costAfter` / `costNote` в файле провайдера и `costSchedule` у встроенных моделей; разрешение — в единственной точке `getModelCapabilities`, чтобы отчёт, роутер и предварительная оценка не разошлись в том, сколько модель стоит сегодня.

Две неочевидности:

- **Момент, а не дата.** Дедлайны объявляются в местном времени вендора («24:00 UTC+8 09.09»), и округление до даты ошибается почти на сутки — в сторону, которая стоит денег. Поэтому `parseDeclaredMoment` принимает и голую дату (читается как полночь UTC), и полный ISO-момент со смещением.
- **Дата без новой ставки не значит ничего.** `costValidUntil` в одиночку сообщает, что акция кончится, но не чем её заменить; применять нечего, и придумать число хуже, чем оставить старое. Поэтому расписание срабатывает только вместе с `costAfter`.

**Побочная находка, ради которой стоило копать:** встроенный `gemini-3.6-flash` нёс цену **2027 года** ($1.50/$7.50) при действующей вводной вдвое меньше — то есть весь 2026-й завышал любую оценку в два раза. Обратная ошибка того же рода: хранишь один момент из двух — врёшь либо до даты, либо после.

**Применение:** добавляя модель с промо-ценой, класть обе ставки и момент перехода сразу; при разборе жалобы «отчёт не сходится со счётом» — первым делом проверить, не истекла ли акция. Таймер в `vibeDynamicProvidersService` пересчитывает цену в момент перехода, но ограничен неделей на итерацию: `setTimeout` выше ~24.8 суток срабатывает мгновенно, и наивная версия крутила бы reload в цикле.

## [грабля] Неизвестное поле в сиде отбрасывается молча — две машины разошлись в именах (2026-09-08)

**Контекст:** цену со сроком годности в тот же день делали с двух сторон. На маке появились
`cost` / `costValidUntil` / `costAfter` в коде и спеке; на виндовой машине в наборе сидов
(VibeBrains) — `pricing` / `priceValidUntil` / `priceAfter` с полем `currency`.

**Суть:** разбор `providers.json` **игнорирует незнакомые поля** — иначе чужой файл из будущей
версии ронял бы весь набор. Побочный эффект: сид с неверными именами выглядит рабочим, проходит
любую проверку синтаксиса, засевается в проект — и не объявляет ничего. Засеянный Gemini не нёс ни
цены, ни срока, и заметить это можно было только по отсутствию предупреждения, которого никто не
ждёт.

Сведено к `cost*`: цена живёт в том же объекте `cost`, который читался и до появления срока
годности, а `currency` в формате нет и не будет — прайсы вендоров всегда USD за 1M токенов, и
второе поле про валюту означало бы, что где-то её нужно конвертировать.

**Применение:** новое поле формата считается сделанным, когда оно есть **в трёх местах сразу** —
тип, JSON-схема и спека; сид, написанный мимо них, тихо мёртв. Если поле придумано на другой
машине — сверить имена до коммита в набор: submodule проверяет только то, что коммит существует,
а не то, что продукт умеет его читать.

**Закрыто гейтом (08.09.2026):** `npm run seed-fields-check` разбирает засеваемые файлы провайдеров
и требует, чтобы каждое поле записи провайдера и модели знали И тип, И спека. Внутрь `extraBody`,
`headers`, `query` и `env` гейт не смотрит — там вендорский словарь, не знать который и есть смысл
этих полей. Проверено подменой: `costValidUntil` → `priceValidUntil` красит гейт и называет файл,
модель и поле.

## [правило] Оркестратор Sakana Fugu: обязательное размышление, своя лестница и ступень цены (2026-09-12)

**Контекст:** запись провайдера уехала в общий набор, и модель-оркестратор ведёт себя не как обычная
OpenAI-совместимая: у неё своя лестница усилий и цена, которая зависит от длины ввода.

**Суть:**
- Профили `fugu-max` и `fugu-ultra` заведены в таблицу возможностей: ползунок `high | xhigh | max`,
  дефолт `high` у Max и `xhigh` у Ultra, размышление не выключается. Значения `low` и `medium` API
  отвергает ошибкой — наш прежний дефолт упёрся бы в неё на первом же запросе.
- Идентификаторы различаются по маршрутам: у вендора Ultra v2 зовётся `fugu-ultra`, у OpenRouter —
  `fugu-ultra-v2`. Ветка подбора ловит обе формы по подстроке, узкая идёт выше общей.
- `max` вендор принимает как синоним `xhigh`; отдельный уровень есть только у `fugu-ultra-v1.1`.
  В ползунке значение оставлено: оно валидно на всех маршрутах.
- Цена Ultra ступенчатая: выше 272K токенов ввода $5/$30 превращаются в $10/$45. Ступень заполнена
  в профиле (12.09.2026) — см. запись ниже.
- Счёт больше видимого: токены оркестрации биллятся как обычный ввод-вывод, разбивка приходит в
  `usage.token_details`. Для правильности счёта она не нужна: эти токены уже входят в
  `promptTokens`/`completionTokens`, и леджер считает их верно.

**Проверено 12.09.2026:** консоль вендора и живой каталог OpenRouter; цифры и набор значений — оттуда.

## [правило] Ступень цены была механизмом без данных (2026-09-12)

**Контекст:** в бэклоге стояло «ступенчатая цена не поддерживается». Проверка кода показала другое:
поле `long_context` в `ModelCost` и его применение в `costOf()` существуют с самого начала —
не хватало не механизма, а данных, которые в него никто не клал.

**Суть:**
- **Ни один встроенный профиль не заполнял ступень.** Заполнены два, у которых она подтверждена
  вендором: `fugu-ultra` (порог 272K, вход ×2, выход ×1.5, кэш ×2) и `MiniMax-M3` (порог 512K,
  вход и выход ×2; множитель кэша вендор не публикует, поэтому он остался 1 — необъявленный
  множитель не выдумывается).
- **Цена каталога теряла всё, кроме двух ставок.** `normaliseCatalogCost` возвращала `{input, output}`,
  а `catalogFields` собирала объект заново по двум полям — так до леджера не доходили ни ставки
  кэша, ни ступень. Каждый кэшированный токен модели из каталога считался по полной цене ввода.
- **У OpenRouter ступень лежит в `pricing.overrides`** — списком, где запись с `min_prompt_tokens`
  задаёт абсолютные ставки выше порога. Мы переводим их в множители: одно представление в коде
  вместо двух расходящихся.
- **Временны́е записи того же списка не берутся.** Рядом живут `utc_days` и `utc_start`/`utc_end` —
  скидки по часам. Они зависят от момента запроса, а скидка, прочитанная как наценка, хуже
  отсутствующей ступени.
- **Из нескольких порогов берётся нижний:** наш тип держит одну ступень, а нижнюю пересекает почти
  каждый запрос, который вообще их пересекает.

**Проверено 12.09.2026:** живой `https://openrouter.ai/api/v1/models` — 69 моделей с `overrides`,
у `sakana/fugu-ultra` запись ровно та, что зашита в профиль.
