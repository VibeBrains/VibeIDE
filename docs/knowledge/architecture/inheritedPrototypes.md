## [архитектура] Что это было и почему удалено

**Контекст:** 2026-07-15, подготовка сплита `vibeide/common`. Новый гейт `npm run service-registration-check` (достижимость модулей с `registerSingleton` от точек входа) нашёл **7 файлов**, чей `registerSingleton` не выполняется никогда: у них ноль импортирующих во всём `src/`. Все датируются `Initial import: VibeIDE` (2026-05-05) — то есть **достались с базой форка** (Cortex/Void), а не были начаты нами и брошены.

**Суть:** удалённый кластер (коммит-удаление 2026-07-15, код доступен в истории git):

| Файл | Строк | Что было |
|---|---|---|
| `common/applyEngineV2.ts` | 517 | Pre-apply verification по хешу содержимого |
| `common/routing/adaptiveRouter.ts` | 430 | Роутер моделей, обучающийся на журнале исходов |
| `common/telemetry/*` (5 файлов) | 1171 | Журнал исходов + хранение + аналитика; кормил только adaptiveRouter |
| `common/routing/speculativeEscalationValidator.ts` | — | Валидатор спекулятивной эскалации |
| `common/routingSmokeTests.ts` | — | Смоук-прогоны роутинга (не настоящие тесты, вне `test/`) |
| `browser/_markerCheckService.ts` | 138 | Сбор quick-fix'ов по маркерам |
| `browser/_dummyContrib.ts` | 64 | Шаблон «как завести сервис» |

**Почему удалено, а не подключено:** мёртвая регистрация — это ложный сигнал. Сервис виден в коде, экспортирует декоратор, компилируется — и не существует в рантайме. Следующий разработчик либо поверит, что фича есть, либо продублирует её. Идея ценнее кода: код лежит в git, идея — здесь.

## [идея] Вектор 1 — роутер, обучающийся на журнале исходов

**Контекст:** `common/modelRouter.ts` у нас **живой** (используется `chatThreadService`), но чисто rule-based: роли, лимиты, цена. Унаследованный `adaptiveRouter` предлагал следующий шаг.

**Про имя — важно.** Унаследованная подсистема называлась `telemetry/`, и это слово мы употреблять не будем. VibeIDE позиционируется **против** телеметрии: заголовок README — «Без телеметрии», таблица сравнения — «Телеметрия вендору ❌ Нет», `securityFaq.md` — «Телеметрия ✅ Отключена». Внутренняя подсистема с таким именем читается как противоречие обещанию, даже будучи локальной. Имя вектора — **«журнал исходов роутинга»**, в коде `routingOutcomeLog` (запасной — `routingFeedback`): **журнал** = локальная запись, а не отправка; **исходов** = факт «что вышло», а не наблюдение за пользователем; **роутинга** = узкая область. Не путать с `auditLogService` — тот про действия агента и GDPR-экспорт, другая сущность.

**Суть замысла** (философия из его шапки — «simple base rules + learned adjustments from telemetry»):

- `route(context: TaskContext): Promise<RoutingDecision>` + `updateFromTelemetry(): Promise<void>` (по расписанию, раз в час).
- Скоринг двухслойный: `finalScore = baseScore + learnedAdjustment`, где поправки живут в `Map<string, number>` по ключу «модель × тип задачи» и пересчитываются из фактической результативности.
- `RoutingDecision` нёс не только выбор, но и **самооценку**: `confidence`, `reasoning` (текстом), `qualityTier`, `timeoutMs` и — важное — `shouldAbstain` + `abstainReason`. Роутер имел право **отказаться** («моделей нет / не уверен»), а не выбирать наугад.

**Применение:** если возвращаемся к теме — брать не код, а два принципа: (1) поправки поверх правил, а не замена правил ML-чёрным ящиком; (2) явный abstain вместо тихого «выбрал хоть что-то». Персистентность поправок в прототипе не была сделана (комментарий «could persist to storage») — это и есть первая нерешённая задача.

**Модель данных, которой кормился роутер** (унаследованная подсистема `common/telemetry/`, 1171 строка, удалена — восстанавливать по описанию, а не по коду; при возврате называть `routingOutcomeLog`):

- **Таксономия задач** — `TaskType = 'chat' | 'code' | 'vision' | 'pdf' | 'web_search' | 'eval' | 'general'`. Это ключ, по которому копились поправки «модель × тип задачи».
- **Три типа событий** — `'routing'` (решение роутера), `'model_performance'` (как отработала модель), `'optimization_impact'` (что дала поправка). `RoutingDecisionEvent` нёс не только выбор, но и факт исхода: `used`, `completed`, `error` — то есть замыкал петлю «решили → что вышло».
- **Хранение** (`telemetryStorage`, 330 строк): локально, gzip, автоматическая ротация с retention 30 дней. При возврате сетевого sink не заводить **вовсе** — не «выключен по умолчанию», а отсутствует: иначе «без телеметрии» становится вопросом настройки, а не свойством продукта.
- **Аналитика** (`telemetryAnalytics`, 273 строки): рейтинги моделей, вычисление quality score, детекция паттернов роутинга, предложения по оптимизации.

**Сигнал качества, который уже собирали и выбрасывали** (`metricsService`, удалён 2026-07-15): живые `editCodeService` и `vibeideCommandBarService` звали `capture('Accept Diff', { diffid })` / `capture('Reject Diff', …)` — и вызов уходил по IPC в `NoOpMetricsClient`, где тела методов пустые («PostHog removed from OSS dependency tree»). То есть **accept/reject правки — готовый сигнал качества**, который система уже умела снимать в нужной точке и терять. При возврате к вектору писать его в `routingOutcomeLog`: «модель X на задаче типа Y → правку приняли/отклонили» и есть тот `model_performance`, которого прототипу не хватало. Ценна именно точка съёма — она уже в живом коде правок, ничего изобретать не нужно.

**Антипаттерн — и причина смерти:** журнал завели раньше потребителя. `telemetryService` тянул только `adaptiveRouter`, а `adaptiveRouter` — никто; события в него не писал **ни один** живой сервис. Получилась замкнутая мёртвая петля из 1601 строки, которая при этом выглядела работающей: свой `README.md` заявлял «foundation for all adaptive optimizations… tracks every AI interaction with zero performance overhead». Если возвращаемся — первым делом писать исходы из живого пути (`chatThreadService` → `modelRouter`), и только когда данные реально копятся, строить поверх них поправки.

## [идея] Вектор 2 — pre-apply verification по хешу

**Контекст:** наш edit-safety (`toolSystem/editSafety.md`) закрывает «сначала прочитай» и truncation-guard. Защиты от «файл изменился между чтением и записью» у нас **нет**.

**Суть замысла:**

- `FileBaseSignature { uri, hash /* SHA-256 содержимого */, isDirty /* true = буфер редактора, false = диск */ }` — снимок состояния на момент чтения.
- Перед применением правки сверяется фактический хеш с базовым; отдельно фиксировался `expectedHash` **итогового** содержимого.
- Операции описывались единообразно: `{ uri, type: 'edit'|'create'|'delete', content?, textEdits? }` — то есть движок применял пачку атомарно и возвращал `{ success, appliedFiles }`.

**Ключевая деталь замысла — `isDirty`:** сигнатура различала «прочитано с диска» и «прочитано из грязного буфера». Без этого хеш-проверка ложно срабатывает на любом несохранённом файле.

**Применение:** вектор актуален для агентских правок пачкой — между чтением и записью успевает вклиниться и пользователь, и другой агент (см. территориальные локи). Web Crypto (`crypto.subtle`) выбран ради кросс-платформенности — в `common/` это легально.

## [идея] Вектор 3 — сбор quick-fix'ов IDE вместо токенов LLM

**Контекст:** маркеры (ошибки линтера/тайпчекера) у нас читает живой `common/errorDetectionService.ts`. Но **программного сбора и применения code actions** нет — repair-loop чинит ошибки, тратя токены модели.

**Суть замысла** (`_markerCheckService`): по маркеру строится `Range`, у `ILanguageFeaturesService` запрашиваются провайдеры code actions на этот диапазон, из ответа фильтруются предпочтительные. В коде остался закомментированный фильтр именно под импорты — `action.isPreferred && action.title.includes('import')`.

**Применение:** самый дешёвый вектор из трёх. Отсутствующий импорт, неверный путь, автофикс тайпчекера — IDE чинит их детерминированно и бесплатно; отдавать это модели значит платить токенами за то, что уже умеет редактор. Разумный порядок в repair-loop: сперва квик-фиксы IDE, LLM — только на то, что осталось.

**Ловушка:** `getCodeActions` асинхронен и требует `ITextModelService.createModelReference` + обязательный `dispose()` ссылки — прототип это делал; при переносе не потерять.

**Связано:** [[verifyBeforeHypothesizing]] («зелёный чек ≠ работающий чек» — мёртвая регистрация того же рода: код есть, поведения нет), [orphanServices.md](orphanServices.md) (там `telemetry` числится как сервис без ссылки в роадмапе — этот гейт объяснил, почему), [editSafety.md](../toolSystem/editSafety.md), [llmAndContext.md](llmAndContext.md).
