# Хуки проекта: детерминированный контроль вокруг агента

← [Knowledge Index](../README.md)

## [архитектура] Почему хук, а не ещё одно правило

Правило в промте (`.vibe/rules`, `CLAUDE.md`) просит модель вести себя определённым образом. Обычно она слушается — но «обычно» и есть проблема: чем длиннее прогон, тем дешевле правило стоит. Хук ничего не просит. Он запускает команду, которой проект уже доверяет (линтер, тесты, свой скрипт), и решение принимает **код выхода**, а не модель.

Отсюда формулировка, ставшая для нас правилом отбора: «не трогай `migrations/`» — пожелание; `preToolUse`-хук, выходящий с кодом `2` на путь внутри `migrations/`, — факт. Тот же принцип уже записан в [telegramBridge.md](telegramBridge.md) решением 9 («доступом управляют ключи, а не промпты») — здесь он получил исполнительный механизм.

Идея — из разбора практик harness-инженерии (awesome-harness-engineering, 08.08.2026): «lifecycle-hook framework» там назван одним из двух механизмов, отличающих харнесс от обёртки над моделью. Код не заимствовался, формат наш.

## [архитектура] Три события и почему их именно три

- **`preToolUse`** — единственное место, где отказ ещё что-то меняет: инструмент не выполняется. Отказ приходит агенту как результат его собственного действия, то есть ровно туда, где он читает исход.
- **`postToolUse`** — действие уже произошло, отменить его хук не может; его вердикт приклеивается к результату инструмента (`[проверка проекта] …`), чтобы «почини это» лежало рядом с тем, что чинить.
- **`turnEnd`** — ход закончен, блокировать нечего; сообщение приходит в тред как требование, на которое агент отвечает следующим ходом.

Событий сознательно не больше: каждое обязано отвечать на вопрос «что изменится от отказа». Момент, где отказ ничего не меняет, — это лог, а не хук.

## [правило] Код выхода: почему отказ — это `2`

| Код | Смысл |
|---|---|
| `0` | Разрешено; stdout уходит агенту заметкой |
| `2` | Отказ с причиной (stderr, иначе stdout) |
| прочее, таймаут, несостоявшийся запуск | Поломка **самого хука**: предупреждение пользователю, работа продолжается |

Единицу возвращает любой сломанный скрипт: нет бинарника, опечатка в пути, синтаксическая ошибка. Если бы `1` блокировала агента, опечатка в хуке молча запирала бы проект — поэтому остановить работу можно **только намеренно**. Асимметрия здесь и есть свойство безопасности.

## [правило] Три замка перед запуском

Хук выполняется, только если: включена настройка `vibeide.hooks.enabled` (**по умолчанию выключена**), папка доверенная (Workspace Trust — переиспользован механизм апстрима, а не изобретён свой), и файл разобрался без ошибок. Клонирование чужого репозитория не должно означать выполнение его кода; при этом молчать о наличии хуков нельзя — IDE один раз предлагает кнопку «Включить».

Битая запись **не применяется частично**: хук, который сработает иначе, чем написал автор, хуже, чем не сработавший. Причина каждой отброшенной записи печатается.

## [правило] Что вскрыл собственный тест

Ожидание «три проблемы разбора» в тесте было записано прикидкой, а фактически их четыре (неизвестное событие, пустая команда, `tools` при `turnEnd`, урезанный таймаут). Исправлено ожидание, а не парсер — тот же класс промаха, что уже дважды ловили в дизайн-правилах; см. [[designReview]].

## [архитектура] Где что лежит

- `common/hooks/hookConfig.ts` — формат и разбор (чистое, 3 теста).
- `common/hooks/hookOutcome.ts` — вердикт по коду выхода и свод по событию (чистое, 2 теста).
- `common/hooks/vibeHookTypes.ts` — контракт канала и интерфейс сервиса (объявлен в `common`, чтобы цикл чата из `browser/` не тянул электронный слой).
- `electron-main/hooks/vibeHooksMainService.ts` — запуск процесса: stdin, exit code, SIGKILL по таймауту. В окне этого нет, а терминальный сервис не отдаёт ни stdin, ни код выхода.
- `electron-browser/hooks/vibeHooksService.ts` — три замка, кэш файла с вотчером, последовательный прогон, уведомления «один раз на проблему».
- Проводка — `browser/chatThreadService.ts`: перед вызовом инструмента, после него и рядом с VERIFY-GATE в конце хода.

Спека формата (пригодна к скармливанию модели) — `docs/manuals/hooksSpec.md`, образец засевается в `.vibe/hooks.example.jsonc`.

## [факт] Живой смоук (09.08.2026)

Прогон в dev-IDE на стенде с тремя хуками, модель MiniMax-M3 — все три ветки контракта подтверждены:

- **Отказ (`exit 2`) на `preToolUse`:** инструмент `read_file` **не выполнился**, а агент получил причину дословно — в чате `Error: Действие остановлено проверкой проекта: читать этот проект запрещено политикой стенда`, и дальше он объяснил пользователю, что содержимое файла получить не удалось. То есть отказ доехал именно туда, где агент читает исход своего действия.
- **Сломанный хук (`exit 1`) на `ls_dir`:** инструмент **отработал нормально**. Единица не блокирует — ровно то свойство, ради которого отказ сделан кодом `2`.
- **Заметка (`exit 0` + stdout) на `postToolUse`:** дословный вывод инструмента создания файла оказался таким:

  ```
  Empty file created at /tmp/hookstand/note.txt. It has NO conte…

  [проверка проекта] проверка проекта: файл записан
  ```

  Заметка приклеилась к результату инструмента, а не улетела в отдельное сообщение.

**Не прогнано:** событие `turnEnd` (проверялись три ветки на инструментах; конец хода требует прогона, меняющего файлы).
