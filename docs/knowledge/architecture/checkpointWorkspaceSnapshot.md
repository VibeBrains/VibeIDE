# Снимок рабочей папки в чекпоинтах

**Домен:** architecture · **Заведено:** 2026-08-10 · **Обновлено:** 2026-10-21 (возврат папки и разбор правок ACP; прежде — 2026-10-16: общий контракт, `-z`, `changed`, ACP) · **Ветка:** `next`

## Дыра, которую закрывает

Чекпоинт чата хранил `voidFileSnapshotOfURI` — содержимое только тех файлов, которые прошли через
`editCodeService`. Всё, что изменило дерево иначе, для отката не существовало: сборка, `git checkout`,
`sed` в терминале, скрипт, запущенный самим агентом. Откат восстанавливал известные файлы и молча
оставлял остальные — это хуже, чем не откатывать вовсе, потому что результат выглядит как чистый
возврат. Дыра подтверждена кодом: `chatThreadService.ts` собирает снимок из моделей, известных
`vibeideModelService`.

## Механизм

Снимок — объект-дерево git, записанный через **временный индекс** (`GIT_INDEX_FILE`), поэтому
настоящий индекс пользователя (его `staged`-правки) не трогается вовсе. Проверено фактом: после
снимка и восстановления `git status` показывает ровно то же, что показывал до.

`git stash create` не подошёл и рассматриваться не должен: он **не берёт untracked-файлы**, а
untracked-вывод — это ровно то, что производит работа в терминале.

Ключевая деталь производительности, без которой механизм неприменим: временный индекс **засевается
копией настоящего** (`.git/index`). На пустом индексе `git add -A` перехэширует всё дерево — на
репозитории такого размера это секунды на каждый чекпоинт; на засеянном срабатывает stat-кэш git и
хэшируется только изменившееся.

Снимок берётся **на пользовательском чекпоинте**, а не на каждой правке инструмента: это и есть
граница, к которой откатываются («до хода агента»), и один `git add -A` на ход допустим, а один на
файл — нет.

## Снимок обязан быть достижимым

Голое дерево от `write-tree` ни на что не ссылается, и `git gc` вправе его удалить. Это не теория:
`git gc --prune=now` сделал только что записанное дерево нечитаемым — то есть чекпоинт хранил бы
хэш объекта, которого больше нет, и восстановление ломалось бы молча, тем позже, чем старше
чекпоинт.

Поэтому дерево заворачивается в **коммит без родителя**, а коммит получает ссылку в приватном
namespace `refs/vibe/checkpoints/<id>`. Проверено: снимок пережил `gc --prune=now`, содержимое
читается, `git branch -a` не изменился, ссылка видна только через `for-each-ref refs/vibe/`.
`read-tree`, `ls-tree` и `checkout-index` принимают commit-ish, поэтому остальной механизм не
менялся — в чекпоинте просто лежит id коммита вместо id дерева.

Личность коммита своя (`VibeIDE <snapshot@vibeide.local>`) и передаётся через `GIT_AUTHOR_*` /
`GIT_COMMITTER_*`: `commit-tree` без идентичности отказывается работать, а репозиторий может её не
иметь — и подставлять пользовательскую в служебный объект незачем.

**Уборка — от живого множества, а не от событий.** При удалении треда пересчитываются все
`workspaceSnapshotTree`, оставшиеся в живых тредах, и лишние ссылки снимаются. Событийная схема
(«тред удалён → сними его ссылки») выглядит проще и течёт молча: один пропущенный путь удаления —
и объекты живут вечно. Пересчёт самокорректируется и подбирает мусор, оставленный прошлыми версиями.
Снятие ссылки только откалывает объекты; собирает их сам git, поэтому снимок, на который ещё
ссылается чекпоинт, исчезнуть не может. Проверено живьём: 3 → 1, выживший пережил `gc --prune=now`.

## Почему восстановление за подтверждением

Обычный откат возвращает содержимое, которое написал сам агент, — пользователь его и просил, нажав
«вернуться». Восстановление снимка перезаписывает файлы, которых чат не касался, и **удаляет
созданные после чекпоинта** (их нет в дереве, поэтому `checkout-index` их не уберёт — удаляет наш
код). Отменить это нечем. Поэтому: сперва `planWorkspaceSnapshotRestore` (ничего не трогает), затем
диалог с числом удаляемых файлов, и только по «да» — запись. Если удалять нечего, вопрос не задаётся.

## Разделение слоёв

- `common/workspaceSnapshotPolicy.ts` — чистое: argv команд, валидация id дерева, план восстановления
  (что перезаписать, что удалить), сборка и разбор сообщения коммита. Тестируется без git.
- `common/checkpointCoverage.ts` — чистое решение «что сказать после отката» и отображение вызовов инструментов
  отрезка в имена для этого решения (`toolNamesForCoverage`).
- `electron-main/vibeideSCMMainService.ts` — запуск git. Через `execFile` с argv, а не строкой в
  оболочку: в путях бывают пробелы. Отдельный раннер `gitArgv`, потому что соседний `git()` считает
  любой `stderr` ошибкой, а git пишет туда советы и на успешных командах.
- `electron-browser/vibeWorkspaceSnapshotService.ts` — резолв открытой папки, `capture()` никогда не
  бросает: снимок — страховка, его отсутствие не должно ломать чекпоинт.

## Грабли

- **Регексп id дерева обязателен.** `tree` уезжает в argv git; `HEAD; rm -rf /` не должно доехать.
  Принимаются только 40/64 hex.
- **Удаление — вторая половина восстановления.** Без него возврат выглядит применённым наполовину:
  файлы вернулись, а мусор, созданный после чекпоинта, остался.

## Общий контракт с VibeIDEA (2026-10-16)

Формат снимка больше не наш: его описывает `checkpointSpec.md` набора `.vibe-defaults` (VibeBrains), проверка — `testVectors/checkpoint.json`.
В одном репозитории работают оба продукта, и снимок одного обязан читаться другим, поэтому сообщение коммита, ссылка, уборка, план отката и решение
о предупреждении — по контракту, а не по привычке одного из продуктов.

- **Сообщение коммита:** тема `VibeIDE checkpoint: ход N (<инструмент|agent>)`, пустая строка, тело — строки `ключ: значение`
  (`tree`, `turnIndex`, `toolName`, `threadId`, `agent`, `label`). Поле без значения не пишется, значение сводится к одной строке — иначе `label`
  с переводом строки и `tree: 000…` подделал бы чужой ключ. Прежняя запись `ключ значение` (без двоеточия) читается для известных ключей, незнакомые
  ключи читатель молча пропускает: контракт может вырасти.
- **`turnIndex` — номер хода, а не номер сообщения.** До контракта подставлялась длина списка сообщений треда; теперь считаются сообщения человека.
  Старые снимки в репозиториях сохраняют прежний смысл числа; они узнаются по прежней записи без двоеточия, а число нужно для чтения истории, не для логики.
- **`agent`:** `builtin` для встроенного агента, id записи реестра ACP (`thread.acpAgent.agentId`) для внешнего. `label` код пока не задаёт: текст запроса
  человека в сообщение коммита не кладётся (он остался бы в `.git` и мог бы содержать секрет).
- **Одна правда о константах.** Порог возраста при уборке (`SNAPSHOT_PRUNE_MIN_AGE_MS`) и имена командных инструментов (`SHELL_TOOL_NAMES`) остаются
  константами кода, а не читаются из вектора в рантайме; `test/node/checkpointVectors.test.ts` сверяет их с вектором и падает, если разошлись.
  Тест читает файл из набора через `fs`, поэтому живёт в `test/node/`, а не в `test/common/`: в `common` нет `fs`, как у всех соседних тестов векторов.
- **Незнакомое поле вектора роняет тест** — выросший контракт надо прочитать, а не пропустить.
- **Указатель набора.** Контракт приехал коммитом в локальной ветке `next` VibeBrains, отведённой от `eed80e7`, то есть без шести коммитов, уже лежащих в `main`
  набора (правило «бригадир», эвалы навыков, каталог моделей распознавания речи, векторы файла MCP). Переключение указателя на тот коммит как есть стёрло бы их
  из сгенерированного манифеста. Правильный порядок — перенести коммит с контрактом на `origin/main` набора, `node bump.mjs`, пуш, затем бамп указателя.

## Пути — только с `-z`

`ls-tree` и `ls-files` без `-z` печатают имена с не-ASCII знаками в кавычках с восьмеричными кодами (`"\320\275…"`, проверено на `git ls-files --others`).
Такой путь не находится на диске, и `rm` из отката молча не срабатывает: созданный агентом файл с русским именем оставался после «полного» отката.
Теперь оба списка читаются по NUL (`parseNulList`), а вывод git для них не режется `trim()` (`gitArgvRaw`): имя может начинаться с пробела.
Это относится ко всему разбору вывода git, от которого зависит откат, — строковый `parsePathList` оставлен только для имён веток и ссылок.

## «Откат что-то изменит» — по сравнению с папкой, а не по числу удалений

Первая версия решала `wouldChangeAnything = plan.delete.length > 0`. Удаляются только файлы, созданные после снимка, поэтому правка существующего файла
(`sed -i`, форматтер, генератор поверх файла) давала «менять нечего», и откат папки не предлагался вовсе — при том что он перезаписал бы файл.
Теперь план несёт `changed` — пути, где папка отличается от снимка: временный индекс (копия настоящего) → `git add -A` → `git diff --cached --name-only -z --no-renames <снимок>`.
Правка, созданный файл и удалённый файл попадают сюда одинаково; игнорируемое git не попадает (`add -A` его уважает), индекс пользователя не трогается.
Диалог показывает оба числа: сколько файлов отличается и сколько из них будет удалено.

## Внешний агент (ACP) в основном чате

Тред ведёт внешний агент, и **его правки идут мимо файлового слежения чата** (`voidFileSnapshotOfURI`): Claude Code правит своими `Edit`/`Write`
напрямую (см. `agentCollaboration/acpHost.md`). Поэтому у ACP-треда откат по чекпоинту — это целиком снимок папки.

- **Когда снимается.** Перед каждым ходом агента, в ветке ACP `_addUserMessageAndStreamResponse`, до `AcpChatRunner.send` — пока агент ещё ничего не тронул.
  Если последним в треде уже стоит чекпоинт (тред только что обрезан до чекпоинта при отправке после отката), второй не добавляется — как в `_makeUsStandOnCheckpoint`.
  У встроенного агента чекпоинт ставится в конце хода; у ACP конца хода нет в явном виде, но граница «перед сообщением N» та же.
- **Что делает кнопка.** `jumpToCheckpointBeforeMessageIdx` для ACP-треда: файловых снимков чата нет (`lastIdxOfURI` пуст), так что откатывать из них нечего;
  дальше `_offerWorkspaceSnapshotRestore` предлагает вернуть папку по снимку этого чекпоинта. Чекпоинт «встань здесь», который jump ставит сам при `currCheckpointIdx === null`,
  тоже снимает папку — по нему можно вернуться вперёд.
- **Команды ACP-агента для предупреждения.** У встроенного агента инструмент называется (`run_command`), у внешнего имя произвольно (`Bash`, `shell`), а стабилен
  `kind` вызова из протокола ACP. Решение: вызов `acp_tool` с `kind: execute` засчитывается как `run_command` (`toolNamesForCoverage`); остальные виды в счёт командных не идут.
  Предупреждение «команды остались» появляется, только если снимка нет (папка не под git).
- **Что остаётся открытым.** Вне git вызовы `edit`/`delete`/`move` внешнего агента откат молча не вернёт, а предупреждение про них не говорит (заведено в roadmap).
  И сессия агента помнит ход, которого после отката в ленте уже нет: перемотать историю агента отсюда нельзя.
- **Проверено чтением кода и на репозитории; кнопка прогнана живьём 21.10.2026.** Цепочка jump → план → диалог для ACP-треда прослежена по коду; чистые части (`toolNamesForCoverage`,
  решение, сообщение) и git-часть (настоящий временный репозиторий) прогнаны тестами. На стенде с заглушкой ACP-агента (папка под git) кнопка «Checkpoint» у сообщения даёт диалог с числом
  изменившихся файлов, «Вернуть папку» возвращает файлы и показывает уведомление «Рабочая папка возвращена к чекпоинту: восстановлено файлов — N, удалено — M»
- **Возврат папки и разбор правок.** Правки внешнего агента стоят на общем разборе «принять / отклонить» (зоны `editCodeService`, см. [[acpHost]]). Возврат папки меняет файлы на диске,
  а зона помнит текст «до» от прежнего состояния: без сверки панель показывала правку, которой уже нет, а «Отклонить» записало бы в файл текст из прошлого (нашёл живой прогон).
  Поэтому `VibeWorkspaceSnapshotService.restore` после возврата снимает зоны на возвращённых и удалённых файлах без изменения текста и без записи в историю и перечитывает их модели с диска;
  файл с несохранёнными правками человека не перечитывается. Тест — `test/browser/vibeWorkspaceSnapshotRestore.test.ts`
