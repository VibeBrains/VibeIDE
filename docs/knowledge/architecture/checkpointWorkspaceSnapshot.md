# Снимок рабочей папки в чекпоинтах

**Домен:** architecture · **Заведено:** 2026-08-10 · **Ветка:** `next`

## Дыра, которую закрывает

Чекпоинт чата хранил `voidFileSnapshotOfURI` — содержимое только тех файлов, которые прошли через
`editCodeService`. Всё, что изменило дерево иначе, для отката не существовало: сборка, `git checkout`,
`sed` в терминале, скрипт, запущенный самим агентом. Откат восстанавливал известные файлы и молча
оставлял остальные — это хуже, чем не откатывать вовсе, потому что результат выглядит как чистый
возврат. Дыра подтверждена кодом: `chatThreadService.ts` собирает снимок из моделей, известных
`vibeideModelService`.

## Механизм

Снимок — объект-дерево git, записанный через **временный индекс** (`GIT_INDEX_FILE`), поэтому
настоящий индекс пользователя (его `staged`-правки) не трогается вовсе. Проверено фактом: после
снимка и восстановления `git status` показывает ровно то же, что показывал до.

`git stash create` не подошёл и рассматриваться не должен: он **не берёт untracked-файлы**, а
untracked-вывод — это ровно то, что производит работа в терминале.

Ключевая деталь производительности, без которой механизм неприменим: временный индекс **засевается
копией настоящего** (`.git/index`). На пустом индексе `git add -A` перехэширует всё дерево — на
репозитории такого размера это секунды на каждый чекпоинт; на засеянном срабатывает stat-кэш git и
хэшируется только изменившееся.

Снимок берётся **на пользовательском чекпоинте**, а не на каждой правке инструмента: это и есть
граница, к которой откатываются («до хода агента»), и один `git add -A` на ход допустим, а один на
файл — нет.

## Снимок обязан быть достижимым

Голое дерево от `write-tree` ни на что не ссылается, и `git gc` вправе его удалить. Это не теория:
`git gc --prune=now` сделал только что записанное дерево нечитаемым — то есть чекпоинт хранил бы
хэш объекта, которого больше нет, и восстановление ломалось бы молча, тем позже, чем старше
чекпоинт.

Поэтому дерево заворачивается в **коммит без родителя**, а коммит получает ссылку в приватном
namespace `refs/vibe/checkpoints/<id>`. Проверено: снимок пережил `gc --prune=now`, содержимое
читается, `git branch -a` не изменился, ссылка видна только через `for-each-ref refs/vibe/`.
`read-tree`, `ls-tree` и `checkout-index` принимают commit-ish, поэтому остальной механизм не
менялся — в чекпоинте просто лежит id коммита вместо id дерева.

Личность коммита своя (`VibeIDE <snapshot@vibeide.local>`) и передаётся через `GIT_AUTHOR_*` /
`GIT_COMMITTER_*`: `commit-tree` без идентичности отказывается работать, а репозиторий может её не
иметь — и подставлять пользовательскую в служебный объект незачем.

**Уборка — от живого множества, а не от событий.** При удалении треда пересчитываются все
`workspaceSnapshotTree`, оставшиеся в живых тредах, и лишние ссылки снимаются. Событийная схема
(«тред удалён → сними его ссылки») выглядит проще и течёт молча: один пропущенный путь удаления —
и объекты живут вечно. Пересчёт самокорректируется и подбирает мусор, оставленный прошлыми версиями.
Снятие ссылки только откалывает объекты; собирает их сам git, поэтому снимок, на который ещё
ссылается чекпоинт, исчезнуть не может. Проверено живьём: 3 → 1, выживший пережил `gc --prune=now`.

## Почему восстановление за подтверждением

Обычный откат возвращает содержимое, которое написал сам агент, — пользователь его и просил, нажав
«вернуться». Восстановление снимка перезаписывает файлы, которых чат не касался, и **удаляет
созданные после чекпоинта** (их нет в дереве, поэтому `checkout-index` их не уберёт — удаляет наш
код). Отменить это нечем. Поэтому: сперва `planWorkspaceSnapshotRestore` (ничего не трогает), затем
диалог с числом удаляемых файлов, и только по «да» — запись. Если удалять нечего, вопрос не задаётся.

## Разделение слоёв

- `common/workspaceSnapshotPolicy.ts` — чистое: argv команд, валидация id дерева, план восстановления
  (что перезаписать, что удалить). Тестируется без git.
- `electron-main/vibeideSCMMainService.ts` — запуск git. Через `execFile` с argv, а не строкой в
  оболочку: в путях бывают пробелы. Отдельный раннер `gitArgv`, потому что соседний `git()` считает
  любой `stderr` ошибкой, а git пишет туда советы и на успешных командах.
- `electron-browser/vibeWorkspaceSnapshotService.ts` — резолв открытой папки, `capture()` никогда не
  бросает: снимок — страховка, его отсутствие не должно ломать чекпоинт.

## Грабли

- **Регексп id дерева обязателен.** `tree` уезжает в argv git; `HEAD; rm -rf /` не должно доехать.
  Принимаются только 40/64 hex.
- **Удаление — вторая половина восстановления.** Без него возврат выглядит применённым наполовину:
  файлы вернулись, а мусор, созданный после чекпоинта, остался.
