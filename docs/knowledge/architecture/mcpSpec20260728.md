## [архитектура] Что меняет ревизия спеки и что из этого касается нас

**Контекст:** 2026-07-22, разбор дайджеста. Спека MCP ревизии **2026-07-28** (release candidate заморожен 21 мая, финал 28 июля) переводит протокол в stateless. Разбирали, что забирать в VibeIDE.

**Суть изменений** ([release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [разбор AAIF](https://aaif.io/blog/mcp-is-growing-up/)):

| Изменение | Что именно |
|---|---|
| Stateless-транспорт | Заголовок `Mcp-Session-Id` и протокольная сессия **удалены**; версия протокола, инфо о клиенте и capabilities едут в `_meta` каждого запроса |
| Новые заголовки | `Mcp-Method` и `Mcp-Name` обязательны для Streamable HTTP — инфраструктура маршрутизирует, не разбирая тело |
| OAuth | Клиент обязан валидировать `iss` по **RFC 9207** и объявлять `application_type` при регистрации; desktop/CLI регистрируются с localhost redirect URI |
| Deprecated | **Roots, Sampling, Logging** — работают ≥12 месяцев, удаление только через отдельный SEP |

**Что сделали у нас:**

- **Валидация `iss` — внедрена.** До этого её не было вовсе (grep по `mcpOAuthPkceContract.ts` и `vibeMCPOAuthService.ts` был пуст). Теперь `verifyOAuthCallback(params, expectedState, expectedIssuer?)` возвращает `issuer-mismatch` / `issuer-missing`, а в `MCPOAuthFlowConfig` появилось поле `issuer`.
- **Sampling помечен «не развивать»** в шапке `vibeMCPSamplingService.ts`. Сервис остаётся (ломаться нечему год), но запланированная «Phase 3b: wire into mcpChannel.ts + streaming» отменена — это вложение в фичу под удаление. Elicitation депрекейшена не касается.

**Ключевые решения и почему именно так:**

- **Проверка `iss` строгая, но только при заданном issuer.** Если issuer сконфигурирован — отсутствующий `iss` тоже отвергается (иначе атакующий просто не прислал бы параметр). Если issuer не задан — проверка пропускается с предупреждением в лог, а **не** выводится из `authorizationEndpoint`: issuer-идентификатор сервера сплошь и рядом не совпадает с origin эндпоинта (`https://example.com` против `https://auth.example.com/authorize`), вывод по origin давал бы ложные отказы у валидных провайдеров.
- **Порядок проверок:** `state` → `iss` → `error` → `code`. CSRF-защита остаётся первой, issuer проверяется раньше разбора ошибки провайдера. Зафиксировано тестами.
- **`application_type` — применимо, отложено.** ⚠️ Формулировка «у нас нет DCR» из первой редакции этой записи **фактически неверна**: динамическая регистрация есть в апстрим-слое — `fetchDynamicRegistration()` в `src/vs/base/common/oauth.ts:857`, `registration_endpoint` там же. Ручной `MCPOAuthFlowConfig.clientId` — это только Vibe-слой PKCE, он не единственный путь. Параметр объявлять есть где, но состав authorization-SEP в RC помечен самими авторами как «provisional» — ждём финальный текст 28.07, кодить по черновику не стали.
- **Своя сессионная поверхность у нас ЕСТЬ — по обе стороны.** ⚠️ Утверждение первой редакции «`Mcp-Session-Id` в коде не встречается» **опровергнуто фактом** (аудит 2026-07-23): заголовок живёт и у клиента (`src/vs/workbench/api/common/extHostMcp.ts:385,429,446,554` — Streamable HTTP с откатом на legacy SSE, реконнект по `Last-Event-ID`), и в **нашем собственном** MCP-сервере — gateway `src/vs/platform/mcp/node/mcpGatewayService.ts:438,502` + `mcpGatewaySession.ts` (свой список поддерживаемых ревизий `2025-11-25 … 2024-10-07`). Клиентский транспорт — апстримный долг ([[upstreamBoundary]]), а вот **gateway наш**, и stateless-переход касается его напрямую: сессии придётся выпиливать самим.
- **Отдельный «пул соединений» заводить не нужно.** Без протокольной сессии запросы становятся чистыми request/response, и переиспользование вырождается в обычный HTTP keep-alive — это часть работы по ревизии, а не самостоятельная задача.

**Чего в первой редакции не было (дополнено 2026-07-23):**

| Тема | Факт | Наш статус |
|---|---|---|
| `server/discover` | Рукопожатие `initialize`/`initialized` удалено (SEP-2575); версия и capabilities едут в `_meta`, дискавери — отдельным RPC. Клиент новой ревизии **обязан** откатываться на `initialize` для серверов ≤ 2025-11-25 | Не реализовано; мы на 2025-11-25 (`modelContextProtocol.ts:43`) |
| Multi round-trip (SEP-2322) | Замена server→client запросам: вызов возвращает `input_required` c `inputRequests` + непрозрачным `requestState`, клиент переиздаёт запрос с `inputResponses`. Elicitation и sampling батчатся в один круг | Не реализовано; ложится поверх готовых `mcpElicitationService` / `mcpSamplingService` |
| MCP Apps (SEP-1865) | Стало официальным расширением: HTML-UI в sandboxed iframe, шаблоны декларируются заранее | **Уже есть** — спека `2026-01-26`, `ui://`, webview-хост `chatMcpAppModel.ts` |
| MCP Tasks (SEP-2663) | Из experimental в расширение; blocking `tasks/result` → polling `tasks/get`, добавлен `tasks/update`; согласование через поле `extensions` в capabilities | **Почти есть** — `mcpTaskManager.ts` + task-augmentation; нет `tasks/update` |

**Вывод по срочности:** миграции на 2026-07-28 «прямо сейчас» не требуется — депрекейты annotation-only с окном ≥12 месяцев (SEP-2596), а RC не финал. Работу делаем по опубликованному 28.07 тексту, одним заходом: `server/discover` + fallback, заголовки, multi round-trip, `tasks/update`, `'2026-07-28'` в список ревизий gateway.

**~~Гэп OAuth: Resource Indicators (RFC 8707) — не реализованы (найдено 2026-07-24)~~ — ОПРОВЕРГНУТО 2026-07-25, гэпа нет.** Запись 24.07 утверждала нарушение «MUST»: `resource=` якобы отсутствует в authorize/token, `application_type` — в DCR. Проверка кода перед реализацией показала обратное **по обоим пунктам**:

- `resource` шлётся в **трёх** местах живого пути — authorize (`extHostAuthentication.ts:110`), device code (`:191`) и token-обмен (`:259`, с комментарием «Add resource indicator if available (RFC 8707)»); значение берётся из Protected Resource Metadata (`_resourceMetadata.resource`, RFC 9728).
- `application_type: 'native'` в теле DCR — `src/vs/base/common/oauth.ts:881`.

**Почему ошиблись:** смотрели в `vibeMCPOAuthService.ts` — в нём `resource` действительно нет. Но **этот сервис не авторизует MCP-серверы**: `initiateOAuthFlow`/`completeOAuthFlow`/`refreshToken`/`storeToken` не вызываются НИОТКУДА, кроме тестов (`grep` по `src/`), из-за чего его реестр токенов всегда пуст. Живой путь — апстримный (`contrib/mcp` → `extHostAuthentication`), и он спеку соблюдает. Наш сервис пришёл целиком из `29769720 «Initial import: VibeIDE»` (2026-05-05, код форкнутого стартера), нашей рукой не писался — на что косвенно указывают и англоязычные строки уведомлений в `vibeMCPTokenRotationContribution.ts:93-94`, нарушающие наше правило «русский в исходнике».

**Что при этом было живо — и что с ним сделали (2026-07-25):** `vibeMCPTokenRotationContribution` нёс **наш замысел**, которого в апстриме нет: политика ротации MCP-токенов (напоминание после 90 дней, предупреждение об истечении, авто-отзыв при удалении сервера / простое / достижении предельного возраста). Питался он пустым реестром мёртвого сервиса, поэтому не срабатывал ни разу. Замысел перенесён на живой носитель: источником стали три апстрим-сервиса — `IDynamicAuthenticationProviderStorageService` (токен с `created_at`/`expires_in`/`refresh_token`), `IAuthenticationService` (сессия: аккаунт + id), `IAuthenticationMcpUsageService` (`lastUsed` по каждому MCP-серверу). Сшивает их чистая `buildMcpTokenRecords`.

Три неочевидных момента этой сшивки — они же грабли на будущее:

1. **Сырой токен и сессия — разные записи.** В store лежит `IAuthorizationTokenResponse & { created_at }` без аккаунта, в `IAuthenticationService` — сессия с аккаунтом, но без времени выпуска. Единственное общее поле — `access_token`; по нему и связываем.
2. **`refresh_token` отменяет `expiresAt`.** Access-токен обновляемой сессии истекает постоянно, и апстрим молча его продлевает. Если подать такой `expiresAt` в политику, она вынесет вердикт «expired» и снесёт исправный вход. Возраст и простой при этом остаются в силе — ротация именно про них.
3. **Отзыв — `removeSession`, а не `removeDynamicProvider`.** Второй сносит и клиентскую регистрацию (DCR), после чего повторный вход требует новой динамической регистрации; первый оставляет клиента и просто разлогинивает.

`vibeMCPOAuthService.ts` (420 строк) удалён.

**Продолжение 2026-07-26: RFC 9207 внедрён в живой путь, `mcpOAuthPkceContract.ts` удалён следом (615 строк с тестами).** Пока проверка `iss` жила только в нашем модуле без потребителя, защиты от mix-up атаки у продукта не было: `state` доказывает, что ответ относится к нашему запросу, но не то, что он пришёл от того сервера, которому мы его отправили. Внедрение — три точки в апстриме: чистая `verifyAuthorizationResponseIssuer` и поле `authorization_response_iss_parameter_supported` в `base/common/oauth.ts`, проброс `iss` в `loopbackServer.ts` (параметр приходил и молча выбрасывался), проверка перед обменом кода в `extHostAuthentication.ts`. Правка апстрима не потребовала отдельного решения: [[upstreamBoundary]] прямо разрешает её ради security.

**Асимметрия, которую стоит помнить:** несовпадение `iss` рвёт флоу всегда, а его отсутствие — только когда сервер объявил `authorization_response_iss_parameter_supported`. Иначе клиент перестал бы работать с любым сервером, не реализовавшим расширение, — то есть «строгая» проверка сломала бы больше, чем защитила. Случай «сравнить не с чем» логируется, а не проглатывается.

**Урок:** «гэп найден по коду» — недостаточное основание, пока не показано, что **этот** код на живом пути. Проверять не только «есть ли параметр в файле», но и «вызывается ли файл» (`grep` по имени метода вне самого модуля + тестов). В форке дублей апстрима больше, чем кажется: экземпляр рядом с апстримным — повод сначала спросить, кто из них работает.

**Пересверка тем 24.07 с первоисточниками:** stateless-состав подтверждён по официальному блогу + Microsoft `mcp-for-beginners` (SEP-2567/2575/2243/2549) — `Mcp-Session-Id` и handshake `initialize` удалены, обязательны `Mcp-Method`/`Mcp-Name`, кэш `ttlMs`/`cacheScope`. Apps (SEP-1865) и Tasks (SEP-2663) подтверждены как расширения; наш Apps на версии `2026-01-26` (старее финала — поднять при 28.07), Tasks объявлены «not backward compatible» с experimental — сверить `mcpTaskManager.ts`. Модельные находки K3 (три уровня effort, mirror подтверждён) — в [[modelQuirks]].

**Применение:** заводя OAuth-подключение к MCP-серверу, заполняйте `issuer` из метаданных сервера (`issuer` в `/.well-known/oauth-authorization-server`), а не из адреса эндпоинта. Без него флоу работает, но защиты от mix-up атаки нет — в логе будет предупреждение.

**Антипаттерны:**

- Выводить issuer из origin authorization-эндпоинта «чтобы работало без конфига» — ломает валидных провайдеров.
- Наращивать функциональность вокруг Sampling / Roots / Logging — они под удаление.

## [инструмент] 2026-07-22 — модельный ландшафт: что забрали в библиотеку провайдеров

**Контекст:** тот же разбор дайджеста. Три модели оценивались на применимость; все три легли в `.vibe-defaults/providers/` конфигом, кода не потребовалось.

**Суть:**

- **DeepSeek V4** ([AA](https://artificialanalysis.ai/models/deepseek-v4-pro)) — V4-Pro 1.6T/49B активных, контекст 1M, MIT, **text-only**. 80.6% SWE-bench Verified (лучшее среди open-weights, по агрегаторам — первоисточник не найден). Цена $0.435/$0.87 за 1M, но модель **очень многословна** (180M выходных токенов на прогоне против медианных 97M) — реальный счёт выше тарифа. Отдельно: **`deepseek-chat` и `deepseek-reasoner` отключены провайдером 2026-07-24**, актуальные id — `deepseek-v4-pro` / `deepseek-v4-flash`.
- **GPT-5.6** ([AA](https://artificialanalysis.ai/articles/gpt-5-6-has-landed), [OpenRouter](https://openrouter.ai/openai/gpt-5.6-terra)) — три тира: `gpt-5.6-sol` $5/$30, `gpt-5.6-terra` $2.50/$15, `gpt-5.6-luna` $1/$6; у всех контекст 1 050 000 и выход 128 000. **Ловушка: голый алиас `gpt-5.6` ведёт на Sol**, а не на дешёвый тир. Coding Agent Index: Sol 80, Terra 55, Luna 51 — Terra/Luna берём на рутину, не на сложные задачи.
- **Kimi K3** ([Simon Willison](https://simonwillison.net/2026/Jul/16/kimi-k3/)) — 2.8T параметров, контекст 1M, Modified MIT, веса обещаны 27.07.2026, id `kimi-k3`, лидер Frontend Code arena. Два подвоха: **reasoning нельзя выключить** (единственный уровень «max») и ~13k токенов рассуждений на простую задачу. Для рутины невыгодна. **Self-host отпадает** — 2.8T на рабочую станцию не кладутся.

**Уточнение по K3 (2026-07-23):** тезис «кода не потребовалось» продержался до первой же проверки — потребовалось два исправления конфига.

- **`effort` уходит на провод дословно.** `vibeDynamicProvidersService.ts:87-89` кладёт список `reasoning.effort` в `effort_slider.values` как есть, а openai-совместимый хук превращает выбранное значение в `reasoning_effort`. Рецепт с `["high"]` слал бы в Moonshot значение, которого у K3 нет: единственный уровень называется дословно **`"max"`**. Исправлено на `["max"]`. Тип `values: string[]` (`modelCapabilities.ts:185`) свободный — произвольные вендорские уровни писать можно.
- **K3 — preserved-thinking-history.** Модель обучена с сохранением истории рассуждений: выбрасывание reasoning предыдущих ходов внутри tool-цикла даёт «generation quality instability» ([apidog](https://apidog.com/blog/kimi-k3-api/)). Это ровно тот класс, что покрывает флаг `mirrorReasoningContent`, — но правило `kimi-k3` в каталоге отсутствовало, и модель подхватывала широкое `kimi` (T=1.0/topP=0.95) **без зеркалирования**. Добавлено правило `kimi-k3`. Матчинг по подстроке: `kimi-k3` не содержит `kimi-k2`, так что merge идёт с широким `kimi`, а не с k2-семейством.
- **Статус доверия:** техрепорта у Moonshot нет, источник вторичный, на живом ключе не прогонялось — помечено прямо в `note` правила. Пересмотреть, когда появятся независимые данные.

**Применение:** для text-only моделей в `providers.json` обязателен `"vision": false`, а в статическом реестре `modelCapabilities.ts` — `supportsVision: false`. Без этого vision-гейт отправит запрос с картинкой в модель, которая её не примет. Добавляя «думающую» модель — сверяйте имя уровня усилия с документацией вендора: значение не нормализуется, а вымышленный уровень уедет в API как есть.

**Антипаттерны:** прописывать в конфиг алиас модели вместо полного id тира — легко получить флагманский тариф там, где хотели дешёвый маршрут.

**Связано:** [[dynamicProviders]], [[modelPricing]], [[vibeDefaults]]
