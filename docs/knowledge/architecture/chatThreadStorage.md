# Хранение тредов чата: файл на тред

## Что было

Все треды всех проектов лежали одним значением `vibeide.chatThreadStorageII` в `IStorageService` (`APPLICATION`)
Каждое изменение (через 1,5 с дебаунса) делало `JSON.stringify` всей истории и слало строку в основной процесс
У пользователя 180 тредов, 134 МБ: русский текст делает строку двухбайтовой, около 270 МБ на копию
`JSON.stringify` падал фатальным `V8 process OOM (Zone)`, окно умирало с `crashed, code 5`
Куча JS при этом была около 550 МБ из 3,2 ГБ свободных: память кончилась не в куче, а внутри сериализации
После повторного открытия первая же запись повторяла то же самое — петля

## Как теперь

`browser/chatThreadStore.ts`: тред — файл `<globalStorage>/vibeide/chatThreads/<encodeURIComponent(id)>.json`
Запись только тредов, чья ссылка отличается от прошлой записи: состояние обновляется неизменяемо, поэтому сравнение ссылок дёшево и точно
Файл пишется во временный `.tmp` и переименовывается поверх
Удаляется только тред, который это окно видело на диске и который исчез из его состояния: тред, созданный другим окном, не трогается
Сериализация и разбор — `common/chatThreadSerialization.ts` (картинки `__base64__:`, URI по `$mid`, старые отказы `withRefusalKind`)

Загрузка асинхронная: состояние стартует пустым, загруженное сливается с тем, что человек успел написать (его треды побеждают)
До конца загрузки запись копится в буфере: пустой старт иначе удалил бы файлы

Перенос: старый ключ раскладывается по файлам и удаляется только после того, как каталог подтвердил все id
Не подтвердил — ключ остаётся, в состояние идёт объединение

## Защита от петли

`common/chatRestoreCrashGuard.ts` — чистое решение, `browser/chatRestoreCrashGuard.ts` — хранилище
Отметка «окно открыто» пишется сразу с `flush()` и снимается через минуту жизни или при обычном закрытии
Две отметки подряд, оставшиеся от окон, не проживших минуту, — вкладки чата не восстанавливаются, треды на диске целы

**Грабли:**
Отметка в `WORKSPACE`, а не в `APPLICATION`: при запуске IDE восстанавливает несколько окон разом, и общая отметка засчитала бы соседние окна как падения
Обычное закрытие окна в первую минуту снимает отметку на `onWillSaveState` с причиной `SHUTDOWN`: иначе быстрое закрытие считалось бы падением

## Как диагностировать такое падение

`renderer.log` пуст: процесс умирает нативно
Причину дали minidump'ы из `~/Library/Application Support/VibeIDE/Crashpad/pending/`: `strings` по файлу показывает `v8-oom-location` = `Zone` и `v8-oom-stack` = `stringify`, а рядом в памяти — начало сообщения хранилища
Размер значения в базе — `sqlite3 state.vscdb "select key, length(value) from ItemTable order by 2 desc limit 5"`
