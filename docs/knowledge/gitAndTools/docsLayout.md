## [конвенция] Всё в `docs/` — camelCase; мануалы — только в `docs/manuals/`

**Контекст:** доки расползлись — руководства лежали и в корне репо (`HOW_TO_CONTRIBUTE.md`, `VIBEIDE_CODEBASE_GUIDE.md`), и в `docs/` вперемешку с каталогом/планом/индексом, в трёх стилях именования (`SCREAMING_SNAKE`, `kebab-case`). Правило введено 2026-07-14 **для мануалов**, при этом `docs/knowledge/**` осознанно оставили kebab — «переименование отдельной волной». Волна проведена **2026-07-15**: раздвоение снято, конвенция одна.

**Суть:**
- **Имена файлов и папок в `docs/` — camelCase.** Включая домены базы знаний: `gitAndTools/`, `chatUx/`, `toolSystem/`, `vibeDotfolder/`, `runtimeQuirks/`, `agentCollaboration/`. Шаблоны — `_templateKnowledgeEntry.md` (ведущее `_` значимо: по нему гейт отличает скелет от записи).
- **Легальные исключения:** `README.md` и общепринятые верхнеуровневые имена (`CONTRIBUTING.md`, `roadmap.md`, `functional.md`, `idea.md`) — их узнают по имени люди и GitHub.
- **Мануал** = руководство «как сделать» по шагам → `docs/manuals/<camelCase>.md`.
- **Не мануалы** → живут вне `manuals/`: каталог возможностей (`functional.md`), план (`roadmap.md`), индекс базы знаний (`knowledge/README.md`), концепт (`idea.md`), FAQ, регламенты, **спеки формата**. Граница именно по жанру: `functional.md` отвечает «что умеет», мануал — «что делать».

**Применение:** новый мануал → сразу в `docs/manuals/`, **живой ссылкой** в [docs/README.md](../../README.md). Переносить/переименовывать существующее — **только `git mv`** (иначе git потеряет историю и покажет delete+add).

## [правило] `docs/README.md` — корень навигации; ASCII-дерево ссылок не создаёт

**Контекст:** 2026-07-15, владелец открыл `docs/` в Obsidian и показал граф: плотное ядро и облако одиноких точек по краю. Замер подтвердил — **29 документов** не имели ни одной связи. При этом в `docs/knowledge/` сирот было **ноль**: гейт членства в индексе держал. Все сироты лежали снаружи базы.

**Суть:** корень был в том, что секция «Структура» в `docs/README.md` была **ASCII-деревом внутри код-блока**. Внутри фенса `├── manuals/ciCdGuide.md` — текст, а не ссылка: ни Obsidian, ни GitHub, ни чекер рёбер там не видят. Правило «новый мануал — строкой в дерево» соблюдалось буквально и нарушалось по смыслу.

Непроверяемое дерево успело и соврать: числился `release-notes-v0.3.0.md`, которого нет, а реально лежавший `release-notes-v0.13.15.md` в дереве не значился. Заодно: `references-v1/README.md` утверждал «вся папка в `.gitignore`» — при 57 файлах под контролем git (утверждение осталось от предшественника, local-only дерева `references/v1/`).

Индексы поддеревьев (`v1/README.md`, `references-v1/README.md`) оказались **неполными** — та же болезнь, что была в базе знаний, только этажом ниже.

**Применение:**
- **`docs/README.md` — корень навигации.** Любой документ обязан быть достижим оттуда по ссылкам: напрямую или через индекс своего поддерева. Не достижим → его не найдут.
- Структуру описывать **списком ссылок**, а не ASCII-деревом. Красивое дерево в фенсе — картинка: не кликается и не проверяется, поэтому врёт незаметно.
- Проверка: `npm run docs-graph-check` = dead links + `unindexed` (записи базы мимо `knowledge/README.md`) + **`unreachable`** (недостижимо от `docs/README.md`). Достижимость **строго сильнее** прежней проверки «сирот» (`нет входящих И нет исходящих`): та пропускала любой файл, у которого есть хоть одна исходящая ссылка.
- Исключения гейта: `_template*` (скелеты, не линкуются намеренно) и `docs/specs/**` (рабочие спеки панели, не документация).
- Release notes в репо **не хранятся** — источник правды GitHub Releases. Одиночный файл-черновик = дубль, который протухает.

**Антипаттерны:**
- Дерево/оглавление в код-блоке как «навигация» — не создаёт ссылок.
- Второй список того же множества (см. волну «один индекс»): расходится по построению.
- Обещать в индексе файл, которого нет (`extension-api-readonly-draft.md` числился в `references-v1/README.md`, при этом отсутствовал и там, и в local-only `references/v1/`; roadmap:1322 при этом рапортует «Draft landed»).

**Как переименовывать массово (проверено на 93 файлах + 6 папках):**
1. `git mv` **сначала файлы, потом папки** — пути остаются валидными на каждом шаге.
2. Ссылки переписывать **по якорям**, а не слепой заменой: `<stem>.md` (расширение = якорь), `<dir>/` с границей `(?<![\w-])`, `[[wikilink]]`. Слепой `sed` по имени домена испортит прозу (`chat-ux` встречается в тексте).
3. Проверять **весь репо**, не только базу: ссылки живут в `CLAUDE.md`, `AGENTS.md`, `.vibe-defaults/rules/*.mdc`, `bin/*.bat`, `build/lib/*.ts`, комментариях `src/**` и `.gitignore` — в волне 2026-07-15 их было 95 файлов.
4. `npm run docs-graph-check` ловит битые ссылки **внутри** базы, но не снаружи — внешние проверять отдельным грепом по старым именам.
5. `.vibe-defaults/**` тронут → `npm run gen:all` (манифест), иначе CI-guard свежести упадёт.
6. **Заложить, что часть ссылок останется битой.** Правка даже комментария втягивает файл в hygiene со всем его пред-существующим долгом ([[precommitHygiene]]). В волне 2026-07-15 так вышло с `src/main.ts`: две ссылки в комментариях (`:101`, `:107`) не обновлены, потому что файл тянет нарушение `local/code-import-patterns` (импорты vibeide в electron-main — by design, с 2026-05-23). Решение: не тащить такой файл в волну и **записать долг явно**, а не глушить правило ради косметики.

**Антипаттерны:**
- Ручное `mv` вместо `git mv` — история файла теряется.
- Переименовать файлы, забыв домены-папки: конвенция «наполовину» — то же раздвоение, только границей ниже.
- Считать, что зелёный `docs-graph-check` = все ссылки целы: он не видит `src/`, `bin/`, `.vibe-defaults/`.

## [ловушка] `docs/CONTRIBUTING.md` переносить нельзя

**Контекст:** при переносе мануалов возник соблазн утащить в `manuals/` и `docs/CONTRIBUTING.md`.

**Суть:** GitHub ищет `CONTRIBUTING.md` ровно в **трёх** местах — корень репо, `docs/`, `.github/`. Список зашит, конфига для переопределения **нет**. Найдёт — покажет плашку «Please review the contributing guidelines» при создании issue/PR и зачтёт пункт в Community Standards. Из `docs/manuals/` не увидит. Ломается только это (плашка + чеклист), на сборку и продукт не влияет. Те же три пути — у `SECURITY.md` и `CODE_OF_CONDUCT.md`.

**Применение:** `docs/CONTRIBUTING.md` — исключение из правила, остаётся на месте. Если очень надо унести — оставить копию/указатель в одном из трёх легальных мест, и **навсегда**, а не «на пару релизов»: удалим — плашка пропадёт.

**Доп. (разведено 2026-07-14):** `HOW_TO_CONTRIBUTE.md` и `docs/CONTRIBUTING.md` — **не дубли**, хоть заголовок у обоих «Contributing to VibeIDE». Первый — про сборку и запуск (prerequisites, Developer Mode) → мануал, уехал в `manuals/howToContribute.md`. Второй — про процесс (TL;DR, structure, workflow, PR review) → регламент, остался. **Не разобрано:** корневой `./CONTRIBUTING.md` — это вообще апстримный «Contributing to **VS Code**», и README ссылается именно на него, говоря «гайдлайны и процесс PR». Три contributing-дока в репо — отдельная задача.

## [ловушка] Перенос дока ломает ссылки в засеянных `.vibe` — навсегда

**Контекст:** `docs/providers-spec.md` → `docs/manuals/providersSpec.md`. На него вёл **абсолютный** URL (`https://github.com/…/blob/main/docs/providers-spec.md`) из `.vibe-defaults/providers/README.md` — файла, который засевается в проект пользователя как `.vibe/providers/README.md`.

**Суть:** правка `.vibe-defaults/**` + `npm run gen:vibe-defaults` чинит только **будущие** засевы. Уже созданные копии не обновятся: `applyVibeDefaults` (`common/vibeDefaults.ts`) пропускает существующие файлы (`exists → skipped++`), а единственный путь перезаписи — опция `overwrite: true`, у которой **нет ни одного вызывающего** (мёртвый параметр; оба вызова — `vibeConfigInitService.ts` и команда «установить обвязку» в `vibeDefaultsContribution.ts` — идут без него). Значит у существующего пользователя битая ссылка останется навсегда.

**Применение:** прежде чем двигать/переименовывать док, грепнуть его имя по `.vibe-defaults/**` и по `*.generated.ts`. Если на него ведёт абсолютный URL из засеваемого файла — либо не двигать, либо осознанно принять битые ссылки у старых пользователей, либо дать им команду обновления окружения (см. Волна 3: `diffVibeDefaults` + «Обновить окружение из релиза», где `overwrite` наконец оживает). Правку `.vibe-defaults/**` **всегда** сопровождать `npm run gen:vibe-defaults`, иначе манифест разойдётся с источником.

## [паттерн] Текст в UI, собираемый из мануала (один источник правды)

**Контекст:** справка «?» в панели «Спеки» должна быть 1-в-1 с документацией. Копия в TS-строке разошлась бы с доком на первой же правке.

**Суть:** мануал — источник, TS — производная. `docs/manuals/specsWorkflow.md` → `scripts/gen-specs-help.mjs` → `common/vibeSpecsHelp.generated.ts` (экспорт markdown-строки) → `showModal({ body, bodyMarkdown: true })`. Устройство скопировано с `gen-vibe-defaults.mjs`; отличия, которые стоило добавить:
- **Маркеры `<!-- specs-help:start/end -->`** вместо «весь файл»: мануал остаётся нормальным доком (заголовок, ссылка на индекс, заметка «правим здесь»), а в модалку едет только тело. Границу видно прямо в файле — не магическое правило «выкинуть первый H1».
- **Падать громко:** нет маркеров / перевёрнуты / регион пуст → `exit 1`. Молчаливый фолбэк на пустую справку хуже красной сборки.
- **`.gitattributes` обязателен:** `docs/manuals/specsWorkflow.md text eol=lf`. Источник встраивается побайтно; без пина Windows выдаст CRLF и генерат будет чурниться от машины к машине (та же грабля, что у `.vibe-defaults/**`).

**Встраивание в сборку:** `gen:all` — агрегат всех генераторов, и **только он** зовётся из 5 скриптов сборки; новый генератор добавляется в `gen:all`, а не в пять мест. `precompile: npm run gen:all` в `package.json` — npm сам зовёт его перед любым `npm run compile`, чем закрыта дыра: `run-dev.sh --compile` раньше codegen не запускал и жил лишь на том, что генерат закоммичен.

**Контракт свежести:** генерат **коммитится** (дев-сборка и навигация по коду не должны требовать предварительного codegen) — и ровно поэтому может протухнуть. Сторож — `.github/workflows/generated-artifacts.yml` (`gen:all` + `git diff --exit-code`). До него протухший генерат всплывал только на релизе (инцидент 2026-05-12, `vibeSettingsRu.ts`).

**Применение:** нужен в UI длинный текст, который обязан совпадать с доком, — не копируйте его в TS. Заведите маркеры в мануале, генератор рядом с существующими, добавьте в `gen:all`, пните eol в `.gitattributes`. Модалка умеет markdown (`bodyMarkdown: true` → ChatMarkdownRender: списки, таблицы, код, ссылки), тело скроллится, `size: 'large'` = 800px.

## [грабли] Массовая миграция путей: два молчаливых провала sed

**Контекст:** 2026-07-19 растворение `references/` → указатели `references/v1/*` переводились на `docs/references-v1/*` по 62 файлам. Два бага, оба тихие (правка «прошла», а эффекта нет).

**Суть:**
- **zsh не делает word-splitting** неэкранированного `$VAR`. `FILES=$(git grep -l …); for f in $FILES; do sed … "$f"; done` в zsh отдаёт sed **весь список одним аргументом** → `File name too long`, ноль правок. В bash сработало бы. Верно в zsh: `… | while IFS= read -r f; do sed … "$f"; done` (построчно) или `for f in ${(f)FILES}`.
- **Строковый sed не видит путей, собранных из сегментов.** `references/v1/foo.md` в тексте — поймает; а `path.join(ROOT, 'references', 'v1', 'foo')` в коде и `URI.joinPath(root, 'references', 'v1', …)` — **нет** (нет подстроки `references/v1/`). Такие константы (`golden-eval.js`, `docs-dedup.js`, contribution `joinPath`) правятся отдельным грепом `'references',\s*'v1'`.

**Применение:** при массовой замене путей — (1) в zsh гнать список через `while read`, не `for in $VAR`; (2) после строкового sed добить грепом сегментные формы `'<dir>',\s*'<sub>'`; (3) **всегда** пост-аудит грепом остатка + typecheck (реальные read-пути молча ломают рантайм, не компиляцию); (4) исключать из sed лог (`roadmap.md`) и исторический нарратив — там старый путь корректен как запись прошлого.
