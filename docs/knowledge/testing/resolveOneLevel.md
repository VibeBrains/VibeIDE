## [грабли] Вложенные `AGENTS.md` не находились ни на каком уровне

**Контекст:** возможность «правила подпроектов из вложенных `AGENTS.md`» пришла 20.09 и вышла в 1.22.0.
Живой смоук 23.09: агент добавил функцию в `src/`, а правило из `src/AGENTS.md` не соблюдено.

**Проверено фактом:**
- Сервис правил сообщил «Loaded 18 rule sources», а в песочнице их 19: `.vibe/rules.md`, 17 файлов
  `.vibe/rules/` и `src/AGENTS.md`. Не хватало ровно правила пакета
- Обход искал файл среди «внуков» — `child.children` у папки, которую только что раскрыли
- `IFileService.resolve` без `resolveTo` раскрывает **только запрошенную папку**: у дочерних папок
  `children` пуст (`fileService.ts`, рекурсия только по дереву `resolveTo`)
- При спуске в `src/` файлы самой папки пропускались строкой `if (!child.isDirectory) continue`
- Итог: на настоящей файловой системе обход возвращал пустой список на любой глубине

**Почему тесты молчали:** тест был только на чистые функции — список пропускаемых папок и константы.
Обход файловой системы не тестировался вовсе. Заглушка `resolve`, отдающая заранее раскрытое дерево,
тоже спрятала бы дефект: она отвечала бы так, как автор думал, что отвечает `resolve`.

**Применение:**
- Обход дерева — один вызов `resolve` на папку; файл ищется среди детей раскрытой папки
- Обход, который ходит по файловой системе, тестируется на `FileService` + `InMemoryFileSystemProvider`,
  а не на заглушке: тест проверяет настоящий `resolve`
- Нужен весь поддерев за раз — `resolveTo` с перечнем путей, а не надежда на заполненный `children`
- Проверка теста: сначала прогнать его на старой логике — он обязан упасть. Тест `nestedRulesScan`
  на старом обходе вернул `[]` там, где ждал два файла
