## [грабли] Вложенные `AGENTS.md` не находились ни на каком уровне

**Контекст:** возможность «правила подпроектов из вложенных `AGENTS.md`» пришла 20.09 и вышла в 1.22.0.
Живой смоук 23.09: агент добавил функцию в `src/`, а правило из `src/AGENTS.md` не соблюдено.

**Проверено фактом:**
- Сервис правил сообщил «Loaded 18 rule sources», а в песочнице их 19: `.vibe/rules.md`, 17 файлов
  `.vibe/rules/` и `src/AGENTS.md`. Не хватало ровно правила пакета
- Обход искал файл среди «внуков» — `child.children` у папки, которую только что раскрыли
- `IFileService.resolve` без `resolveTo` раскрывает **только запрошенную папку**: у дочерних папок
  `children` пуст (`fileService.ts`, рекурсия только по дереву `resolveTo`)
- При спуске в `src/` файлы самой папки пропускались строкой `if (!child.isDirectory) continue`
- Итог: на настоящей файловой системе обход возвращал пустой список на любой глубине

**Почему тесты молчали:** тест был только на чистые функции — список пропускаемых папок и константы.
Обход файловой системы не тестировался вовсе. Заглушка `resolve`, отдающая заранее раскрытое дерево,
тоже спрятала бы дефект: она отвечала бы так, как автор думал, что отвечает `resolve`.

**Применение:**
- Обход дерева — один вызов `resolve` на папку; файл ищется среди детей раскрытой папки
- Обход, который ходит по файловой системе, тестируется на `FileService` + `InMemoryFileSystemProvider`,
  а не на заглушке: тест проверяет настоящий `resolve`
- Нужен весь поддерев за раз — `resolveTo` с перечнем путей, а не надежда на заполненный `children`
- Проверка теста: сначала прогнать его на старой логике — он обязан упасть. Тест `nestedRulesScan`
  на старом обходе вернул `[]` там, где ждал два файла

**Связано:** [missingRuntimeDependency.md](../build/missingRuntimeDependency.md) — та же картина:
звенья покрыты по отдельности, цепочка не работала; [liveSmokeStand.md](liveSmokeStand.md) — как смоук
это нашёл.

## [грабли] Правило пакета, созданное на лету, не подхватывалось

Общий наблюдатель сервиса правил проверял изменения по фиксированным путям (`contains` для корневых файлов,
`affects` для `.vibe/rules/`). У вложенного `AGENTS.md` фиксированного пути нет — он может появиться где угодно
ниже корня, — поэтому созданный или изменённый файл пакета доезжал только после перезапуска.

Рекурсивный наблюдатель с корреляцией (`createWatcher`) пока не поддерживается: «only non-recursive file watching
supports event correlation». Корень же VS Code и так наблюдает рекурсивно, и события приходят в общий обработчик —
их достаточно узнать. Сырые списки изменений помечены устаревшими, но именно так ищет события по шаблону агентский
хост самого VS Code; предикат `isNestedRuleFile` повторяет правила обхода (глубина, пропускаемые папки), поэтому
изменение в `node_modules` перечитывания не вызывает.

**Узнать изменение мало — его надо применить.** Живой стенд показал, что правило пакета не доезжало и после этого.
Планировщик наблюдателя с исходного импорта только слал `onRulesChanged`, на которое никто не подписан, и писал в
журнал «Rules changed, cache invalidated». Кэш оставался прежним для любого файла правил: `rules.md`, корневого
`AGENTS.md`, `.vibe/rules/`. Теперь планировщик перечитывает правила и потом шлёт событие.

Первый тест сервиса этого не ловил: он сам вызывал `reloadRules()` и проверял звено «перечитать → собрать», обходя
звено «событие файла → перечитать». Регрессионный тест пишет файл после загрузки и ждёт событие сервиса — на старом
коде он падает. Строка журнала, называющая действие, которого код не делает, хуже её отсутствия: она и сбила с толку.

**Самоотчёт модели о своём промпте не доказательство.** Модель, спрошенная о метках правил, полезла искать их
поиском по файлам и ответила «цитировать нечего». Доставку доказали тест на настоящем сервисе и полный дамп
запроса на стенде (`vibeide.debug.dumpFullPrompt`), а не её ответ.
