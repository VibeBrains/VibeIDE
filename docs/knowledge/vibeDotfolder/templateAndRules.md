## [vscode] Шаблон `.vibe/` при первом открытии воркспейса

**Контекст:** пользователь тестирует VibeIDE и ожидает русские подсказки в `.vibe/`.

**Суть:** **`vibeConfigInitService`** создаёт каталог при первом открытии workspace: JSON с **`_comment`**, **`rules.md`**, **`ignore`**, **`README.md`**, **`goals.md`**, **`prompts/example.md`** и папки **`snapshots`**, **`prompts`**, **`workflows`**, **`plans`**. Уже существующие файлы не перезаписываются — **`README.md`** в старых проектах нужно добавить вручную или удалить `.vibe` для пересоздания (осторожно с данными). Текст карты для людей — **`getDefaultVibeReadmeMarkdown()`** (**`vibeDefaultWorkspaceReadme.ts`**). Полный разбор блока **GUIDELINES**, встроенного playbook и записи **`goals.md`** — см. секцию ниже.

**Применение:** правки дефолтов локальной конфигурации проекта — **`vibeConfigInitService.ts`**; текст **README.md** — **`vibeDefaultWorkspaceReadme.ts`**.

## [vscode] GUIDELINES и playbook для `.vibe/`

**Контекст:** нужно чтобы любая выбранная модель понимала намерения вида «перенеси правила из Cursor в один файл», «зафиксируй цели в goals», «создай план/workflow».

**Суть:** блок **GUIDELINES** собирается в **`convertToLLMMessageService._getCombinedAIInstructions()`**:
1. глобальные **AI Instructions** из настроек;
2. содержимое из буферов **`.vibe/rules.md`** и **`AGENTS.md`** в корне папки (**`_getVibeRulesFileContents()`**); документы открываются в модель через **`IVibeideModelService.initializeModel`** при старте (**`convertToLLMMessageWorkbenchContrib`** + после создания **`rules.md`** в **`vibeConfigInitService`**);
3. если в воркспейсе есть хотя бы одна папка — константа **`VIBE_DOTVIBE_AGENT_PLAYBOOK`** (**`src/vs/workbench/contrib/vibeide/common/vibeDotVibeAgentPlaybook.ts`**) с маршрутизацией:
   - импорт правил Cursor (**`.cursor/rules`**, **`.cursorrules`**, профиль пользователя **`.cursor/rules`**) → слияние без дублей и без секретов → **`.vibe/rules.md`**;
   - цели из чата → структура и запись в **`.vibe/goals.md`**;
   - планы → **`.vibe/plans/<slug>.plan.md`**;
   - workflow → **`.vibe/workflows/<name>.json`**;
   - при нехватке данных — уточняющие вопросы.

**`goals.md`:** жёсткий **deny_write** в коде **снят** — по умолчанию агент может писать файл; запрет — **`deny_write`** на **`.vibe/goals.md`** в **`constraints.json`**.

Для UI/кэша правил с санитизацией используется **`IVibeProjectRulesService`** (**`vibeProjectRulesService.ts`**), не путать с потоком чата выше. Полуавтоматический импорт из Cursor: **`node scripts/vibe-init-from.js --from cursor`**.

**Применение:** менять «что модель обязана делать с `.vibe` из естественного языка» — **`vibeDotVibeAgentPlaybook.ts`**; политика только-человек для целей — **`constraints.json`**.

## [ловушка+дизайн] Сверка `.vibe` с релизом: auto-seed на каждом открытии и lock примирения (2026-07-14)

**Контекст:** нужно было показать пользователю, что окружение отстало от релиза, и дать обновить.

**Ловушка, которая перевернула дизайн:** `VibeConfigInitContribution` зовёт `_initVibeDirectory()` **из конструктора, без guard'а** — комментарий «on first workspace open» неверен, засев идёт на КАЖДОМ открытии проекта. Внутри `applyVibeDefaults` create-if-missing. Отсюда:
- **«Новое в релизе» не накапливается** — недостающие файлы дописываются сами. Фича «уведомить о новом» была бы мертворождённой.
- Реально копится только **«релиз изменил файл, который у пользователя уже есть»** — create-if-missing его не тронет никогда. Это и есть кейс битой ссылки в засеянном `providers/README.md` после переноса дока.

**Дизайн — lock как точка примирения, а не «что засеяли».** `.vibe/.defaults.lock.json`, на путь `{release, local}` — хеши версии релиза и файла пользователя **на момент последней сверки**. Оба обязательны: зная только засеянное, «релиз поехал» и «юзер правил» неразличимы, а реакции у них противоположные.

| Сдвинулось с последней сверки | Статус | Реакция |
|---|---|---|
| ничего / только юзер | `customized` | **молчать** |
| только релиз, а файл на точке сверки равнялся релизу | `outdated` | безопасно обновить |
| оба; или только релиз, а файл на точке сверки уже был вашим | `conflict` | слияние с основой (дифф, если основы нет), решает человек |
| нет записи | `unknown` | показать один раз |

**Главный инвариант (требование владельца):** настроенный файл отличается от релиза **всегда**, поэтому `customized` исключён из `needsAttention`. Иначе уведомление вечно напоминало бы пользователю о его же правках — и было бы выключено на второй день. Любой путь разрешения («Оставить своё», «Обновить», «Заменить») пишет новую точку примирения → файл замолкает до следующего сдвига релиза.

**Мелочи, которые кусаются:**
- Хешировать **после нормализации к LF**: манифест LF-нормализован генератором, а файл на диске у виндового пользователя CRLF → иначе «отличается» вообще всё.
- `applyVibeDefaults` обязан писать lock на всё, что записал, — иначе свежезасеянный файл на следующем открытии числится `unknown` и просит решения, которого никто не принимал.
- Lock **не** в `.vibe/.gitignore` (в отличие от `.window-lock.json`, `agent-locks.json`, `snapshots/`): это решение проекта, а не машинное состояние. Не закоммитишь — каждый в команде отдельно разбирается с одной и той же общей кастомизацией.
- `JSON.stringify(obj, Object.keys(obj).sort(), '\t')` — **не сортировка**, а replacer-массив разрешённых ключей: вырежет вложенные поля и запишет пустой lock. Сортировать ключи руками при сборке объекта.
- «Мерж» произвольного markdown/JSON автоматом — гадание, съедающее правки. Честный путь — человек в штатном редакторе: read-only схема (`vibe-default:` + `ITextModelContentProvider`) даёт версии релиза URI, дальше дифф-редактор или, когда есть основа, редактор слияния.
- **Основа слияния (21.10.2026, формат — `seedBaseSpec.md` набора).** Трёхстороннему слиянию нужен текст ревизии, от которой засеян файл, а lock хранит только хеши. Текст лежит в `.vibe/local/seedBase/<путь>` (вне git; папка закрывает себя `.gitignore` со звёздочкой, потому что корневой `.vibe/.gitignore` старых проектов о `local/` не знает). Пишется в `recordVibeDefaultsReconciled` (им же пользуется засев, «оставить своё» и закрытое слияние) и в `refreshSeedBases` для файлов, которые равны ревизии набора (`same`, `outdated`). Правленому файлу основу не придумать, поэтому без неё остаётся дифф двух сторон, и окно говорит об этом.
- **Редактор слияния открывается через `editorService.openEditor({ base, input1, input2, result })`** (как внутренняя команда `_open.mergeEditor`), результатом служит сам файл в `.vibe/`. «Ваша» сторона не может быть тем же ресурсом, что результат: правка результата меняла бы и сторону. Для неё — схема `vibe-seed-yours:` с меткой на каждое открытие, иначе повторное слияние в той же сессии получило бы устаревший снимок. Файл без маркеров конфликта редактор слияния не пересобирает: результат остаётся вашим текстом, а входящие правки релиза принимаются по одной. Закрытие без изменений решением не считается.
- **Ловушка классификации (поймана при этой работе):** `outdated` определялся как «релиз сдвинулся, файл с точки сверки не менялся» — но «оставить своё» тоже ставит точку сверки, и файл с вашими правками, которых релиз ещё не видел, после следующего сдвига набора попадал в «обновить безопасно» и терял их. Теперь точка сверки, где файл уже отличался от релиза (`lock.local ≠ lock.release`), при сдвиге набора даёт `conflict`.

**Осталось:** сам auto-seed на каждом открытии молча дописывает файлы в проект пользователя без спроса — давнее поведение, но спорное.

**Грабля доставки (поймана только живым смоуком):** `VibeConfigInitContribution` зарегистрирован на `WorkbenchPhase.BlockRestore` — засев обязан быть ранним (другие сервисы читают `.vibe` сразу). Но `INotificationService.prompt()`, вызванный на этой фазе, **молча теряется**: воркбенч ещё не восстановлен, показывать тост некому. Симптом коварный — код выполняется, ошибок нет, лог до конца доходит, а уведомления нет; при этом та же логика через команду отчёта работает. Фикс: `await lifecycleService.when(LifecyclePhase.Restored)` перед `prompt()` — засев остаётся ранним, а разговор с пользователем ждёт UI. Проверять уведомления на старте **только вживую**: юнит-тест и typecheck такое не ловят.
