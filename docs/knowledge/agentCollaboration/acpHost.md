# ACP: где на самом деле стоят ворота

**Дата:** 2026-08-14 · **Проверено:** живым прогоном против `@agentclientprotocol/claude-agent-acp` 0.67.0 (Claude Code 2.1.217)

## Заявка, которая не подтвердилась

Замысел ACP-хоста строился на фразе спецификации: агент не правит файлы сам, а просит редактор — `fs/read_text_file`, `fs/write_text_file`. Отсюда следовал план: пропустить эти запросы через наши инструменты правки, и работа чужого агента попадёт в чекпоинты и журнал.

**Claude Code клиентскую файловую систему не вызывает вовсе.** Три прогона, счётчик `fs/write_text_file` — ноль. В `dist` адаптера методы объявлены как прокси к клиенту, но ни один вызывающий их не дёргает: правки идут его собственными `Read`/`Edit`/`Write` напрямую в файловую систему. Объявленные нами `clientCapabilities.fs` корректны — их не используют.

Вывод шире одного агента: **объявленная возможность протокола не равна используемой**. Проверять надо не спецификацию, а конкретного собеседника.

## Где ворота стоят на самом деле

Контроль есть, и он лучше задуманного:

- `session/request_permission` приходит **до** записи на диск и несёт `toolCall` с путями и готовым диффом;
- кадры `tool_call` / `tool_call_update` несут `content[].type === 'diff'` с `oldText`/`newText`, а в `_meta.claudeCode.toolResponse` — `structuredPatch` и `originalFile`.

Поэтому чекпоинт снимается **в момент вопроса**, а не после ответа агента: между «да» и правкой места нет. Отказ снимок отбрасывает — иначе история заполняется точками отката, которым не соответствует ни одной правки.

## Грабля: дифф приезжает не в том кадре

Кадры одного вызова идут так:

1. `tool_call` — вызов объявлен, `rawInput` пуст;
2. `tool_call_update` — появились аргументы;
3. `tool_call_update` — **появился дифф**, статуса нет;
4. `session/request_permission` — вопрос человеку;
5. `tool_call_update` со `status: "completed"` — **только текстовый итог, диффа нет**.

Слушатель, ждущий диффа от завершающего кадра, не запишет **ни одной** правки. Лечится накоплением по `toolCallId` в ленте сессии (`common/acp/acpSessionLog.ts`): поздний кадр дополняет карточку вызова, но не обедняет её, и в журнал уходит накопленное, а не пришедшее последним. Дефект поймал живой смоук, а не тесты — тесты писались по той же ложной модели, что и код.

## Окружение

- **Метки чужой сессии.** С унаследованным `CLAUDECODE` агент отказывается стартовать: «Claude Code cannot be launched inside another Claude Code session». Хост гасит эти переменные у любого агента.
  С 21.10.2026 в списке (`NESTED_SESSION_MARKERS`, `electron-main/acp/vibeAcpMainService.ts`) и `CLAUDE_CODE_SIMPLE`: с ней Claude Code стартует голым — без входа, `CLAUDE.md`, правил пользователя. Проверено запуском адаптера 0.93.0 с этой переменной: `session/new` проходит, а `session/prompt` отвечает `-32000 Authentication required`. Заданное в `env` записи агента остаётся (`childEnv` пропускает метки, которые назвала сама запись). Находка VibeIDEA: в её списке метки не было; наш список перечитан, и в нём её тоже не было
- **`authenticate` адаптер не реализует** — отвечает `Method not implemented`, хотя в `initialize` объявляет `authMethods: [claude-login]`. Вход только внешний: `claude /login`. Отказ выглядит как `-32000 Authentication required` на `session/prompt` — на `session/new` он ещё не срабатывает, сессия создаётся успешно.
- **Пакет переименован:** `@zed-industries/claude-code-acp` (deprecated) → `@agentclientprotocol/claude-agent-acp`.
- **`stopReason: end_turn`**, а не `completed` — приведение в [[acpHost]] это учитывает; неизвестная причина к «завершено» не приводится.
- **`usage_update` несёт стоимость хода** (`cost.amount`, USD) — 0.19 $ за трёхшаговый смоук.

## Поверхность: две грабли слоя React

Панель «Внешние агенты» — вкладка-редактор (снята 15.10.2026, агенты переехали в чат и в Настройки; урок остаётся в силе для любой React-панели), и на ней вскрылись два дефекта класса «код правильный, стилей нет». Оба подтверждены замером через CDP, а не чтением исходника.

**Классы на корне скоупа не применяются.** `scope-tailwind` генерирует правила как `.vibe-scope .vibe-px-6` — для ПОТОМКОВ. Корневой элемент несёт и `vibe-scope`, и `vibe-px-6`, поэтому селектор на него не действует: `getComputedStyle` показывал `padding: 0px` при заявленных `px-6 py-5`. Лечится так: корень несёт только скоуп, размеры и фон задаются инлайновым `style`, всё оформление живёт на внутренней обёртке. Дефект не наш личный — та же форма записи в «Диспетчерской агентов».

**Классы из строковой константы не префиксуются.** `const BUTTON_CLASS = 'rounded-md …'` не проходит через scope-tailwind: он видит только литералы `className` в JSX. Кнопки остались голыми, и в снимке это выдал селектор `button.rounded-md.border` — без префикса `vibe-`. Лечится компонентом с литеральным className, а не константой.

**Шкала размеров у проекта своя:** `xs=10px`, `sm=11px`, `root=13px`, `lg=14px`. Значит привычные `text-xs`/`text-sm` дают нечитаемый текст, и минимум для интерфейса — `text-root`.

**Собственный интерфейс проверяется собственным детектором.** Сборщик `buildReloadClientScript` выполняется в контексте workbench через CDP, снимок скармливается `reviewDesign` — и панель проходит те же 78 проверок, что чужая страница. На первом прогоне это дало 47 находок, после правок — ноль подтверждённых. Правило `occludedText` при этом само оказалось с дефектом: оно считало перекрывающим слоем собственного предка, если его селектор записан от `body`. Починено структурно — снимок несёт `parentId`, и родство определяется по цепочке, а не сравнением строк.

## Переподключение без перезапуска IDE (2026-09-23)

Процесс агента умер — раньше это значило перезапуск IDE: событие `failed` писало строку в журнал
активности, и больше сделать было нечего. Теперь новый процесс подхватывает ту же сессию. Грабли:

- **Спека даёт три дороги, и выбор — по объявлению агента.** `session/resume`
  (`agentCapabilities.sessionCapabilities.resume` — объект) возвращает ту же сессию без повтора
  истории; `session/load` (`agentCapabilities.loadSession: true`) — тоже ту же, но сначала агент
  прогоняет весь разговор кадрами `session/update`; иначе остаётся `session/new`. Вызывать
  необъявленное спека запрещает. Объявленное всё равно может не сработать — упавший агент мог не
  сохранить сессию, — поэтому каждая неудача падает на следующую дорогу
- **Повтор истории при `load` надо глотать.** Разговор уже в ленте; пропущенный дальше повтор показал
  бы каждое сообщение и каждую правку дважды и дважды записал бы их в журналы
- **`_fail` срабатывал на штатное закрытие.** Закрытие убивает процесс, приходит `exit`, и в журнал при
  каждом закрытии уходило «связь оборвалась». Плюс `error` и `exit` приходят на одну смерть — событие
  шло дважды. Теперь у процесса флаги: закрыт нами — не обрыв; уже учтён — второй раз не учитывается
- **Поздний `exit` мёртвого процесса не должен снимать с учёта живой.** После `resume` и `load` новый
  процесс обслуживает тот же id сессии; снимать с учёта можно только свой процесс
- **При новой сессии id меняется, а карточка остаётся на месте** — в ленте пометка редактора: помнит
  ли агент разговор выше. Это главное, что человеку надо знать после обрыва
- **Процесс, не прошедший знакомство, убивается.** Раньше при сбое `initialize` дочерний процесс
  оставался жить без присмотра

## Импорт из реестра ACP (2026-09-23)

Реестр ACP — курируемый JSON с CDN, версии в нём бампает ежечасный cron по релизам npm, PyPI и GitHub.
Импорт из него — канал поставки, и решения ниже держат его честным:

- **Контрольной суммы у сборки может не быть.** Формат показывает `sha256` в примере, но в живом реестре
  (23.09.2026) у 47 бинарных сборок из 100 её нет. Правило «бинарь только со сверкой» на деле означает «часть
  агентов из реестра не ставится» — список говорит это словами, а не прячет таких агентов
- **Пакет — точной версией.** В реестре все `npx`/`uvx` пригвождены (`pkg@1.2.3`, `pkg==1.2.3`); запись в
  `agents.json` несёт ровно эту строку, иначе ежечасный cron менял бы запускаемое под тем же именем
- **`--yes` у `npx` не нужен.** Документация npm 11: «When standard input is not a TTY… `--yes` is assumed». У
  ACP-агента stdin — канал протокола. Флаг только сделал бы нашу же запись находкой Config Guard
- **Бинарь пишется в машинный слой.** Проектный `agents.json` едет в репозитории, абсолютный путь в профиль одной
  машины там бессмыслен. Отсюда `~/.vibe/agents.json`: набор допускает машинный реестр как деталь продукта, у
  VibeIDEA это `~/.jetbrains/acp.json`
- **`~/.jetbrains/acp.json` читается третьим слоем (30.09.2026)** — туда ставят агентов VibeIDEA и IDE JetBrains
  (`agent_servers`: ключ — отображаемое имя, `command`, `args`, `env`). Файл только читается: копия устарела бы при
  первом же обновлении агента в соседнем продукте. Слой самый слабый — проект, потом машина, потом JetBrains; id
  выводится из имени (строчные, всё кроме букв и цифр — дефис). Для агента этого слоя `layerOf` возвращает
  `undefined`: добавление и обновление пишут только в наши файлы. Config Guard тот же, выключатель —
  `vibeide.acp.readJetBrainsAgents` (APPLICATION: репозиторий не должен включать чтение чужого файла команд)
- **Скачивание пишется на диск по мере прихода с хешем на лету**, распаковка идёт в папку-заготовку и переносится
  на место, только когда команда нашлась внутри: недоделанная установка не выглядит готовой
- **`tar.bz2` не распаковывается** — штатный `tar` из зависимостей понимает только gzip; четыре сборки из ста
  отклоняются с причиной, а не тянут новую зависимость ради них
- **Обновление правит поля, а не запись.** `jsonEdit.setProperty` в массив умеет только вставлять, поэтому
  меняются `command`, `args` и `registry` по отдельности — имя, `mcpServers`, `dir` и комментарии остаются

**Запуск агента.** Два дефекта, о которых раньше знала только спека:
- Хост брал голый `process.env`, а приложение из Dock не наследует `PATH` оболочки — `npx` давал `ENOENT`.
  Главный процесс VS Code уже разрешает окружение оболочки для терминалов и хоста расширений (с кэшем), но свой
  `process.env` не меняет; теперь его получают и агенты
- `child_process.spawn` без оболочки не запускает `.cmd`-обёртки Windows (`npx`, `uvx`). MCP-серверы с `npx`
  работали, потому что SDK запускает их через `cross-spawn`; теперь им пользуется и ACP-хост. `cross-spawn` —
  прямая зависимость той же версии, что приходила транзитивно, и внесён в список разрешённых модулей ESLint

## [решение] Настройки сессии гостя и закрытие по протоколу (2026-09-25)

**Контекст:** спека ACP стабилизировала настройки сессии (`configOptions`) и `session/close`.
У нас не было ни того ни другого: ответы `session/load` и `session/resume` выбрасывались целиком, а незнакомые обновления молчали.
«Закрыть сессию» гасил процесс, не сказав агенту ни слова.

**Суть:**
- Настройки — модель, режим, уровень мышления гостя — приходят в ответе на открытие сессии и обновлением `config_option_update`.
  Меняются методом `session/set_config_option`, ответ несёт всё состояние целиком.
  Смена модели может поменять и список режимов, поэтому карточка показывает ответ агента, а не выбранное значение.
- Булевы настройки агент вправе прислать, только если клиент объявил `session.configOptions.boolean`.
  Мы объявляем: флажок в карточке есть.
  У булевой настройки в запросе смены стоит `type: "boolean"`, как требует спека.
- Настройки хранит main-процесс: при смене булевой нужен её тип.
  Обновление настроек во время повтора истории `session/load` не глушится вместе с повтором: это текущее состояние, а не история.
  Кэш обновляется ещё до того, как новый процесс получил сессию, и переподключение отдаёт его карточке.
- Выбор, у которого текущее значение не совпадает с типом, и неизвестный тип пропускаются: такой контрол показал бы ложное состояние.
- `session/close` зовётся, только если агент объявил `sessionCapabilities.close`, и ждётся не дольше 3 секунд.
  Процесс гасится в любом случае.

**Применение:** разбор — `configOptionsOf` в `common/acp/acpProtocol.ts`, пилюли у поля ввода — `AcpConfigPills` в `sidebar-tsx/AcpChat.tsx` (до 15.10.2026 это была карточка `SessionSettings` на вкладке).
Старые `modes` и `models` не читаются: спека отдаёт приоритет `configOptions`.

## [решение] Отзыв вопроса агентом и команды агента (08.10.2026)

**Контекст:** разбор VibeIDEA (их решения №120 и №122) указал на два пробела, оба подтверждены кодом.
Уведомления кроме `session/update` хост игнорировал, и вопрос о разрешении, который агент отозвал `$/cancel_request`,
висел во вкладке. `available_commands_update` разбор не знал вовсе.

**Отзыв:**
- Ответ на отозванный запрос — ошибка `-32800`, карточка закрывается событием `permissionWithdrawn`, чекпоинт под
  вопрос отбрасывается, как при отказе
- Грабля гонки: окно сначала асинхронно снимает чекпоинт и лишь потом показывает вопрос. Отзыв, пришедший в этот
  промежуток, не находит карточку, поэтому запоминается (`_withdrawnBeforeShown`), и `_guard` после снятия чекпоинта
  выбрасывает и его, и вопрос
- Попутно найдено: протокол требует от клиента, отменившего ход (`session/cancel`), ответить `cancelled` на открытые
  вопросы хода. «Прервать» этого не делал — тот же зависший вопрос другим путём

**Команды:**
- Список приходит целиком и заменяет прежний; может прийти до того, как сессия передана окну, поэтому хранится на
  процессе агента и едет в ответе старта, как `configOptions`
- Команда выполняется, только если она первое слово задачи. Указание «Краткие ответы» ставится перед текстом задачи,
  и команда с ним агентом не узнаётся: для команды указание не отправляется и уходит со следующей обычной задачей

**Не проверено:** логика главного процесса тестом не покрыта (у `VibeAcpMainService` нет тестовой обвязки), живьём
с агентом, который шлёт `$/cancel_request` и команды, не прогонялось.

## [решение] Внешний агент в основном чате (15.10.2026)

**Контекст:** гость жил на отдельной вкладке «Внешние агенты» и не видел редактор.
Причина — `session/prompt` слал один блок `text`, а `promptCapabilities` не читались: на «изучи открытый файл» агент не знал, какой файл открыт.
Вкладка при этом была вторым чатом со своей лентой, вводом и очередью вопросов.

**Решения владельца:**
- А1: агент — группа «Внешние агенты» в общем списке моделей, выбор хранится на тред.
  Агент ведёт тред целиком, поэтому смена цели посреди треда выключена: это два разных цикла с разной памятью
- Б1+Б2: наш режим (Вручную / Правки / План / Автопилот) плюс наш слой разрешений.
  Режимы агента `auto` и `bypassPermissions` не спрашивают вовсе: пропали бы чекпоинт и проверка необратимой команды.
  Поэтому на агента выставляется только `plan`, остальные три оставляют его спрашивающим, а отвечает за человека `acpPermissionPolicy`
- В2: блоки контекста в промпте плюс свой MCP-сервер IDE (`vibe_open_file`, `vibe_problems`) на localhost с токеном
- Г2: реестр агентов — Настройки → «Агенты», вкладка удалена

**Что подтверждено живьём (Claude Agent, адаптер 0.79.0):**
- «Изучи открытый файл» с выделением строк: агент назвал файл и строки, в ленте карточка чтения
- Вопрос о правке приходит карточкой с диффом в ленте; «Отказать» оставляет файл нетронутым, карточка правки — «ошибка»
- «Стоп» посреди вызова: карточка команды становится «отменено», а не остаётся «идёт»; карточка, оставшаяся от прошлого запуска IDE, снимается при следующем сообщении треда
- Тред после перезапуска IDE: агент помнит разговор (на вопрос о первом задании назвал его), модель и режим треда на месте
- Режим «Правки»: правка проходит без вопроса, в журнале «разрешено без вопроса»
- «На сессию» для `npm` разрешает последующие `npm --version` без вопроса; составная команда (`a | b`) «На сессию» не получает
- `/caveman lite` из меню «/» уходит агенту первым словом и исполняется
- ↑ в поле ввода возвращает прошлую задачу

**Грабли:**
- **Прерванный ход оставлял карточку «идёт».** «Стоп» или закрытый вопрос посреди вызова: завершающий кадр не приходит, карточка висела вечно.
  Судя по итогу, карточка читалась со стадией `unknown` (подпись у неё тоже «идёт»): первая версия правки, снимавшая только `pending` и `in_progress`, живьём ничего не меняла, а версия с `unknown` сработала. Самой стадии карточки в окне не видно — это вывод, а не замер
  Теперь конец хода (`settleTurn` в `AcpSessionLog`, зовётся из `finally` у `prompt`) переводит в «отменено» все незавершённые карточки, `unknown` включая (`isToolOpen`), а раннер чата делает то же с карточками, оставшимися в сохранённом треде от закрытого IDE
- **Отдельное окно: хост React пуст, ошибки в интерфейсе нет.** Вспомогательное окно VS Code подменяет `document.createElement` на бросающий исключение: элементы обязаны создаваться в главном окне.
  React берёт документ у контейнера (`rootContainerElement.ownerDocument`), поэтому первый же рендер в окне падает, а исключение уходит в консоль главного окна.
  Редактор показывает панель вкладок и пустое тело. Стек: `completeWork → ownerDocument.createElement`
  Лечение — в `mountFnGenerator`: контейнер отдаёт React вид своего настоящего документа, где `createElement` идёт в главное окно, а остальное — настоящему документу. Узел усыновляется окном при добавлении
  **Граница:** чат — не редактор, а вид (`VibeChatViewPane`) в панели справа, и в отдельное окно его вынести нельзя: окна у VS Code открывают только редакторы (`auxiliaryEditorPart`) и несколько служебных окон.
  Через `mountFnGenerator` монтируются React-редакторы — Настройки и «Диспетчерская агентов»: они и получают исправление
  Обработчики «клик снаружи» и границы выпадающих списков в React-слое читают глобальный `document` (главное окно) — в отдельном окне выпадающие списки закрываются и позиционируются неверно. Это не исправлено
- **Стенд из копии профиля владельца поднимает его Telegram-мост.** Бот `@VibeBrainsBot` ответил из тестового экземпляра. Копия профиля для стенда должна нести `vibeide.telegram.enabled: false`
- **Агенты ниже сгиба.** Список моделей из десятков записей прятал группу агентов, поэтому порядок такой: «Авто», агенты, группа «Модели»

**Потеряно вместе с вкладкой:** сессии, начатые из Telegram, больше не видны в IDE как лента (остаётся журнал активности агентов).
Вопрос такой сессии отвечается с телефона: уведомления «Показать» в IDE больше нет.

**Находка про `/ide`.** В бинаре Claude Code есть собственная IDE-интеграция: каталог `~/.claude/ide/`, переменная `CLAUDE_CODE_AUTO_CONNECT_IDE`, инструменты `mcp__ide__getDiagnostics` и `mcp__ide__executeCode`; `/ide` управляет подключением.
Она рассчитана на расширение редактора, которое оставляет там файл-метку, и привязана к Claude Code. Адаптер ACP 0.79.0 про неё ничего не знает (в его `dist` нет ни одного упоминания).
Поэтому редактор отдаётся гостю своим MCP-сервером: он работает с любым ACP-агентом, а не только с одним.
**Не проверено:** подхватывает ли Claude Code внутри адаптера метки из `~/.claude/ide/` сам и что тогда делает `/ide` — живьём не прогонялось.

## [решение] Кто ведёт тред: строка состояния и чип читают тред, а не функцию «Чат» (21.10.2026)

**Контекст:** при выбранном в треде Claude Agent элементы строки состояния («</> MiniMax-M3», зелёная галочка здоровья провайдера) и чип «Модель MiniMax:MiniMax-M3» на пустом чате называли модель функции «Чат», а под полем ввода стоял агент.
Выбор модели хранится на функцию (`modelSelectionOfFeature['Chat']`), выбор агента — на тред (`ThreadType.acpAgent`). Показ, читавший только первое, о втором не знал: так бывает с любым новым ведущим, если «текущая модель» берётся отовсюду по-своему.

**Решение:**
- Один источник — `common/chatLeader.ts`: `chatLeaderOf(тред, выбор модели)` отдаёт агента или модель, `chatLeaderKey` — ключ смены. Чистая, тест `chatLeader.test.ts`
- Строка состояния берёт ведущего через `browser/chatLeaderWatcher.ts` (`currentChatLeader`, `onDidChangeChatLeader`). Пять элементов: модель (`vibeideStatusBar`), статус провайдера и расход (`vibeProviderStatusBar`), политика обучения, формат вызова инструментов; конфиденциальность для агента прячется — где он работает и куда шлёт данные, решает он сам
- Для агента элемент говорит, что решение за агентом, а не молчит: «обучение: у агента», «FC: агент», у расхода — подсказка про подписку агента. Связь с агентом (`✅` на связи, `⚠️` оборвалась, `plug` — сессия ещё не начата) читается из сервиса сессий и обновляется только на смене состояния связи
- Чип над полем ввода (`ContextChipsBar` в `SidebarChat.tsx`) называет агента «Агент …», а не модель; строка про обучение в быстрых настройках чата — тоже

**Грабля:** событие сервиса чата `onDidChangeCurrentThread` стреляет на КАЖДОЕ изменение состояния треда (его комментарий в `_setState`: оно же служит общим сигналом), то есть на каждый кусок ответа. Подписка без сравнения ключа перерисовывала бы пять элементов строки на каждом куске: `onDidChangeChatLeader` зовёт слушателя, только когда ключ ведущего сменился.

**Проверено живьём на стенде** с подставным ACP-агентом: в треде агента — `Stub Agent` в строке и чип «Агент Stub Agent», после старта сессии ✅; новый тред — снова модель; возврат на вкладку агента — снова агент.

## [решение] Правки внешнего агента — на общем разборе «принять / отклонить» (21.10.2026)

**Контекст:** хендофф VibeIDEA от 16.10 — правки Claude по ACP шли мимо «принять/отклонить», а откат снимка нигде не вызывался. Сверено с нашим кодом командами:
- Claude пишет файл **сам**: клиентский `fs/write_text_file` не зовёт (см. «Заявка, которая не подтвердилась» выше). Клиент узнаёт о правке из кадров `tool_call`/`tool_call_update` (дифф) и вопроса `session/request_permission`; оба приходят до записи, а `completed` — после
- Дифф шёл только в ленту и карточки чата (`acpSessionLog.ts`, `AcpChat.tsx`): в `vibeAcpSessionsService.ts` и `acpChatRunner.ts` не было ни одного обращения к `editCodeService` и зонам разбора
- Старый снимок `IRollbackSnapshotService` (`_snapshotBefore`) снимается на вопрос о правке, но `restoreSnapshot` для ACP не звал никто, а сам он выключен по умолчанию (`vibeide.safety.rollback.enable`). Подпись «Чекпоинт по этим файлам уже снят — правку можно откатить» в карточке вопроса обещала его безусловно. Подпись заменена на «Принятая правка встанет в список файлов с изменениями…», сам снимок оставлен: его читает «частичный откат» (`vibePartialRollbackService`)
- Откат **треда** по чекпоинту для ACP уже был (`4b95f1809`, 16.10: снимок папки перед ходом); хендофф писался раньше. Живьём он проверен впервые — см. ниже

**Решение — правка агента встаёт на тот же разбор, что правка встроенного:**
- Вызов с `kind: edit`, дошедший до `completed`, ставится на разбор по факту (`browser/acp/vibeAcpEditReview.ts`): `editCodeService.registerExternalEdit` заводит зону на весь файл, исходный текст — база, текст в модели — то, что на диске. Панель «N файлов с изменениями», «Принять»/«Отклонить» по файлу и по всем, подсветка в редакторе — штатные, их читает `vibeideCommandBarService` по зонам
- **База «до» — первое касание файла в ходу**, как у зоны встроенного агента (`keep-conflicts`): вторая правка того же файла вливается в уже стоящую зону, прежняя база остаётся. «Отклонить» возвращает файл к началу хода, а не к началу последней правки
- Базу читает **главный процесс** (`electron-main/acp/acpFileBefore.ts`) в момент, когда кадр вызова-правки только пришёл, и шлёт событие `before` раньше самого кадра. Не окно: до него кадр идёт ещё через IPC, а быстрый инструмент успевает записать файл. Не кадр `completed`: на нём файл уже записан. Чтение синхронное намеренно (порядок «база, затем кадр»), файл крупнее `ACP_BEFORE_MAX_BYTES` (1 МиБ), не UTF-8 или вне рабочей папки сессии базы не даёт
- Решение, что ставить на разбор, — чистая `resolveBaseline` (`common/acp/acpEditBaseline.ts`): снятая база, если диск уже другой; **база совпала с диском** (вызов успел записать раньше, чем прочли) — «до» восстанавливается обратной подстановкой `newText → oldText` из диффа, но только если новый текст в файле один; запись файла целиком (`oldText` пуст) и удаление текста без базы **не ставятся** — угаданная база сделала бы «Отклонить» разрушительным
- **Файл, которого до хода не было**, ставится с пустой базой; «Отклонить» убирает файл (в корзину, если она есть) — иначе от него остался бы пустой. Удаление ждёт сохранения отката: иначе оно вернуло бы файл обратно пустым
- Файл с несохранёнными правками человека и файл вне проекта на разбор не идут. Файл, записанный агентом через наш `fs/write_text_file` (его используют другие агенты), ставится так же: базу снимает главный процесс перед записью

**Грабли:**
- Первый кадр вызова приходит с пустым `rawInput` и без путей, путь появляется в следующих кадрах. Главный процесс помнит вызов-правку по `toolCallId` (`editCalls`) и читает файл на первом кадре с путём
- Адаптер 0.93.0 после правки присылает итоговый дифф по `structuredPatch` — **обрывки с контекстом**, а не файл целиком; `originalFile` из ответа инструмента в кадр больше не попадает (в 0.67.0 он ехал в `_meta`). Поэтому дифф агента годится только как подсказка для восстановления базы, но не как сама база
- **Возврат папки и зоны разбора.** После «Вернуть папку» у файла на разборе зона держала текст «до» от прежнего состояния: панель показывала правку, которой уже нет, а «Отклонить» записало бы в файл текст из прошлого. Нашёл живой прогон, не тесты. Теперь `VibeWorkspaceSnapshotService.restore` после возврата снимает зоны на возвращённых и удалённых файлах без изменения текста и без записи в историю, а модель берёт текст с диска (файл с несохранёнными правками человека не перечитывается)
- Кнопка «Вернуть папку» в диалоге подтверждения: клик координатами по кнопке модалки в стенде закрыл её без возврата, а клик по кнопке через DOM — вернул. Это поведение стенда, а не продукта: проверять по уведомлению «Рабочая папка возвращена…», а не по закрытию окна

**Проверено живьём** (стенд `launch` на заглушке ACP-агента, правящей файлы сама, как Claude; папка под git): правка с вопросом → «1 файл с изменениями» → «Отклонить» вернул файл, `git status` чист; правка без вопроса; «позднее объявление» (файл записан до кадра) — база восстановилась по диффу, отклонение вернуло файл; создание файла → отклонение убрало файл; запись поверх существующего (`oldText` пуст) — база из главного процесса, «Отклонить всё» вернул два файла; две правки одного файла в разных ходах — одна зона, «2 правки»; «Принять всё» оставил текст. Откат треда кнопкой «Checkpoint» (ACP-тред): диалог с числом изменившихся файлов, «Вернуть папку» вернула файлы, уведомление «Рабочая папка возвращена к чекпоинту».

**Не проверено / открыто:**
- С настоящим Claude Code правки через этот путь не прогонялись: стенд на заглушке по форме кадров, снятой с живого прогона (`tool_call` без путей → обновление с путями → `request_permission` → `completed`). Какая именно гонка у адаптера 0.93.0 в режиме «Правки», когда вопроса нет, не измерена: оба исхода гонки покрыты (база из главного процесса и восстановление по диффу), но частота каждого неизвестна
- Удаление и перемещение файлов (`kind: delete`, `move`) и записи командами (`sed -i` в `Bash`) на разбор не идут: у них нет диффа и базы. Их покрывает только откат всей папки по снимку
- Файл, на котором уже стоит **не** весь файл зона быстрой правки (Ctrl+K), получает правку агента только внутри её строк: зона одна и не растягивается

## [знание] Цена контекста Claude по ACP: правила проекта агенту не клеим (21.10.2026)

**Контекст:** хендофф VibeIDEA от 21.10 — одно и то же ревью кода через Claude Code в двух продуктах стоило по-разному: у VibeIDEA 935 тыс. токенов и пропавшая метка «Бригадир: включён», у нас 99 тыс. у субагента и около 66 тыс. в главной сессии. Причина у них: правила проекта, указатели и стиль клеились к **каждому** ACP-сообщению, а Claude Code читает всё это сам.

**Сверено с нашим кодом:**
- `buildAcpPromptBlocks` (`common/acp/acpPromptContext.ts`) собирает блок `<ide_context>` (активный файл и вкладки), текст задачи, прикреплённое (выделения, файлы, папки) и картинки. Правил проекта, `AGENTS.md`, указателей базы знаний в нём нет. Стиль «Краткие ответы» уходит один раз за сессию и ещё раз при смене уровня (`brevityForAgent`, `state.brevitySent` в `vibeAcpSessionsService.prompt`)
- Адаптер открывает сессию с `settingSources: ["user", "project", "local"]`, то есть `CLAUDE.md`, `AGENTS.md` и правила пользователя Claude Code читает сам; приставка из тех же правил читалась бы дважды и лежала в истории на каждом вызове модели. Замер VibeIDEA на адаптере 0.93.0: около 9,4 тыс. токенов на сообщение и +39 % токенов на одном ревью
- Правка у нас не нужна: двойной загрузки нет. Нужна была одна вещь — метка `CLAUDE_CODE_SIMPLE` (раздел «Окружение» выше)

**Правило:** агенту, у которого своя история и который сам читает файлы инструкций, постоянный текст отдаётся **раз на сессию**, а не с каждым сообщением. Прежде чем передавать агенту правила, проверить, не читает ли он их сам: двойная загрузка не видна ни в одном тесте, только в счёте.

**Не измерено у нас:**
- Расход нашей стороны на настоящем Claude Code прогоном обоих продуктов не сверялся: числа выше — VibeIDEA и наши цифры из того же хендоффа, а не замер этого репозитория
- Цена MCP-серверов, которые гость получает по умолчанию («все пригодные», 21.10): описания их инструментов входят в контекст агента на каждом вызове (кэшируются, но входят). Сколько это на типичном наборе серверов — не мерили
- Блок `<ide_context>` повторяется в каждом сообщении (редактор меняется), он короткий, но тоже не измерен

**Как перемерить одинаково в обоих продуктах:** сессии лежат в одном каталоге транскриптов (`$CLAUDE_CONFIG_DIR/projects/<путь проекта>/`), поэтому `python3 vibe-plugins/tools/agentTurnUsage.py <корень проекта> --last 4` из репозитория VibeIDEA читает оба. Разбор — `docs/vibe/knowledge/agents/acpContextCost.md` там же.

## [решение] «Автопилот» и удаление: область «проект и временные каталоги» (21.10.2026)

**Контекст:** живой случай 20.10 — `export VIBEAGENT_HOME=$(mktemp -d /tmp/va-XXXXXX) … rm -rf $VIBEAGENT_HOME` останавливал «Автопилот» вопросом `irreversible`, в Claude Code тот же ход проходит. `analyzeShellLine` зовёт удаление разрушительным, потому что не знает, что удаляется, а политика спрашивала такое «до режима и разрешений».

**Решение:**
- Удаление внутри проекта (чекпоинт хода) и внутри временных каталогов необратимым не считается — дальше решает режим. Остальное, что было необратимым, осталось им: вне области, `~`, `/`, принудительный пуш, код из сети
- Классификатор общий: его зовёт основной чат (`toolsService._gateDestructiveCommand`). Поэтому область — параметр, а не правка правила: `analyzeShellLineIn(line, scope)` рядом с прежней `analyzeShellLine(line)`. **Не второй параметр прежней:** `lines.map(analyzeShellLine)` (так её зовёт тест) передал бы индекс элемента как область, и тест упал на первой же строке
- `common/shellRemovalScope.ts` — чистая область: цели `rm` (после `--`, без `--no-preserve-root`), значения переменных, `cd`, `mktemp`. Контекст политики получил `cwd` (рабочая папка сессии хранится в состоянии сессии: от неё читаются относительные пути)

**Почему область читает так осторожно:** разрешение выдаётся молча, поэтому всё неясное — «нет».
- `.git` не удаляется без вопроса в любой записи: там `refs/vibe/checkpoints`, удаление `.git` уничтожило бы чекпоинт, ради которого удаление в проекте и считается обратимым. Шаблон `.*` или `.g*` тоже ловится: проверка идёт по самому шаблону
- Относительный путь читается от `cwd` сессии, и `..` из него не выводит; после `cd` наружу или в неизвестное доверие к относительным путям не возвращается (если `cd` не сработает, строка останется там, куда разбор уже не дошёл)
- Присвоения — только отдельным этапом или `export`; второе присвоение той же переменной в строке делает её неизвестной (оно могло уйти в фон), `+=` — тоже; значение с пробелом или шаблоном отбрасывается (при подстановке без кавычек оно распалось бы на цели); `eval`, `source`, `read`, `unset`, группа `{ … }`, `if/for/while` — снимают доверие ко всем переменным
- `$TMPDIR`, `$TMP`, `$TEMP` считаются временным каталогом по определению, их настоящее значение не нужно
- PowerShell (`Remove-Item`) область не читает: разбор строки ведётся по правилам POSIX, и `C:\Windows\Temp` превращается в чужое относительное имя `C:WindowsTemp`. Путь Git Bash `/c/proj` приводится к `c:/proj`

**Граница:** удаление, спрятанное в аргументе `bash -c "rm -rf /tmp/x"` или `$(rm -rf /tmp/x)`, по-прежнему спрашивается: флаг `-rf` в тексте аргумента классификатор считает разрушительным сам, до разбора вложенного.

**Проверено живьём** (подставной ACP-агент, «Автопилот»): `export VIBEAGENT_HOME=$(mktemp -d /tmp/va-XXXXXX) && echo ready && rm -rf $VIBEAGENT_HOME` и `rm -rf build dist .cache` проходят без вопроса, `rm -rf /Users/…/Documents/…` и `git push --force origin main` приходят карточкой с новым объяснением.

## [решение] Зеркало треда живёт дольше `session/prompt` (25.10.2026)

**Контекст:** после хода по таймеру Claude Agent продолжал работать по уведомлениям, но тред показывал только следующие сообщения человека. `AcpChatRunner._runTurn` подписывался на журнал лишь на время `prompt` и каждый раз начинал с `turnStart`; записи между запросами оставались в `AcpSessionLog`, но не попадали в тред. До этого дефект скрывался тем, что адаптер держал один `prompt` открытым несколько часов.

**Суть:** привязка треда владеет одним наблюдателем и одним курсором журнала. Курсор сохраняется при отвязке, поэтому повторное открытие переносит только накопленный хвост; стабильные ключи блоков не дают дублей, а перечтение последнего блока сохраняет потоковые обновления. Перед новым сообщением человека хвост синхронизируется принудительно, закрытие и `dispose` снимают подписку и scheduler. Новая автономная полоса получает заметку IDE «Агент продолжил сам»; `task-notification` и `scheduled` уточняются по уже существующему `_meta["_claude/origin"]` кадра `usage_update`, который теперь проходит через разбор без выдуманных ACP-полей.

**Применение:** не возвращать зеркало в `_runTurn` и не использовать `turnStart` следующего запроса как границу истории. Регрессия в `acpChatRunner.test.ts` воспроизводит событие именно после завершения `prompt`; также покрыты два автономных события, человек после них, повторное открытие, `dispose` и `busy` → `interrupt` → `cancel`. Если `view.busy` истинно, работа и Stop действуют штатно. Текущий `VibeAcpSessionsService` выставляет `busy` только вокруг вызванного окном `prompt`: для автономного хода вне запроса надёжного начала/конца и безопасной отмены из существующих событий не выводится, нужен отдельный протокольный контракт. Отнесение scheduled-origin к автономной полосе остаётся внешней задачей `claude-agent-acp`; перенос журнала VibeIDE от неё и от длины `prompt` не зависит. Живой сценарий с таймером не прогонялся.
