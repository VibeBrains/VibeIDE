# Спецификация Agent Skills: где мы от неё расходились

**Дата:** 2026-08-11 · **Ветка:** `next` · **Источник:** [agentskills/agentskills](https://github.com/agentskills/agentskills) (Apache-2.0 / CC-BY-4.0)
**Код:** `scripts/vibe-skills.js`, `common/vibeSkillsLibraryService.ts`

## Что это

Не каталог скиллов, а **сама спецификация** формата `SKILL.md` плюс эталонный валидатор на
Python и документы по написанию скиллов. Формат у нас тот же — расхождения были в деталях,
и каждая из них ломала совместимость в одну или другую сторону.

## Разрешённые поля верхнего уровня — закрытый список

```
name  description  license  allowed-tools  metadata  compatibility
```

**Эталонный валидатор отвергает всё остальное** («Unexpected fields in frontmatter»), а не
игнорирует. Это проверено по его исходнику, и это меняет вывод: наши поля верхнего уровня
делали скилл невалидным для любого стандартного клиента, а не просто «нестандартным».

**Наши расширения живут под `metadata`** — `vibeVersion`, `depends`, `precheck`, `triggers`,
`glob`, `keywords`, `requires-tools`, `min-vibeide`, `locale`, `tags`. Приятная неожиданность:
переписывать парсеры не пришлось — они читают поля через `^\s*поле:`, и ведущий отступ им не
мешает, так что вложенные значения распознаются как прежде. Проверено прогоном: `depends`
внутри `metadata` собрал граф зависимостей, `vibeVersion` прочитался.

## Ограничения, которые мы не проверяли

| Правило спеки | Что было у нас |
|---|---|
| `name` ≤ 64, строчные, цифры, одиночные дефисы не по краям | не проверялось |
| `name` **совпадает с именем папки** | не проверялось — расхождение ломает вызов молча |
| `description` ≤ 1024 | не проверялось |
| `compatibility` ≤ 500 | поля не было |
| тело ≤ 500 строк (рекомендация) | стоял предел 512 КБ — при рекомендации в 500 строк он не срабатывал никогда |

## Два дефекта совместимости, найденных сверкой

**Мы требовали `vibeVersion` обязательным.** Любой скилл из экосистемы — а формат поддержан
десятками клиентов — у нас не проходил проверку, потому что такого поля в стандарте нет.
Теперь поле необязательное и читается из обоих мест.

**Описание парсилось однострочным regex.** Спека разрешает блочный скаляр (`description: |`),
и такой скилл давал описание `|` — формально непустое, поэтому проверка его пропускала, и в
каталог попадала палочка вместо текста. Дефект был в **двух** местах: в CLI-валидаторе и в
рантайме (`parseSkillMarkdown`), то есть пользователь увидел бы это в самой IDE.

## Соответствия наших полей стандартным

| Наше | Стандартное | Решение |
|---|---|---|
| `requires-tools` (через запятую) | `allowed-tools` (через пробел) | принимаются оба; разделитель выбирается по содержимому, иначе `Read, Write` распалось бы на «Read,» |
| `min-vibeide` + `precheck` | `compatibility` | принимаются все три: первые два про версию IDE и путь, третье — про окружение словами и читается **до** раскрытия скилла |

## Практика, которую стоит перенять

Спека предлагает мерить пользу скилла **прогоном каждого теста дважды** — со скиллом и без —
и сравнивать вслепую. Без этого «скилл помог» остаётся ощущением. Там же полезное наблюдение:
скилл может улучшить результат и при этом втрое поднять расход токенов — это две разные
сделки, и мерить надо обе.

Ещё оттуда, про описания: императивная формулировка, упор на намерение пользователя, явное
перечисление ситуаций **включая те, где предметная область не названа прямо**.
