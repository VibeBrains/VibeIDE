# Сторонний код и провенанс — флажок ДО сборки/релиза

← [Knowledge Index](../README.md)

**Контекст.** В релиз v0.16.0 ушло встроенное расширение `vibe-keybindings`, представлявшее собой дословный вендоринг чужого MIT-проекта (kasecato/vscode-intellij-idea-keybindings) с его копирайтом. Проблема всплыла уже ПОСЛЕ публикации релиза (по ченджлогу), релиз пришлось удалять и переавторивать keymap. Пользователь: «впредь предупреждай о такой лаже».

**Суть (правило поведения агента).**
- Любой код/данные, взятые из стороннего репозитория (вендоринг, порт, «по образцу»), — это **провенанс-риск**, его нужно поднять ЯВНО и ДО того, как он попадёт в `git commit` → билд → релиз. Не молча тащить и не «разберёмся потом».
- «Это же опен-сорс / просто данные / просто сочетания клавиш» — **не** отменяет лицензию апстрима. Open source ≠ public domain. MIT/BSD/Apache требуют сохранять копирайт-уведомление при копировании существенной части.
- «Сделаем как у них, но наше» при дословной копии файла — это производная работа, а не независимое авторство. «Наше» = переавторить инженерную часть (у keymap: `when`-клаузы, выбор сопоставлений, кураторскую подборку), а функциональные факты (схема горячих клавиш JetBrains, ID команд VS Code) совпадать могут и это не нарушение.
- Самый плохой исход — оставить копию, но снять атрибуцию: это прямое нарушение лицензии. Либо честная атрибуция, либо честное переавторивание.

**Применение.**
1. Перед бандлингом стороннего артефакта — назвать пользователю: источник, лицензию, что именно копируется (весь файл / подмножество / только идея) и вытекающие обязательства. Дождаться решения.
2. Никогда не доводить такой артефакт до `release-windows.ps1` без явного «ок» по лицензии.
3. Если решение «сделать своим» — переавторить, а не переименовать; убрать `repository.url`/копирайт апстрима, задокументировать наш провенанс (на основе какой публичной спецификации построено).
4. Связано: [vibeKeybindings.md](vibeKeybindings.md) (история этого конкретного кейса и текущая модель владения keymap).

## [лицензирование] Наш код — AGPL-3.0, апстрим — MIT (03.10.2026)

**Контекст.** Решение владельца 03.10.2026: все продукты семейства (VibeIDE, VibeIDEA, VibeMemory) — под AGPL-3.0. Причина в разборе VibeMemory (`docs/knowledge/design/openSource.md`): по MIT код можно взять, закрыть доработки и продавать хостинг, ничего не отдав; AGPL оставляет бесплатными использование и установку у себя (в том числе внутри компании), но обязывает открыть изменения тому, кто даёт изменённую версию другим по сети. Кому AGPL не подходит, продаётся отдельная лицензия.

**Суть.** Сборка в целом — AGPL, но она собрана из кода под разными лицензиями, и путать их нельзя: MIT и Apache-2.0 совместимы с AGPL в одну сторону (их код можно включать в AGPL-сборку), поэтому лицензии апстрима не переписываются — их файлы и уведомления остаются как есть. Уже выпущенные версии остаются под прежней лицензией; переход виден начиная со следующего выпуска.

**Применение.**
1. Файлы: `LICENSE.txt` — AGPL-3.0 (наш код), `LICENSE-MIT.txt` — MIT Microsoft для кода Code-OSS (дословная копия прежнего `LICENSE.txt`, не редактировать), `ThirdPartyNotices.txt` — вендорные компоненты (апстрим, не трогать).
2. Метаданные: `product.json` → `licenseName: "AGPL-3.0-only"` (значение уезжает в SPDX-поля Linux-метаданных через `@@LICENSE@@`), `licenseUrl`/`serverLicenseUrl` остались на `LICENSE.txt` — файл сменил содержимое, а не имя; `package.json` → `"license": "AGPL-3.0-only"`.
3. Сборка: `build/gulpfile.vscode.ts` кладёт в артефакт два файла лицензии — рядом со штампом `product.licenseFileName` вписан `LICENSE-MIT.txt`. Без этого условие MIT нарушилось бы: уведомление Microsoft обязано ехать с каждой распространяемой копией, а имя штампа в `product.json` теперь указывает на AGPL.
4. Встроенные расширения нашего авторства — тоже AGPL (`extensions/vibe-keybindings`: `LICENSE.txt` и поле `license` в манифесте).
5. Шапка исходников со строкой `Licensed under the MIT License` унаследована от Code-OSS и описывает апстримный код. Массовой правки шапок при переходе не было — это отдельное решение (в README сказано, что строка относится к апстриму).
6. Двойное лицензирование чужих правок невозможно без права автора распространять вклад и под другой лицензией — эта строка есть в `CONTRIBUTING.md` и `docs/manuals/howToContribute.md`.
