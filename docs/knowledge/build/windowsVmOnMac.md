## [грабли] Инструменты родные, цель — x64

**Контекст:** 10.10.2026, релиз 1.24.0. Windows-машины под рукой нет, self-hosted раннер снесён.
Сборка `win32-x64` поднята в Windows 11 ARM64 под UTM на Mac с M4. Порядок работы — `docs/manuals/windowsBuildOnMac.md`.

**Суть:**
- Гонять инструменты сборки как x64 под эмуляцией нельзя. При параллельной сборке встроенных расширений
  один `esbuild.exe` не завершается и держит унаследованные каналы вывода соседних сборок.
  `gulp` ждёт `git` и `microsoft-authentication` вечно: ночь простоя, 23 секунды процессора за 10 часов.
  По одному расширения собираются за секунду — зависание видно только под нагрузкой
- Правильно: Node, esbuild и tsgo родные (ARM64), цель задаётся `npm_config_arch=x64` и `VSCODE_ARCH=x64`.
  Нативные модули MSVC кросс-компилирует под x64
- npm выбирает готовые платформенные пакеты по процессору хоста; цель сборки он не учитывает.
  В поставку попал `@vscode/vsce-sign-win32-arm64`. `sherpa-onnx-win-x64` не попал вовсе: ARM64-варианта у него нет.
  Лечит `scripts/win-vm/crossDeps.mts`: по lock-файлу докладывает production-пакеты под цель и убирает вставшие вместо них.
  Dev-пакеты не трогает — инструменты должны остаться родными
- Дочерние процессы сборки не наследуют `--max-old-space-size` у gulp. На машине с 10 ГБ памяти лимит кучи Node
  по умолчанию около 2 ГБ, и бандл ядра падает с кодом 134. Нужен `NODE_OPTIONS=--max-old-space-size=8192`
- `release-windows.ps1` — UTF-8 без BOM. Windows PowerShell 5.1 читает его как ANSI, и русское тире ломает разбор.
  Запускать через `pwsh` (PowerShell 7)
- `npm ci` в машине отказывается: у `ssh2` в lock-файле записан необязательный `cpu-features` без своей записи.
  На маке тот же npm этого не замечает. В сценарии — `npm install`, lock после него возвращается из git
- InnoSetup в систему ставить не нужно: `ISCC.exe` сборка берёт из npm-пакета `innosetup`
- PR в winget открывается с мака (`scripts/win-vm/wingetPr.sh`): `wingetcreate` нужен токен GitHub внутри Windows,
  а сам PR — три файла в форке. winget-pkgs слишком велик для клона, файлы кладутся через API одним коммитом
- Сверка нового манифеста с прошлым принятым показала `License: MIT` в шаблоне после перехода на AGPL-3.0:
  шаблон winget — ещё одно место, где живёт лицензия

**Применение:**
- Кросс-сборку проверять сверкой с артефактом настоящей платформы: список бинарников и архитектура каждого PE.
  Смоук-чек скрипта (версия, коммит, x64) прошёл на сборке без голосового ввода и с чужим `vsce-sign`
- Долгую фоновую сборку сторожить по росту журнала: зависший процесс кода выхода не возвращает
- Виртуальную машину гасить после сборки: 10 ГБ из 16

## [грабли] Сеть: open-vsx.org и uploads.github.com отваливаются на часы

**Контекст:** 12.10.2026, релиз 1.25.0. Сборка в машине дошла до `gulp vscode-win32-x64` и упала на `TypeError: fetch failed`.

**Суть:**
- Встроенные расширения (`ms-vscode.js-debug`, `js-debug-companion`, `vscode-js-profile-table`) задача `bundle-marketplace-extensions-build`
  качает с open-vsx.org, если нет готовой копии в `.build/builtInExtensions`. Сайт не отвечал ни из машины, ни с мака.
  Загрузка делает десять повторов с таймаутом тридцать секунд и падает; повторный запуск `package.ps1` падает так же
- На маке копия уже лежит: сборки мака берут её с диска. Лечение — перенести каталог в машину
  (`scp -r .build/builtInExtensions vsadmin@…:C:/b/VibeIDE/.build/`) и запустить `package.ps1`: компиляция второй раз не нужна, штамп `out-build` цел.
  Копия мака старее: в `vscode-js-profile-table` лежит `LICENSE.txt` вместо `ThirdPartyNotices.txt` и `telemetry.json` из выдачи open-vsx. Бинарников это не касается
- Загрузка в релиз упирается в `uploads.github.com`: `dial tcp … i/o timeout` при том, что `api.github.com` и `github.com` отвечают.
  Окно доступности бывает коротким (минуты), и повтор раз в две минуты его пропускает. Помогает цикл, который щупает `curl https://uploads.github.com`
  каждые несколько секунд и запускает `gh release upload` сразу после ответа. Файл в 346 МБ прошёл в одно такое окно
- Пока идёт компиляция, журнал молчит десятками минут (`compile-src` в машине занял 73 минуты против нескольких минут на маке).
  Признак жизни — рост процессорного времени `QEMULauncher` на хосте (`ps -o time -p <pid>`) и процесса `node` в машине; ping в машину не отвечает, порт 22 открыт

**Применение:**
- Перед сборкой проверить `curl -m 10 https://open-vsx.org`; не отвечает — сразу перенести `.build/builtInExtensions` с мака
- Время сборки в машине на 1.25.0: компиляция около часа с четвертью, упаковка около полутора часов, плюс загрузка в релиз

## [замеры] Выпуск 1.26.0: время уходит на загрузку, а не на сборку

**Контекст:** 15.10.2026, релиз 1.26.0, обе платформы с одного мака (Фаза 2 мака и Windows-догон).

**Суть:**
- open-vsx.org отвечал, перенос кэша расширений не понадобился. Сборка в машине: компиляция 24 минуты, приложение 10, установщик 5;
  от запуска `build.ps1` до `BUILD OK` около 40 минут (на 1.25.0 — 73 минуты компиляции и около полутора часов упаковки)
- uploads.github.com отвечал всё время, но сеть отдавала около 110–200 КБ/с: DMG и ZIP мака (645 МБ) ушли за 67 минут,
  файлы Windows (556 МБ) — за 88. Хватило одного `gh release upload` без повторов; цикл с `--clobber` остался страховкой
- Тег пушится в начале Фазы 2 мака, до загрузки файлов, и `build.ps1` клонирует его сразу: Windows-сборка шла параллельно с загрузкой мака
- `wingetPr.sh` однажды оборвался таймаутом `api.github.com` на `git/trees`: ветку в форке скрипт к этому месту ещё не создаёт, повтор прошёл

**Применение:**
- Релиз на два набора файлов планировать по загрузке (около двух с половиной часов при такой сети), а не по сборке
- Windows-сборку запускать, как только тег запушен, не дожидаясь конца загрузки мака

## [грабли] Выпуск 1.27.0: сборка в машине не должна жить в сеансе SSH

**Контекст:** 15.10.2026, релиз 1.27.0; `build.ps1` запущен по руководству через `vssh.sh` в фоне, пока мак грузил DMG и ZIP в релиз.

**Суть:**
- Через полминуты соединение оборвалось (`Connection reset by peer`, `Broken pipe`), и сборка ушла вместе с ним: в машине не осталось ни `node`, ни `git`, журнал кончился на `HEAD is now at …`
- Запуск вне сеанса — `Invoke-CimMethod -ClassName Win32_Process -MethodName Create` с командной строкой `pwsh.exe … -Command "& C:\build.ps1 -Tag vX.Y.Z *> C:\b\build.log"`; сам вызов лучше положить файлом в машину (`launch-build.ps1`), а не собирать из кавычек двух оболочек
- Под Windows PowerShell 5.1 такой процесс умер после первой строки журнала без записи об ошибке; под `pwsh` 7 дошёл до `BUILD OK`. Причину в 5.1 не искали
- Состояние читается из машины: `Get-Content C:\b\build.log -Tail 5`. Журнал в UTF-16, на 76 байтах («node v24… target x64») процесс уже мёртв
- Сверка с 1.26.0 снова чистая: 16 665 файлов, те же имена, список PE и архитектура без изменений
- Загрузка Windows (556 МБ) заняла около 15 минут, мака (645 МБ) — 10; `wingetPr.sh` скачивает 209 МБ установщика ради хеша ещё раз, и при медленной сети это затягивается: хеш того же файла отдаёт GitHub в `digest` ассета

**Применение:**
- Запускать `build.ps1` в машине только вне сеанса SSH, под `pwsh` 7, и опрашивать журнал отдельными короткими вызовами
- Если процессов `node`/`git` нет, а журнал не растёт, сборка умерла — запускать заново: `build.ps1` повторяем, клон и зависимости переиспользуются

## [замеры] Выпуск 1.28.0: сборка за 48 минут, запуск машины упёрся в UTM

**Контекст:** 22.10.2026, релиз 1.28.0, обе платформы с одного мака.

**Суть:**
- `build.ps1` вне сеанса SSH (`launch-build.ps1` через CIM под `pwsh` 7) дошёл до `BUILD OK` за 48 минут: клон тега и `npm install` меньше минуты,
  компиляция `compile-src` — семь минут, дальше около пятнадцати минут журнал молчит (процесс `node` держит до 7,5 ГБ из лимита 8 ГБ), потом упаковка приложения и `ISCC`
- `utmctl start` и `tell application "UTM" to start virtual machine` отвечали `-1712` (AppleEvent не дожил до ответа), машина оставалась `stopped`, хотя `get name of virtual machines` UTM отдавал.
  Помог перезапуск самого UTM (`osascript -e 'tell application "UTM" to quit'`, затем `open -a UTM`) и повторный `utmctl start`: через двадцать секунд `started`, SSH ответил под именем `VS-WIN`
- `wingetPr.sh` снова оборвался на скачивании 209 МБ ради хеша (`curl: (56) Recv failure`) при том, что загрузка тех же файлов в релиз прошла за минуты: хеш брать из `digest` ассета
  (`gh release view vX.Y.Z --json assets`), копия скрипта без `curl` открыла PR с первого раза
- Сверку с прошлым выпуском делает `release/cmp-win.sh <версия>` (в `Caches/vibeide/release/`): список файлов и таблица PE по `file`, на 1.27.0 она воспроизводит прежний `ref-1.27.0.tsv` байт в байт

**Применение:**
- Перед сборкой — `utmctl status`; не стартует с `-1712` — перезапустить UTM, а не повторять `start`
- Замер состояния сборки — короткий `.ps1`-файл в машине (`vmps.ps1`: процессы, размер и время журнала), а не строка в кавычках двух оболочек: русская локаль ломает разбор
