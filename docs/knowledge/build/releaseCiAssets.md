## [грабли] В релизе 1.29.0 был пустой sbom.json и образы с чужим оформлением (2026-10-28)

**Контекст:** v1.29.0 собран workflow `release.yml` (а не `release-macos.sh`). В релизе нашлось три дефекта.

**1. Пустой SBOM (195 байт, `"components": []`; у v1.28.0 — 4 МБ)**
- Шаг «Generate SBOM» в `release.yml` писал заглушку с пустым списком и класть её в релиз
- Настоящий SBOM делает `sbom.yml`, но только по событию `release: published`
- Первый прогон `sbom.yml` по тегу v1.29.0 отработал честно: «SBOM generated with 1394 components», приложил файл (прогон 40456790255, 27.10)
- Потом `release.yml` перезапускали, пока чинили сборку; каждый прогон заново публиковал релиз и затирал `sbom.json` заглушкой (`overwrite_files` по умолчанию включён), а `sbom.yml` второй раз не запускался
- Сборка без `node_modules` тут ни при чём: причина — две разные реализации одного файла

**Как сделано:**
- `scripts/vibe-sbom.mts` — единый генератор для обоих workflow
- Зависимости берутся из `package-lock.json` (`cyclonedx-npm --package-lock-only`), `node_modules` и `npm install` не нужны
- Версия `@cyclonedx/cyclonedx-npm` закреплена (6.0.1)
- Меньше `MIN_NPM_COMPONENTS` (100) компонентов — скрипт падает, пустой SBOM больше не публикуется
- Тест `scripts/vibe-sbom.test.mts`; проверено на каталоге только с `package.json` и `package-lock.json`: 1515 компонентов
- Из `sbom.yml` убраны `npm install --ignore-scripts` и дублирующий Python

**2. Имена образов без версии (`VibeIDE-darwin-arm64.dmg`)**
- Так называет файл апстримовый `build/darwin/create-dmg.ts`; версию он не знает
- Теперь образ собирается сразу под именем `VibeIDE-<тег>-darwin-<arch>.dmg`, как ZIP и остальные пакеты того же CI-релиза (тег с `v`)
- Локальные `release-macos.sh` и `release-windows.ps1` называют файлы без `v` — расхождение осталось, на манифест не влияет (`release-manifest.json` берёт имя из файла)

**3. Образ 1.29.0 открывался окном «VS Code» с фоном апстрима (`#HAPPY_CODING!`)**
- Причина: CI-задача macOS звала `create-dmg.ts` (dmgbuild, стоковый фон и том «VS Code»), а наш `scripts/build-dmg-macos.sh` — только `release-macos.sh`
- Теперь CI зовёт `scripts/build-dmg-macos.sh`: том «VibeIDE», фон `build/darwin/dmg-background.svg` с версией, раскладка и гейты проверки образа
- Заодно CI-задача больше не отдаёт приложение с испорченной подписью: версия в `Info.plist`, строка про микрофон и подпись вынесены в `scripts/finish-macos-app.sh`, его зовут и CI, и `release-macos.sh`
- Страж `scripts/dmg-single-path.test.mts` (идёт первым шагом перед сборкой образа) падает, если `release.yml` или `release-macos.sh` вызовут `create-dmg.ts`
- Сам `create-dmg.ts` и стоковые фоны не удалены — это файлы апстрима, нужны для слияний

**Проверено:** `build-dmg-macos.sh` на готовом `VibeIDE.app` 1.29.0 — образ собран, внутренние гейты прошли (фон по sha256, версия, раскладка), том смонтировался как `/Volumes/VibeIDE` с `.background`, `Applications`, `VibeIDE.app`. `finish-macos-app.sh` на копии приложения — версия записана, подпись переставлена.
**Не проверено:** сам CI-прогон (`brew install librsvg` и venv на раннерах `macos-15-intel` / `macos-latest`, `sbom` на `ubuntu-latest`) — workflow проверен только `actionlint`.

## [релиз CI] CI не публикует релиз сам: черновик или долив недостающего

**Контекст:** v1.29.1 — Linux x64 собрался в CI, но в релиз не попал: шаг публикации ждал успеха всех платформ, а упали macOS и Linux arm64.
Тот же шаг при зелёных задачах выпустил бы релиз сразу опубликованным, с автоматическим ченджлогом вместо наших нот — в обход двухфазного выпуска.

**Суть:** шаг `release` идёт при любом исходе сборок, если собрался `compile`, и выкладывает то, что есть.
Релиза тега нет — создаёт **черновик** (`gh release create --draft`), опубликует его владелец после проверки.
Релиз есть — только доливает файлы, которых в нём нет, по имени: ноты и уже выложенные локальные сборки не трогает.
`release-manifest.json` и `checksums-sha256.txt` в чужой релиз не идут: они посчитаны по файлам CI, а не по выложенным.
Linux arm64 собирается на `ubuntu-24.04-arm`: кросс-сборка на x64 падала на линковке `native-keymap` — `cannot find -lX11`, `-lxkbfile` (arm64-версий библиотек на машине нет).

**Применение:** порядок выпуска прежний — локальная Фаза 2 создаёт релиз и тег, push тега запускает CI, CI доливает Windows и Linux.
Проверить логику долива без релиза — тот же скрипт в `docker run bash:5` со списком имён из `gh release view <тег> --json assets`; системный bash macOS 3.2 не знает `globstar`.

## [дефект→фикс] Три удара по linux-сборке v1.31.3: анонимные лимиты GitHub и протухшие checksums (22.11.2026)

**Контекст.** Релиз v1.31.3 упал на `Build Linux (x64)` дважды подряд, третий прогон — зелёный. Оба падения — анонимные обращения к GitHub из CI, оба лечатся закреплёнными правками.

**Суть.**
1. **429 от raw.githubusercontent.com → deb-пакет.** Апстримный `build/linux/debian/calculate-deps.ts` качает `dpkg-shlibdeps.pl` через curl БЕЗ `--fail`: тело 429 писалось в `.pl`, perl падал с «syntax error near "429:"». Фикс `0e002043271`: `--fail --retry 5 --retry-all-errors` + проверка, что файл начинается с `#!`.
2. **403 от api.github.com → sysroot.** `install-sysroot.ts` качает sysroot через API анонимно (60/ч на IP раннера; ubuntu-latest — общий пул). В workflow `GITHUB_TOKEN` передавался только в `Install dependencies`, а в `Prepare .deb`/`.rpm` — нет, хотя скрипт токен читает. Фикс `6cc3390958b`: env `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` в оба prepare-шага (с токеном 5000/ч).
3. **Протухшие checksums при повторных прогонах.** Публикатор доливает только недостающие имена, а `checksums-sha256.txt`/`release-manifest.json` выкладываются ТОЛЬКО при создании релиза → после rerun'ов суммы от первого прогона не покрывают долитые пакеты. Плюс deb/rpm имена включают сборочный таймстамп → каждый rerun создаёт ДУБЛИ пакетов (дедуп имён их не ловит). Фикс `7cb1de6c078`: own_extras перезаписываются `--clobber` под стражем «релиз после долива состоит ровно из файлов этого прогона» (смешанный релиз с локальными сборками не трогаем). Дубли после rerun — удалять руками (`gh release delete-asset`).

**Применение.** Падение linux-сборки v1.31.4+ с «syntax error near ...» или «403 api.github.com» — rerun (правки закреплены); если упало на чём-то новом — проверять, какие сетевые вызовы в шаге анонимны. После любого rerun'а Release Build: сверять состав активов (дубли по таймстампу) и перегенерированность checksums.
