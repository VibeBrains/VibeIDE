## [дефект→решение] Перезагрузка окна запускала каждый MCP-сервер второй раз (2026-09-23)

**Контекст:** владелец поймал это живьём на dev-стенде. После «Разработчик: Перезагрузить окно» у главного процесса стало по два процесса заглушки и `vibememory-mcp`. В установленной 1.22.0 под одним главным процессом висело пять `vibememory-mcp`, запущенных за два дня.

**Причина:**

- Клиенты MCP живут в главном процессе, один набор на всё приложение. Окно же считало дифф «добавлено / убрано / изменено» по своему состоянию.
- Перезагруженное окно начинает с пустого состояния. Для него каждый работающий сервер — «добавленный».
- Главный процесс диффу верил: для «добавленного» создавал нового клиента и перезаписывал запись, не закрыв прежнего. Старый процесс оставался жить, и на `tools/list_changed` отвечали оба.

**Тем же разбором найдено ещё пять дефектов** (исправлены все):

- включение сервера создавало клиента, но не запоминало его: процесс-сирота, а вызов инструмента падал с «Client for server X not found»;
- окно ставило `isOn: true` всем «добавленным», поэтому выключенные серверы включались после каждой перезагрузки окна;
- выключенный сервер всё равно запускался и только помечался «offline», а его инструменты уходили модели;
- если процесс поднялся, а подключение или список инструментов упали, клиент не закрывался;
- любая правка `mcp.json` перезапускала все серверы, а при двух окнах — дважды.

Побочный симптом той же утечки: HTTP-сервер после перезагрузки окна падал в «конфликт портов», потому что адрес держал старый клиент.

**Решение:**

- Окно больше не считает, что изменилось. Оно шлёт `syncMCPServers` с полной картиной:
  - записи после Config Guard, найденный сервер памяти тоже;
  - включённость по сохранённым настройкам;
  - свою настройку MCP Apps.
- Главный процесс сверяет картину с реально работающими клиентами. Чистая часть — [`common/mcpReconcile.ts`](../../../src/vs/workbench/contrib/vibeide/common/mcpReconcile.ts): по паре «известно — нужно» решает `keep` / `start` / `restart` / `off` / `remove`.
- Сравнивается отпечаток запуска: ключи записи отсортированы, без `tools`, плюс возможность MCP Apps. `tools` — фильтр окна, процесс сервера его не видит, поэтому правка списка сервер не перезапускает.
- Синхронизации и переключения идут очередью, по одной. Два окна, синхронизирующиеся одновременно, иначе запустили бы один сервер дважды.
- Переключатель — та же сверка, но по одному серверу.
- Переключение, сделанное за сессию, сильнее вида окна: каждое окно читает настройки один раз при старте, и другое окно может держать состояние до переключения.
- «Новый» и «убранный» для сохранённого вкл/выкл окно считает по сохранённому состоянию, а не по своему списку.
- MCP Apps объявляется, пока настройка включена хотя бы в одном окне. Голос окна снимается при отключении его IPC-соединения.
- Закрытие окна серверы не гасит: они общие, `mcp.json` у приложения один. При выходе из приложения клиенты закрываются штатно.

**Грабли:**

- **Хук завершения нельзя регистрировать в хранилище канала.** `CodeApplication` в самом раннем обработчике `onWillShutdown` освобождает всё, что передал каналам. Эмиттер пропускает слушателя, снятого во время рассылки, и клиенты не закрывались бы никогда. Подписка сделана `Event.once` без регистрации. Проверено: до правки строки «Closed MCP server vibememory» при выходе не было, после — есть.
- **Стенд — только после полной компиляции.** Точечная транспиляция изменённых файлов поверх старого `out/` дала при загрузке окна «does not provide an export named»: свежие и старые модули разошлись. `npm run compile` на этой машине — 4 минуты 20 секунд.
- **Настройки окна пишутся целиком** (найдено чтением кода, живьём не воспроизводилось). Окно читает настройки один раз при старте и, сохраняя любую из них, записывает своё состояние полностью, включая вкл/выкл серверов. Внутри сессии MCP от этого защищён: главный процесс помнит переключения. Но окно с устаревшим видом, сохранив потом что угодно, перепишет и сохранённое вкл/выкл, и после перезапуска IDE сервер вернётся в прежнее состояние. Проблема шире MCP — пункт в roadmap.

**Проверено живьём** — dev-стенд, подставной stdio-сервер и `vibememory-mcp`, процессы считаются `pgrep -P` от главного:

- перезагрузка окна — те же PID, повторного запуска нет;
- выключение — процесс сервера вышел;
- перезагрузка с выключенным сервером — не запустился, в карточке серый;
- включение — ровно один новый процесс;
- второе окно — те же PID, в новом окне оба сервера зелёные;
- закрытие второго окна — оба живы;
- правка записи заглушки — перезапущена только она;
- удаление записи из `mcp.json` — сервер закрыт;
- выход из приложения — клиенты закрыты штатно.

**Не проверено:** вызов инструмента после включения (нужна модель), HTTP- и SSE-серверы, Windows.
