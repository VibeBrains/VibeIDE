## [архитектура] Каталог встраивается в сборку, проект говорит только разницу (2026-09-23)

**Контекст:** каталог примет машинного письма (`slop/catalog.jsonc`, 64 правила, русская и английская части) живёт в общем наборе `.vibe` VibeBrains. VibeIDEA читает его своим детектором на Kotlin; VibeIDE получил порт того же детектора на TypeScript (`common/textSlop/`).

**Суть:**
- Каталог в `products.json` адресован пустому списку и **не засевается**: засеянная копия заморозила бы сегодняшние списки, как засеянный файл базового языка замораживает формулировки. Генератор `scripts/gen-slop-catalog.ts` встраивает сырой JSONC в `common/slopCatalog.generated.ts`: в шапке каталога едет лицензия MIT английской части (misbahsy/anti-ai-slop).
- Проект держит только разницу — `.vibe/slop.json` (засевается обоим продуктам). Сервис `common/textSlop/vibeTextSlopService.ts` читает его при каждой проверке: правка действует сразу, вотчер не нужен. Каталог сборки компилируется один раз.
- Поверхности: инструмент `vibe_text_slop_check` (имя и аргументы VibeIDEA — навык `anti-slop` зовёт его по имени), правило дизайн-детектора `copy-slop` (только лексические виды — ритм и частоты ничего не говорят об одной кнопке), роли только для чтения.
- Ответ инструмента — слово в слово формат VibeIDEA (`common/textSlop/slopRender.ts`): навык описывает ответ, и один навык не может описывать два разных.

**Применение:** правка каталога — в VibeBrains, потом бамп указателя и `npm run gen:all`. Своя копия каталога в продукте запрещена по той же причине, по которой разъехались `marketing-filler` и `marketing-promise`.

## [квирк] `\w`, `\d`, `\b` в JavaScript видят только ASCII (2026-09-23)

**Контекст:** VibeIDEA компилирует шаблоны с `UNICODE_CHARACTER_CLASS` — там `\w`, `\d`, `\b` понимают все письменности. В JavaScript они ASCII даже с флагом `u`.

**Суть:** правило проекта `\bсинерги\w*` в VibeIDEA находит «Синергия», в VibeIDE без перевода — ничего и молча. В shipped-каталоге `\b` и `\w` стоят только в английских правилах, поэтому каталог расхождения не показывал; ловушка — в правилах проектов. `unicodeClassesOf` в `slopCatalog.ts` переписывает классы вне скобок (`\w` → `[\p{Alphabetic}…\p{Pc}]`, `\b` → пара lookaround-ов), внутри скобок — только `\w` и `\d` (`[\b]` там — backspace). Класс начинается и кончается property-escape: рядом с `-` раскрытие остаётся ошибкой, как сам `\w`, а не становится диапазоном.

**Применение:** конструкции, которых нет в JavaScript (`*+`, `(?>…)`, `(?i)`, `\A`, `\Q…\E`, `[a-z&&[^b]]`, `\p{IsCyrillic}`), не компилируются, и правило отбрасывается с предупреждением. Переносимая запись письменности — `\p{sc=Cyrillic}`. Это написано в `docs/manuals/slopSpec.md`.

**Цена:** раскрытый `\b` дороже ASCII-версии. Замер: документ 168 КБ — около 0,2 с в обоих вариантах; 600 фрагментов страницы — 68 мс против 55. Детектор работает в окне примерно за миллисекунду на килобайт, поэтому инструмент не берёт файл больше 1 МБ (`limits.size` при чтении) и текст длиннее миллиона знаков: лог с расширением `.md` держал бы окно секундами.

## [квирк] Переводы строк Windows ломали фронтматтер (2026-09-23)

**Суть:** детектор ищет фронтматтер, абзацы и номера строк по `\n`. Файл с CRLF читался бы с фронтматтером как прозой: `title: Стоит отметить` давал находку на строке 2. Нормализация — в начале `analyzeTextSlop`, а не у вызывающего: так её получают все поверхности. Позиции находок относятся к тексту с `\n`.

**Применение:** у VibeIDEA была та же проблема — `FRONTMATTER` требовал `\n`, MCP-инструмент читал файл сырым. Их прогон вектора это подтвердил (по их словам — `2:8 [RU-W2]` на строке фронтматтера, счёт 80 вместо 85), исправлено так же — нормализацией `\r\n?` на входе `TextSlop.analyze` (VibeIDEA `4fdea49463`, 24.09).

## [правило] Контракт двух движков — общие векторы, а не два теста (2026-09-23)

**Суть:** `testVectors/textSlop.json` в наборе (29 кейсов: все поведенческие случаи `TextSlopTest.kt` VibeIDEA — 16 тестов из 18, плюс CRLF, `\b`/`\w` по кириллице и ничья по весу; два оставшихся теста — каталог без предупреждений и навык, проходящий свой детектор, — проверяют сборку продукта и остались тестами каждого продукта). Кейс сверяет только названные поля (`findings`, `has`/`lacks`, `matches`, `density`, `deductions`, `warnedAbout`…), поэтому рост каталога не ломает векторы, а расхождение движков — ломает. VibeIDE гоняет их в `test/node/textSlopVectors.test.ts` на вшитом каталоге, VibeIDEA — в `TextSlopVectorsTest` (с 24.09; 29 из 29 — их прогон, нашим не сверено).

**Новое поле в векторах — договорённость с соседом:** тест VibeIDEA падает на незнакомом поле (в файле, в кейсе, в ожидании) и на `version`, отличной от 1. Добавил поле в `testVectors/textSlop.json` — положи хендофф VibeIDEA или подними `version`. Сверка у них: `blocking` — как множество, `findings` и `matches` — точный список в порядке текста, `warnedAbout: []` — предупреждений нет вовсе, числа — с точностью 1e-9.

**Грабли при переносе:** в кейсе «битое правило» рабочее правило искало `синерги*` — то же слово, что и каталожное `RU-W1` того же веса. Дедупликация оставляет одну находку, при ничьей — каталожную (порядок правил: каталог, потом свои; сортировка устойчивая, в обоих продуктах одинаково). Исходный тест проверял только, что правило скомпилировалось; вектор проверяет находку — пришлось взять слово, которого в каталоге нет. Ничья теперь закреплена отдельными векторами и описана в спеке.

**Применение:** таблицы правил и весов в `docs/manuals/slopSpec.md` сверяет с каталогом `test/node/slopSpecTables.test.ts` — правило без строки в спеке не пройдёт сборку. У VibeIDEA с 24.09 таблицу стережёт `SlopSpecTableTest` — id, язык, вес, имя в обе стороны и фраза «Всего правил».

## [грабля] Пара «path или text» объявлялась обязательной целиком (2026-09-24)

**Суть:** схему инструмента для модели строит главный процесс: параметр, чьё описание не начинается с «Optional», попадает в `required`. У `vibe_text_slop_check` оба параметра ушли обязательными, и модель, послушная схеме, слала бы и путь, и текст. Юнит-тесты это не видят — только тело запроса. Нашёл живой смоук: заглушка OpenAI-совместимого провайдера записывала запросы, в теле стояло `"required": ["path", "text"]`. Теперь оба описания начинаются с «Optional — give this or …», а «хотя бы один» проверяет `validateParams`.

**Применение:** список инструментов собирает главный процесс (`aiSdkAdapter.ts`, вызов `availableTools`), поэтому правка описания инструмента видна на стенде только после перезапуска всего приложения — «Перезагрузить окно» главный процесс не трогает.

## [правило] Переименованное правило дизайна — через канонический id (2026-09-23)

**Суть:** `marketing-filler` (23 слова) заменён правилом `copy-slop` по общему каталогу. Проекты могли принять старый id в `.vibe/design/design.md`; `marketing-promise` — прежний id того же правила у VibeIDEA, а папка `.vibe` общая. `canonicalRuleId` в `ruleIds.ts` отображает оба на `copy-slop`, и параметр `canonical` у `acceptedDriftFor` и `unknownAcceptedDrift` **обязательный**: с умолчанием «как есть» вызывающий мог забыть переименования, и доктор назвал бы принятое правило опечаткой.

## [открыто] Регулярка из `.vibe/slop.json` может подвесить окно

**Суть:** проектные правила вида `regex`/`density` — шаблоны из репозитория, возможно чужого. Шаблон с катастрофическим возвратом (`(a+)+$`) на длинном тексте блокирует поток окна на время проверки: инструмент и дизайн-замер выполняют детектор синхронно. У VibeIDEA тот же риск на Java. Пункт заведён в roadmap.

**Связано:** [../ui/designReview.md](../ui/designReview.md) (детектор дизайна, правило `copy-slop`), [../vibeDotfolder/sharedSeedContract.md](../vibeDotfolder/sharedSeedContract.md) (общий набор, адресация файлов продуктам).

## [дефект→решение] 2026-09-24 — регулярка проекта вешала окно

`.vibe/slop.json` приходит с репозиторием, возможно чужим, а детектор работал синхронно в окне: и инструмент
`vibe_text_slop_check`, и правило страницы `copy-slop`. Регулярку JavaScript на её потоке не прервать.

**Замеры** (M-серия, node): `(a+)+$` удваивает время на символ — 20 символов 75 мс, 26 — 0,8 с, дальше секунды и
часы. Встроенный каталог на тексте в 1 МБ — 2,8 с сам по себе: окно замирало и без злой регулярки.

**Решение.** Весь детектор — в веб-воркере (`common/textSlop/textSlopWorker.ts`, точка входа `textSlopWorkerMain.ts`,
прописана в `build/buildfile.ts`, `build/gulpfile.vscode.ts`, `build/next/index.ts`). Сервис — `browser/vibeTextSlopService.ts`:
у воркера бюджет `vibeide.textSlop.checkTimeoutMs` (20 с), по истечении клиент воркера закрывается — это `terminate()`,
следующая проверка получает новый воркер. Распорядитель `slopWatchdog.ts` (чистый, тест с подставным исполнителем):

- не уложилась полная проверка — спрашивает встроенный каталог отдельно
- правила проекта прогоняет по одному; зависшие называет в предупреждении
- проверяет каталог проекта без них — честные правила проекта продолжают считаться
- не уложился даже встроенный каталог — «текст не проверен», не «чисто»

Худший случай с одним зависшим правилом — два бюджета. На окне `.vibe/slop.json` только разбирается ради id правил —
ни один шаблон там не компилируется и не выполняется.

**Правило страницы** получает готовые находки по текстам (`IVibeTextSlopService.pageFindings`), а не каталог: правила
дизайна синхронные и чистые, а считать им находки на окне — то же зависание.

**Грабли стенда:** настройку в `settings.json` стенда под `/Volumes` окно не перечитывает (наблюдатель файлов там
не работает) — после правки перезагрузить окно (⌘R), см. `testing/liveSmokeStand.md`.

**VibeIDEA** держит тот же риск; ей передан приём для JVM — `CharSequence`, чей `charAt` проверяет дедлайн.
