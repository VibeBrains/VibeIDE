# Сверка файла перед применением правки агента

**Домен:** toolSystem · **Заведено:** 2026-08-10 · **Ветка:** `next`

Дополняет [[editSafety]] — там пре-флайты «сначала прочитай» и truncation-guard.

**Происхождение:** это один из трёх векторов, спасённых из мёртвого кода базы форка по правилу
«раскопки перед удалением» ([[inheritedPrototypes]], 2026-07-15). Тогда идею записали, а код удалили;
сегодня она реализована с нуля. Сбор quick-fix'ов оттуда же закрыт следом ([[quickFixRepairLoop]]);
третий — роутер на журнале исходов — ещё открыт.

## Что закрывает

«Читал ли модель этот файл» ничего не говорит про окно **между** чтением и записью. А в этом окне
человек печатает в редакторе, второй агент правит тот же файл, сборка его перегенерирует,
`git checkout` меняет ветку. Дальше два исхода, и худший — тихий:

- SEARCH не совпал → громкая ошибка, модель перечитает. Это ещё повезло.
- SEARCH совпал, но строка теперь значит другое → правка ложится поверх чужого изменения молча.

## Механизм

При чтении запоминается `{ hash, source }`, при записи — сверяется.

**Хэшируется весь файл, а не отданная страница.** `read_file` пагинирует, но `edit_file` применяется
ко всему файлу: изменение вне прочитанного куска ровно так же ломает правку.

**`source` (`buffer` | `disk`) — не украшение.** Файл с несохранёнными правками отличается от своей
копии на диске по определению. Проверка, которая сравнивала бы буфер с диском, отказывала бы на
каждом открытом грязном файле — это и есть ложное срабатывание, о котором предупреждала исходная
формулировка задачи (`isDirty`). Поэтому сравниваются только однородные чтения, а смена источника
докладывается отдельным вердиктом `source-changed`: равные хэши через границу источников ничего не
доказывают про вторую сторону.

**Подпись обновляется после каждой успешной записи** — в четырёх точках: чтение, создание файла
(пустое содержимое), `rewrite_file`, применённый `edit_file`. Без этого цепочка `edit → edit` по
одному файлу блокировала бы сама себя со второго шага.

**При расхождении базлайн сбрасывается.** Повтор упирается в «сначала прочитай», а не в ту же
ошибку — модель получает одну и ту же инструкцию обоими путями.

Хэш — `StringSHA1` из `base/common/hash.ts`: синхронный, без обращения к `crypto.subtle`. Для
детекции гонки этого достаточно; криптостойкость здесь не требуется, задача — заметить изменение.

## Грабли

- **`blocksApply(verdict)` не сужает тип** — TypeScript не выводит поля `from`/`to` через функцию-
  предикат над union'ом. Сообщение ветвится по `verdict.kind`, а не по результату хелпера.
- **Порядок гейтов важен.** Сверка стоит ДО `invalidateExistenceCache` + `initializeModel`: после
  них модель уже наша, и источник сменился бы на `buffer` нашими же руками.
- Нормализация переводов строк обязательна с обеих сторон (`getValue(LF)` и `replace(/\r\n/g,'\n')`),
  иначе на Windows подпись расходилась бы на ровном месте.

## Не проверено

Живой прогон «агент прочитал → файл изменили снаружи → агент пишет» на dev-IDE не делался —
только юнит-тесты чистого ядра и компиляция. Пункт заведён в roadmap.
