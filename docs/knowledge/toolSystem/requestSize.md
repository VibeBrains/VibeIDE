## [решение] Схемы, ссылки правил и индекс навыков — у каждого свой предел (20.11.2026)

**Контекст:** встроенный агент на kimi/k3.1-pro стабильно получал HTTP 500, индикатор контекста при этом показывал 14%.
Записка с чужой машины: тело упавшего запроса 558 КБ, в `tools[]` 221 схема на 228 474 символа, системный промпт 158 973 символа.

**Что подтвердилось кодом:**
- Схемы всех инструментов всех MCP-серверов в статусе `success` уходили в каждый запрос агента: `availableTools()` в `common/prompt/prompts.ts`, вызов в `electron-main/llmMessage/aiSdkAdapter.ts`
- Два сервера vibememory дают по 35 схем, около 40 КБ каждый
- Отложенной загрузки не было: `getMCPToolsDeferred` в `electron-browser/mcpService.ts` никто не вызывал, инструмента `MCPSearch` в реестре не было
- Файлы по ссылкам из правил (`<referenced_files>`) встраивались в каждый запрос целиком до 20 файлов и 256 КБ: эти пределы задуманы защитой от отказа, а не бюджетом
- Индекс навыков ограничивал описание навыка 600 символами, но число навыков — ничем
- Ошибка 5xx не знала размера запроса
- Выключить личный MCP-сервер в одном проекте можно было только копией записи с токеном в проектный `mcp.json`: проектная запись заменяет личную целиком

**Что не подтвердилось:**
- «151 собственный инструмент IDE»: в реестре 50 встроенных, в режиме агента 49, вместе 51 348 символов (замер `JSON.stringify({name, description, parameters})`)
- Остальные около ста схем — другие MCP-серверы той машины; без дампа не проверить
- «Скелет системного промпта 126 КБ»: постоянная часть в коде около 9 КБ; остальное — пользовательские данные, вероятнее всего файлы по ссылкам из правил
- «Индикатор CTX вводит в заблуждение»: при окне k3.1-pro в 1 048 576 токенов около 147 тыс. токенов запроса — честные 14%, калибровка по настоящим `promptTokens` схемы учитывала
- Провайдер упал задолго до заполнения окна: предел тела у апстрима не связан с окном модели
- «История растёт монотонно»: сжатие старых результатов инструментов и сводка старых сообщений уже были

**Решение:**
- Отложенная загрузка схем — `common/prompt/toolDeferral.ts`, инструмент `tool_search`, настройки `vibeide.agent.toolSearch` (`auto`/`always`/`off`) и `vibeide.agent.toolSearchThresholdChars` (60 000)
- Порог по размеру схем, а не по числу инструментов: упал размер тела, а встроенные 51 КБ без MCP откладывать незачем
- Откладывание идёт порядком жертв бюджета `maxTools` (`sacrificeOrder` в `toolBudget.ts`): сначала MCP, потом встроенные с конца реестра, ядро `CORE_TOOL_NAMES` никогда
- Имена отложенных модель видит блоком `<deferred_tools>`, иначе выдумывает имена
- Загруженные имена выводятся из сообщений разговора (`loadedToolNamesOfMessages`): вызванный инструмент и всё, что вернул `tool_search`
- Промпт и запрос считают их одной функцией, иначе модель прочла бы один список, а получила другой
- Откладывание включается только у вызывающего, который передал загруженные имена (основной чат, субагенты): без них загрузка через `tool_search` не дошла бы до запроса
- Разбор XML-вызовов и подсказки имён в ошибках видят все инструменты, включая отложенные
- Бюджеты в промпте: `vibeide.projectRules.maxLinkedChars` (20 000) для файлов по ссылкам — файл встраивается только целиком, остальные списком путей; `vibeide.skills.discoveryMaxChars` (12 000) для индекса навыков — сверх него только имена
- Оценка контекста прибавляет отданные схемы одинаково ко всем бюджетам и к сырой оценке для калибровки: иначе множитель калибровки уехал бы
- Ошибка 5xx несёт хвост `Request ≈ N KB, tool schemas ≈ M KB.`, карточка переводит его и при теле от 200 КБ подсказывает, что делать
- Хвост считается только при ошибке: `JSON.stringify` сообщений с картинками — мегабайты работы, на каждый запрос она не нужна
- Правила целиком не превращены в сводки: правило без условий — воля человека «всегда в силе», а режим «по запросу» у `.mdc` уже есть

**Грабли: MCP-клиенты общие для всех окон**
- Клиенты живут в главном процессе (`electron-main/mcpChannel.ts`), а запущенное — объединение картин окон (`common/mcpReconcile.ts`)
- Первая версия выключателя «в этом проекте» слала проектное значение через `toggleMCPServer`, который пишет общий для всех окон `_isOnOfName`
- Окно, где сервер выключен, гасило бы его соседнему окну, которому он нужен
- Правильно: переопределение едет в картине окна (`MCPSyncParams.workspaceOverrideOfName`), сервер работает, пока включён хотя бы для одного окна (`isMCPServerWantedByAnyWindow`)
- Окно, где он выключен, только не отдаёт его инструменты агенту
- Глобальный переключатель после записи запускает полную сверку, а не действие над одним сервером: иначе он не увидел бы окон с переопределением «включён»
- Карта переопределений хранится в рабочей области; `mcp.json` не меняется, его формат общий с VibeIDEA

**Ограничение:** кандидатов `tool_search` берёт по глобальному режиму чата, а не по режиму конкретного субагента. В субагенте режима `gather` он может назвать загруженным инструмент, которого этот режим не отдаёт.

**Не проверено:** живой ход агента с `tool_search` — в dev-профиле нет модели с деньгами и нет локальной модели.
