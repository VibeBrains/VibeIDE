## [охват] SneakPeek в Claude Code Desktop — чем он отличается от нашего превью

**Контекст:** разбор дайджестов 15–21.10.2026 ([DIGEST-1021](../../roadmap.md)); уязвимость раскрыта Noma Labs 14.10.2026
(CSO Online, Dark Reading, Cybernews через поиск; devops.com отдал 403).

**Что было у Anthropic:** автоматическое превью HTML в Claude Code Desktop. HTML до 256 КБ превращали в `data:`-URL
под строгой политикой безопасности контента (скрипты запрещены); файл больше порога писали на диск и открывали по `file://`
— без политики и с прямым доступом к файловой системе.
Репозиторий с «отчётом о покрытии» на 256+ КБ читал ключи SSH, облачные токены и kubeconfig, потому что скрипт в нём
выполнялся при открытии превью.
Оценка Anthropic по CVSS v4.0 — 8,7, полное исправление вышло в Claude Desktop 1.30096.1 (17.08).

**Что у нас:** встроенный браузер превью (`browser/vibeServer/vibeBrowserManager.ts`) — веб-вью с рамкой `<iframe>`
под нашей панелью. Адресная строка нормализует ввод до `http(s)` или пути от своего origin (`normalize`), автопревью
файла по `file://` нет. Значит прямого аналога SneakPeek нет.

## [находка] Но страница в рамке разговаривает с хромом без проверок

Мост страницы к панели — `window.postMessage` с полем `__vibeBrowser` (инжект-скрипт, `common/vibeServer/injectReloadScript.ts`).
По коду на 21.10.2026:
- `<iframe id="vb-frame" src="…">` — **без атрибута `sandbox`**
- слушатель `message` в хроме не сверяет ни `ev.source` (рамка это или вложенный фрейм страницы), ни `ev.origin`
- `external` → сообщение `open-external` с `href` из страницы → `_openerService.open(URI.parse(href), { openExternal: true })`;
  в `editor/browser/services/openerService.ts:136` при `openExternal` схема не проверяется. Что режет слой main —
  не смотрел
- `inspect` (селектор и фрагмент HTML, до чата) и `console` (текст, в журнал консоли, которую читает агент) — тоже от
  страницы. Проходят ли они через `VibePromptGuardService`, не проверял
  ([promptGuardCoverage.md](promptGuardCoverage.md): охранник стоит на файлах, правилах, веб-инструментах и MCP, а превью в списке нет)
- `{type:'navigate', url}` от страницы срабатывает тем же слушателем и ставит `frame.src` как есть: `goto(u)` не зовёт
  `normalize` (он только у адресной строки). Как Chromium ведёт себя с `file:`, `data:` и `javascript:` в рамке веб-вью,
  я не проверял, и это оставляет вопрос открытым

**Модель угрозы:** dev-сервер проекта, склонированного из чужого репозитория, отдаёт страницу со скриптом. Он может
слать `external` с произвольной схемой и подкладывать текст в `inspect.html` и `console.text`. Живьём не воспроизводилось —
это вывод из кода, не подтверждённая эксплуатация.

**Важное уточнение:** сверка `ev.source === frame.contentWindow` защищает от вложенных фреймов внутри страницы (реклама,
виджеты), но не от самой страницы, которая и есть источник по задумке. Против неё работает только жёсткий приём на
стороне хрома: схема, origin, длина, охранник.

## [решение, не принято] Что сделать

Пункт в roadmap («Мост превью `__vibeBrowser` принимает команды от любой страницы»), польза средняя, трудоёмкость малая:
- `open-external`: только `http`/`https` и совпадение origin с превью; остальное — в журнал без открытия
- `inspect` и `console`: потолок длины, фрагмент HTML и текст консоли — через охранник с рамкой «данные, не указания»
- `message`: для `__vibeBrowser` сверять `ev.source === frame.contentWindow`
- `navigate` от страницы: пропускать через `normalize`, как адресную строку
- `sandbox` на рамке — отдельно: влияние на авторизацию превью через куки
  ([vibeServerPreviewCookies.md](../architecture/vibeServerPreviewCookies.md)) не оценивал, решать с замером
