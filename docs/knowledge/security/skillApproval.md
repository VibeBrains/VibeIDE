## [архитектура] Что одобряется и где стоит гейт

**Контекст:** DIGEST-0911 (2026-09-11), тема «безопасность пакетов skills». До этого одобрения не
было вовсе: `vibeide.skills.sessionActiveIds` — фильтр, а не одобрение, а происхождение сверялось по
одному `SKILL.md`. arXiv 2604.02837: код скрипта в контекст модели не попадает, ей возвращается
только вывод; модель доверия «одобрил один раз навсегда» даёт скиллу права оператора.

**Суть:**
- **Единица целостности — каталог скилла:** все файлы, по содержимому и по именам
  (`skillPackageDigest`: SHA-256 над отсортированными строками «путь, NUL, sha256 файла»). Скилл одним
  файлом (`name.skill.md`) — пакет из этого файла. Вложенный скилл — отдельный пакет со своим
  одобрением. `.git` в пакет не входит.
- **Решение** (`decideSkillTrust`, первое совпадение выигрывает): встроенный в продукт → доверен; нет
  отпечатка → «не проверить» (одобрить нельзя); все файлы совпадают с ревизиями набора → «из
  релиза»; отпечаток совпал с одобренным → «одобрен»; не совпал → «изменился» — с разницей по файлам;
  иначе «ещё не одобрен».
- **Гейт стоит там, где текст скилла доходит до модели:** `convertToLLMMessageService.prepareLLMChatMessages`
  зовёт список скиллов (`getDiscoveryText`), неявные подсказки (`getImplicitSkillRetrievalHints`) и
  раскрытие `/skill:` (`IVibeSlashCommandService.expand`). Список и подсказки показывают только
  доверенные скиллы, неодобренные — одним числом, без имён: имя — это текст автора скилла. Раскрытие
  неодобренного спрашивает модальным окном и по согласию одобряет.
- **Отказ запоминается по версии** (корень пакета + отпечаток) до перезапуска окна.
  `prepareLLMChatMessages` вызывается на запросах к модели в цикле агента (если не сработал кэш
  подготовки сообщений), и без памяти один отказ превращался бы в тот же вопрос на каждом шаге.
- **Одобрения — в `IStorageService` профиля, цель `MACHINE`** (без синхронизации настроек): репозиторий
  не может принести свои, а тот же путь на другой машине указывает на другие байты. Настройка
  `vibeide.skills.requireApproval` — `APPLICATION`: проект выключить требование не может.
- **Изменения ловятся событиями** всех корней: `.vibe/skills`, `.cursor/skills`, `.claude/skills` (раньше кэш
  сбрасывался только для первого) и глобальных — для них заведено `IFileService.watch`. Иначе
  одобренный глобальный скилл, у которого поменялся скрипт, сохранял бы одобрение до перезапуска.
- **Пределы отпечатка** — 500 файлов и 16 МБ (`vibeide.skills.approvalMaxFiles`,
  `vibeide.skills.approvalMaxMegabytes`), вложенность до 8 уровней. Больше — «не проверить»:
  частичный отпечаток ручался бы за файлы, которых никто не хешировал.

**Применение:** любая новая дорога, по которой текст скилла идёт в модель, обязана спрашивать
`isSkillAvailableToModel`. Одобрять — только отпечаток, который человек видел (`approveSkills` берёт
`digest` из показанного списка), никогда не свежий пересчёт: иначе правка, случившаяся между показом
и нажатием, одобрится невиданной.

## [квирк] Происхождение — по всему каталогу

Раньше «из релиза» решалось по `SKILL.md`: скрипт, подложенный рядом со скиллом набора, подписи не
менял. Теперь «из релиза» — только если каждый файл совпадает с какой-то ревизией набора
(`isUntouchedPastRevision`). Скилл набора с лишним или изменённым файлом — «из релиза, изменён» и
требует одобрения.

## [правило] Исполняемые файлы — в окне одобрения, а не всплывающим уведомлением

Config Guard (`skill-executable-files`, medium) называет исполняемые файлы скилла не из релиза: по
расширению, по `#!`, по сигнатуре ELF, PE, Mach-O. Всплывающим уведомлением находка не показывается —
она повторяла бы «у скилла есть скрипты» для каждого скилла со скриптами; её место — диалог одобрения
и команда «Скиллы — проверить и одобрить». Правило `skill-remote-execution` теперь идёт через разбор
строки детектора команд (`findFetchAndRunInText`) — в тексте, в блоках кода и в скриптах, без ложной
тревоги на `| python3 -m json.tool`. Через тот же разбор идёт и `mcp-remote-command`.
