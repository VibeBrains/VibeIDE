## [архитектура] Config Guard: валидация недоверенных machine-config при загрузке

**Контекст:** VibeIDE грузит из (потенциально чужого) воркспейса два machine-config файла, которые управляют сетью и запуском процессов: `.vibe/providers.json` (динамические LLM-провайдеры — `baseURL`, `headers`, `apiKeyEnv`) и `mcp.json` (MCP-серверы — `command`, `args`, `env`, `url`). До Config Guard оба грузились без проверки: подмена `baseURL` уводила весь модельный трафик на чужую инфраструктуру, а `mcp.json` мог запустить произвольный процесс (`curl|sh`, `npx -y`, `--no-sandbox`). Идея и набор эвристик перенесены из AgentShield (победитель Claude Code Hackathon, Feb 2026), но **только узкий срез под реальную поверхность VibeIDE** — остальное уже покрыто `vibePromptGuardService` (prompt-injection/unicode в правилах) и `secretDetection` (секреты в исходящих сообщениях). Дублировать их Config Guard не должен.

**Суть:**
- Чистый модуль детекта — [common/vibeConfigGuard.ts](../../../src/vs/workbench/contrib/vibeide/common/vibeConfigGuard.ts). Без I/O, без VS Code-зависимостей, без чтения конфига → тестируем из `test/common/`. Две функции: `scanProviderConfig(entries)` и `scanMcpConfig(servers)` → `ConfigGuardFinding[]` (`ruleId`, `severity`, `subject`, `message`).
- **13 правил** (provider × 3, mcp × 10):

  | Файл | ruleId | Severity |
  |---|---|---|
  | providers | `provider-endpoint-non-https` | critical |
  | providers | `provider-endpoint-raw-ip` | high |
  | providers | `provider-hardcoded-secret` (baseURL userinfo / header / query литерал) | critical |
  | mcp | `mcp-remote-command` (`curl\|sh`) | critical |
  | mcp | `mcp-shell-wrapper` (`sh -c`) | high |
  | mcp | `mcp-disabled-security` (`--no-sandbox` …) | critical |
  | mcp | `mcp-npx-no-pin` (`-y` / без точной версии: тег и диапазон — не версия, локальный путь — не загрузка) | medium |
  | mcp | `mcp-uvx-no-pin` (`uvx` без точной версии; `-y` у него нет) | medium |
  | mcp | `mcp-env-override-critical` (PATH/LD_PRELOAD/NODE_OPTIONS…) | critical |
  | mcp | `mcp-hardcoded-env-secret` | critical |
  | mcp | `mcp-shell-metacharacters` | medium |
  | mcp | `mcp-url-non-https` | high |
  | mcp | `mcp-url-credentials` (user:pass@) | high |

- **Где НЕ ловит (осознанно):** секреты в исходящих сообщениях (→ `secretDetection`), prompt-injection в правилах (→ `vibePromptGuardService`), серверные правила AgentShield `bind 0.0.0.0` / wildcard-CORS — VibeIDE MCP-**клиент**, он подключается, а не слушает порт. Локальный `http://localhost` / `127.0.0.1` не флагается (легитимный прокси).
- Конфиг: `vibeide.configGuard.enabled` (bool, default `true`), `vibeide.configGuard.mode` (`warn`/`block`, default `warn`) — [common/vibeConfigGuardConfiguration.ts](../../../src/vs/workbench/contrib/vibeide/common/vibeConfigGuardConfiguration.ts). Дефолт `warn` ничего не отключает — это анти-DoS на легитимные proxy-конфиги.
- Точки врезки (скан при загрузке, существующий парсинг не тронут):
  - провайдеры — `reload()` в [browser/vibeDynamicProvidersService.ts](../../../src/vs/workbench/contrib/vibeide/browser/vibeDynamicProvidersService.ts) (`_runConfigGuard`): находки → `state.warnings` + лог; в `block` критичные провайдеры выпадают из transport.
  - MCP — `_refreshMCPServers()` в [common/mcpService.ts](../../../src/vs/workbench/contrib/vibeide/common/mcpService.ts) (`_runConfigGuard`): в `block` критичные серверы вырезаются из конфига до старта.
  - Уведомление — одно консолидированное `INotificationService.warn` на сет находок, дедуп по сигнатуре (`_lastGuardSig`), чтобы правки файла не спамили.
- Диагностика: команда `vibeide.configGuard.showFindings` («VibeIDE: Config Guard — показать находки») — [browser/vibeConfigGuardDiagnosticContribution.ts](../../../src/vs/workbench/contrib/vibeide/browser/vibeConfigGuardDiagnosticContribution.ts). Оба сервиса отдают `getLastGuardFindings()`; команда reload'ит провайдеры и рендерит таблицу по severity в untitled-md.

**Применение:**
- Добавляешь новое правило → пиши его в `scanProviderConfig`/`scanMcpConfig` (чистая функция) + кейс в [test/common/vibeConfigGuard.test.ts](../../../src/vs/workbench/contrib/vibeide/test/common/vibeConfigGuard.test.ts) (срабатывание + «чистый конфиг»). Сервисы и UI трогать не надо — они работают по `ConfigGuardFinding[]`.
- Прежде чем добавить правило про секреты/инъекции — проверь, не покрыто ли уже `secretDetection`/`vibePromptGuardService`. Config Guard — только config-as-code риск.
- `block`-режим включать осознанно: он не активирует провайдер/не стартует MCP-сервер с critical-находкой; для proxy на сыром IP или `http://` это может «отключить» рабочий канал.
- Тест: положить в `.vibe/providers.json` запись с `baseURL: "http://1.2.3.4/v1"` → уведомление Config Guard + строка `[critical]` в логе VibeIDE; команда показывает её в таблице.

**Антипаттерны:**
- Не тащить из AgentShield все 125 правил «на будущее» — большинство мимо поверхности VibeIDE (хуки `.claude/`, серверные bind/CORS, дубли secret/injection). Правило трёх и реальная поверхность, не маркетинговая полнота.
- Не делать `mode="block"` дефолтом — тихий DoS на легитимные конфиги.

**Связано:** [[russianFirst]] (тексты находок — на русском, ruleId — английский идентификатор) · [dynamicProviders.md](../architecture/dynamicProviders.md) · [.vibe/ config](../vibeDotfolder/).

## Граница рабочей области отвечала не на тот вопрос (2026-08-12)

Весь контроль записи агента был построен вокруг одного вопроса: «внутри рабочей области путь или
снаружи». Снаружи — список разрешённых папок плюс `referenceFolders` (читать можно, писать нет).
Внутри — пиши что угодно.

Это оставляло без защиты ровно тот случай, ради которого защита и нужна: папку исходников
**внутри** репозитория. Когда агент собирает страницы знаний из статей, стенограмм и выгрузок,
самое уязвимое место — сам исходник, который он в этот момент читает: перезаписать его нечем было
помешать, а «не трогай эту папку» в промпте остаётся пожеланием, которое подводит в три часа ночи.

Закрыто настройкой `vibeide.agent.sourceFolders` — пути относительно корня рабочей папки,
раскрываются в КАЖДОМ корне многокорневого проекта (раскрытие только в первом молча оставило бы
остальные открытыми — это и есть тот отказ, от которого настройка защищает). Пустые и `..`-записи
отбрасываются: запись, схлопнувшаяся в корень, заморозила бы весь проект.

Отдельный тип ошибки, а не `ExternalAccessRequiredError`: тот означает «спроси пользователя», а
здесь пользователь уже принял решение — спрашивать нечего. Текст отказа называет путь и настройку,
поэтому агент узнаёт границу с первого отказа и не бьётся в неё ходами.

## Привязка к 127.0.0.1 не защищает от браузера (2026-08-12)

У нас три локальных слушателя, и каждый, если до него дотянуться, что-то исполняет: входящий
HTTP API запускает агента, MCP-gateway вызывает инструменты, превью отдаёт файлы. Привязка к
петлевому адресу кажется исчерпывающей защитой — «снаружи не достучаться». Это неверно.

**DNS rebinding:** страница, которую владелец открыл в браузере, резолвит собственный домен в
`127.0.0.1` и шлёт запросы на локальный порт. Сокет при этом честно локальный, запрос идёт из
браузера владельца, и единственная улика — заголовок `Host`, где стоит чужое имя.

Отсюда правило: **сокет проверяем И заголовок `Host` проверяем**, причём `Host` — до всего
остального. У MCP-gateway роль пропуска играет UUID маршрута в пути; порядок проверок важен,
чтобы чужая страница не узнала даже, угадала ли она путь.

Секрет в URL — отдельная слабость, с которой мы пока живём: он утекает в логи, историю браузера
и `Referer`. Полноценный токен на вызов требует согласованно поменять способ, которым адрес
маршрута попадает к MCP-клиентам, — заведено отдельно.

Чистые предикаты живут в `base/common/loopbackAdmission.ts` и переиспользуются всеми
слушателями. Две реализации «локальный ли это запрос» неизбежно разъезжаются, и разъезжается
та, которую никто не тестировал.

## [архитектура] Правило на последовательность: хук судил вызов в вакууме (2026-09-08)

**Контекст:** JetStream Clearance (03.09.2026) авторизует действие агента **до** исполнения и, по их же примеру, ловит эксфильтрацию именно как цепочку: «прочитать карточку клиента → собрать вложение → отправить письмо» законно, а тот же ряд с внешним bcc в конце — нет. Формат правил они не публикуют, движок закрыт.

**Суть:** брать было нечего, кроме самой постановки задачи, — и она вскрыла дыру у нас. `preToolUse` получал `tool` и `params`, `turnEnd` — `changedFiles`, истории вызовов не видел никто. Наша цепочка выглядит как «прочитал `.env` → собрал текст → `run_command` с curl», и **ни один из трёх шагов по отдельности не преступен**; к моменту третьего первые два для хука не существуют.

Лечение — не движок правил, а один аргумент: в payload появился `recent` — до 20 вызовов не старше 30 минут, только имя инструмента, путь-цель и сервер. Правило пишется пользователем на чём угодно, решает по-прежнему код выхода.

Три решения, которые стоило принять сознательно:

- **Что едет.** Имена и пути — да, аргументы и командные строки — никогда: ту же границу уже провёл журнал аудита, и вторая, другая, граница в том же продукте была бы хуже любой из них. У командных инструментов пути нет по той же причине — их «цель» и есть командная строка.
- **`secondsAgo` вместо отметки времени.** Правило спрашивает «это было только что?»; отдай абсолютные часы — и вычитать их будет каждый хук, по-своему.
- **След пишется до проверок включённости и доверия.** След с дырами хуже отсутствующего: правило прочитает «ничего не было» там, где было. Поэтому запись идёт раньше, чем выясняется, есть ли вообще подходящий хук.

**Ложные срабатывания — не теория, а стоимость фичи.** Правило «не запускать команды после чтения секретов» тормозит и честную работу (правка `.env.example`, потом тесты). В спеке хуков поэтому написано прямо: сужать `tools`, сужать окно, начинать с хука, который печатает предупреждение и возвращает `0`, и неделю смотреть, как часто он сработал бы.

## [архитектура] Скилл — единственный чужой артефакт в `.vibe/`, и он едет в модель дословно (2026-09-08)

**Контекст:** Tenable + OpenAI объявили Exchange AI Inspector (03.09.2026) — ревью агентов, скиллов, MCP-серверов и плейбуков **до** деплоя. Какие поля манифеста считаются рискованными — не опубликовано; переносится только сама идея «проверять до запуска».

**Суть:** MCP-серверы Config Guard уже читал (`curl|sh`, `sh -c`, `--no-sandbox`, неприпиненный `npx`, метасимволы, подмена критичных env, секреты, http://), а коллизии имён инструментов закрыты в 1.19.0. Непроверенным оставался ровно тот артефакт, который **приходит от чужих людей по общему стандарту** и попадает в системный контекст без пересказа, — скилл.

`scanSkills` отмечает три вещи, которые трудно списать на случайность: `precheck` за пределами папки скилла (путь к чужому скрипту), ключ вендора в открытом виде (уедет в модель вместе с текстом), инструкции обойти правила пользователя или скрыть от него действие.

**Почему проверок именно три, а не тридцать:** это не контент-фильтр и не может им быть. Гейт, который срабатывает на слово «ignore», выключат за день — а скилл **про** prompt injection писать законно, и тест на это стоит рядом с остальными. Поэтому фразы матчатся узко и императивно («ignore all previous instructions», «действуй без подтверждения»), а вердикт — предупреждение, а не блокировка: молча выброшенный скилл неотличим от скилла, который не работает.

**Применение:** добавляя новый источник текста, который уезжает в модель дословно, спросить, кто его автор; если ответ «кто угодно» — ему нужен свой скан. Дедупликация по `правило+субъект` обязательна: список скиллов пересобирается на каждое изменение файла под `.vibe/skills`, и повтор предупреждения на каждое нажатие клавиши научит игнорировать его — худшее, что может случиться с сообщением о безопасности.

## [правило] Пакет без точной версии: одно понятие «закреплено» для скиллов и MCP (2026-09-11)

**Контекст:** разбор spotify/portal-ai-plugins: в их плагине `shunt` скрипт скилла запускает
`npx --yes @spotify/portal-cli` без версии. У нас такая находка была только для MCP-серверов
(`mcp-npx-no-pin`), а в скиллах связка оставалась невидимой — хотя VibeIDEA её уже ловил
(`SkillCodeScan.unpinnedRunner`).

**Суть:**
- Две новые находки скилла, medium: `skill-unpinned-runner` — `npx`/`uvx` без точной версии в блоке кода
  `SKILL.md` или в скрипте; `skill-unpinned-inline-deps` — зависимость PEP 723 (`# /// script`) без `==`.
  Проза не читается: пакет, названный в предложении, — не команда (так же у VibeIDEA).
- «Закреплено» — только точная версия: `@latest` и `@^1.2.3` — нет; локальный путь (`./tool`, `file:`) — не
  загрузка. То же понятие теперь у MCP-правила: раньше `npx pkg@^1.2.3` в `mcp.json` считался закреплённым,
  а `npx ./local.js` — нет. Отдельным правилом `mcp-uvx-no-pin` закрыт и `uvx` в `mcp.json`: спрашивать
  про `-y` у него нечего, важна только версия.
- Правило перенесено из VibeIDEA и сверено их вектором дословно (`SkillValidatorTest`, `SkillCodeScanTest`).

**Грабля:** регулярка версии Python у VibeIDEA — `v?\d+(\.\d+)*([.-]?[A-Za-z0-9]+)*` — это `(a+)*`: на
почти-версии из чужого скилла (`uvx pkg@1aaaa…!`) перебор удваивается с каждым символом. Замер тем же
шаблоном в node: 18 символов — 1,1 мс, 24 — 62 мс; на 40 это часы. У нас тот же язык записан так, что у
каждого символа один способ совпасть — `^v?\d[A-Za-z0-9]*(?:[.-][A-Za-z0-9]+)*$`; на 13 образцах ответы
совпали, тест на 40 символов проходит мгновенно. VibeIDEA передан хендофф
(`sessions/skill-runner-redos-from-vibeide.md` в их памяти).

**Применение:** правило, общее с VibeIDEA, меняется строкой в векторе обоих продуктов. Регулярка над текстом
из скилла — без вложенных квантификаторов: скилл пишет кто угодно.
