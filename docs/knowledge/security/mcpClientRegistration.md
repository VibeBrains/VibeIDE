# Регистрация MCP-клиента: собственный gateway рождается на CIMD, а не на DCR

> Решение записано 10.09.2026 по итогам разбора дайджеста. Кода сегодня нет — и это часть решения.

## Что у нас есть сейчас

Собственного OAuth-клиента к MCP-серверам у VibeIDE **нет**. Вход выполняется штатным механизмом
редактора: токены живут в защищённом хранилище ОС и продлеваются им же. Наша часть — гигиена:
раз в сутки проверяем сроки годности и предупреждаем (`docs/functional.md`, секция MCP).

Проверено грепом 10.09.2026: слово `oauth` встречается в нашем коде один раз и не по этой теме;
`resource_metadata`, `oauth-protected-resource` и RFC 8707 не встречаются вовсе.

Отсюда прямое следствие: **CIMD, DCR и `resource`-параметр сегодня — забота апстрима VS Code,
а не наша.** Гнаться за спекой в коде, которого нет, значит писать слой ради слоя.

## Что решено на случай собственного gateway

Когда у нашего MCP-gateway появится собственная авторизация, он **регистрируется через Client ID
Metadata Documents и не реализует Dynamic Client Registration**.

Основание — спека MCP от 2026-07-28
([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)):

- серверы авторизации и клиенты **SHOULD** поддерживать CIMD;
- DCR — **MAY**, и прямо назван **устаревшим**, «сохранён для обратной совместимости с серверами
  авторизации, не поддерживающими CIMD»;
- **даты удаления DCR в спеке нет** — проверено, дайджест спрашивал про сроки, их не публиковали.

Что при этом обязан делать клиент, и это надо заложить сразу, а не «потом»:

- `resource`-параметр по RFC 8707 **в обоих** запросах — авторизации и токена;
- Protected Resource Metadata (RFC 9728) как **единственный** путь обнаружения сервера авторизации;
- поддержка **обеих** схем discovery (RFC 8414 и OpenID Connect Discovery);
- валидация `iss` по RFC 9207. Спека прямо предупреждает, что в будущей ревизии требование к
  серверу поднимется со SHOULD до MUST — писать валидацию сразу дешевле, чем возвращаться.

## Как работает CIMD, в двух строках

Клиент использует **HTTPS-URL в качестве `client_id`**. Сервер авторизации распознаёт URL-форму,
скачивает по этому адресу JSON с метаданными клиента и валидирует их вместе с `redirect_uris`.
То есть регистрация заменяется публикацией документа: нет ни POST `/register`, ни выданных
секретов, ни состояния на стороне сервера.

## Следующий слой, который пока не наступил

Роадмап MCP называет **DPoP** («финализируется, продвигаем принятие») и **Workload Identity
Federation** («предпочтительный путь для идентичности и делегирования агентов») —
[roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/). **Конкретных дат нет ни у
того, ни у другого.** Заводить их сейчас не за чем; строка здесь стоит затем, чтобы при
проектировании gateway о них вспомнили до, а не после.
