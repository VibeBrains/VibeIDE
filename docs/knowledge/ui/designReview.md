## [архитектура] Почему правила, а не «спроси модель, красиво ли»

Модель на один и тот же экран отвечает по-разному, не показывает пальцем на элемент и стоит запроса. `common/designReview/designSlopRules.ts` — фасад над правилами поверх снимка того, что страница **реально вычислила**: кегли, цвета, рамки, геометрия, движение. Находка воспроизводима, несёт селектор и измеренное значение, поэтому с ней можно спорить числом.

Каталог — **55 признаков** в семи категориях, по файлу на категорию (`rules/{typography,color,visual,layout,motion,copy,imagery}.ts`): 55 правил в одном файле не читаются и не ревьюятся. Реестр id и классов — `ruleIds.ts`, правила берут id и класс **оттуда** (см. [[designContext]] — пол качества против принятого дрейфа). Фасад ставит класс и метку вьюпорта; сортировка детерминирована, два прогона дают побайтово одинаковый вывод.

Идея и перечень «следов генератора» — из разбора [pbakaus/impeccable](https://github.com/pbakaus/impeccable) (Apache-2.0, v4 на 30.07.2026 — 51 паттерн в 7 категориях). **Код не копировался:** их лицензия не ложится на нашу MIT, а перечень антипаттернов — факты о дизайне, а не код. Наши правила написаны с нуля по описаниям, плюс пять своих, которых у них нет (контраст по WCAG с исключением для крупного текста, выключка, пропуск уровня заголовка, зона нажатия 44px, текст <12px) и два по русской типографике: **висячий предлог** и **одинокое слово на последней строке** — измеряются по реальным строкам через `Range`, потому что разбиение на строки нельзя вывести из исходника (его решают гарнитура, бокс и переносы браузера).

## [архитектура] Как снимок доезжает до правил

Страница превью уже несёт мост для inspect (`common/vibeServer/injectReloadScript.ts`) — сбор снимка добавлен туда же четвёртой ролью: chrome шлёт `__vibeServerDesignScan` (с ярлыком вьюпорта), страница отвечает `__vibeBrowser:"design-scan"`. Дальше `VibeBrowserManager.scanDesign(viewport)` (таймаут 5 с, один запрос за раз) → `IVibeServerService.scanDesign()` → инструмент агента `design_review`.

Снимок описан в `common/designReview/designSnapshot.ts` — это контракт «страница измеряет, правила судят». Кроме кеглей и цветов страница отдаёт рамки по сторонам, радиусы, `backdrop-filter`, `overflow`, `position`/`z-index`, документные координаты, `scrollWidth` против `clientWidth`, тайминги анимаций, атрибуты картинок и результат построчного замера текста. Бюджет: 400 элементов на снимок, 40 элементов на построчный замер (`Range` на каждое слово стоит layout-rect).

**Мобильный проход**: chrome физически сужает iframe до 390px, ждёт кадр + 120 мс на собственный relayout страницы, измеряет и возвращает ширину; страховочный таймер 8 с (больше рабочего таймаута) не даёт превью застрять в телефонной ширине, если страница не ответила.

**Ограничение то же, что у inspect:** мост живёт только в статическом превью. Для dev-server и Docker инструмент отвечает «не измеряли», а не пустым списком — «ничего не найдено» и «ничего не измеряли» обязаны выглядеть по-разному.

## [правило] Ловушки, на которых наступали

- **Полоса показывает остаток, цвет — израсходованную долю.** Передал остаток прямо в `toneColorFor` — полный лимит покрасился красным. Тот же класс ошибки, что в кружке контекста.
- **Границы диапазонов проверять на каноническом образце.** Правило `ai-color-palette` сначала имело диапазон hue 255–285 и **промахивалось мимо `#7C5CFF`** — цвета по умолчанию половины генераторов: у него hue 252. Ловушка вскрылась тестом; граница расширена до 245–290.
- **Свои прикидки чисел не считать фактом.** В тест ожидание hue было записано «на глаз» (254 вместо 252), а серый `#969696` взят как пример «между порогами», хотя он даёт 2.8:1 и проваливает даже порог для крупного текста. Оба ожидания исправлены по факту прогона, а не подгонкой правил.
- **Снимок ограничен 400 элементами.** Это выборка, а не копия страницы; при обрезке инструмент прямо говорит, что видел не всё.
- **Ожидания в тестах — по факту прогона, не по прикидке (рецидив).** В волне 30.07 два новых теста ждали список без `single-font`, хотя фикстуры набраны одной гарнитурой — правило сработало верно, ошибочными были ожидания. Тот же класс промаха, что с hue #7C5CFF: сперва прогон, потом ожидание.
- **Дефолтная гарнитура фикстуры участвует в правилах.** `Inter` в базовом элементе теста стала находкой `overused-font` и зашумила половину ожиданий — фикстура переведена на нейтральную `PT Sans`, а `Inter` проверяется отдельным тестом.

## [правило] Словарь вместо «сделай красивее»

Скилл `.vibe-defaults/skills/design-vocabulary/` задаёт десять команд (`critique`, `audit`, `polish`, `distill`, `bolder`, `quieter`, `typeset`, `layout`, `clarify`, `harden`), у каждой — **контракт с запретами**: что трогать нельзя. Порядок работы: прочитать контекст (`design_context`) → замерить `design_review` до правок → выбрать команду → соблюсти запреты → замерить после и показать разницу. Без замера «стало лучше» недоказуемо.

Связано: [[designContext]] (контекст проекта, классы правил, хук), [[tokenBudgetSurfaces]] (тот же приём — носитель числа, а не тост), [[projectsPane]].
