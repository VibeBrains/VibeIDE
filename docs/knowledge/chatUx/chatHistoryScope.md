### 1. Conversation Search — ЕДИНСТВЕННЫЙ реальный гэп

Cursor 3.11 ищет **по содержимому транскриптов** (`Cmd+K`, локальный индекс на тысячи разговоров) плюс `Cmd+F` внутри текущего транскрипта с навигацией по совпадениям ([testingcatalog](https://www.testingcatalog.com/cursor-3-11-adds-side-chats-and-agent-transcript-search/)).

**У нас поиск есть, но узкий.** `SidebarHistory.tsx:161` — `threadMatchesQuery` берёт **первое сообщение пользователя** в треде и сравнивает с запросом:

```ts
const fu = t.messages.find((m): m is ChatMessage & { role: 'user' } => …);
return (fu?.displayContent || fu?.content || '').toLowerCase().includes(q);
```

То есть ищется **заголовок**, а не разговор. Спросить «в каком чате я решал проблему с манглером» — не сработает, если фраза прозвучала в середине.

→ **VibeIDE, трудоёмкость `фича` (но меньше, чем кажется):** ядро лексического поиска у нас **уже написано** — `common/docsSearch.ts` (разбиение на секции, ранжирование с весами, выдержки, насыщение по повторам) сделано для `docs_search` 31.07 и не привязано к документации. Транскрипт ложится на ту же модель: сообщение вместо секции, роль+дата вместо заголовка. Переиспользовать ядро дешевле, чем писать второй поиск.

### 2. Side Chats — частично есть, ценность в том, чего нет

У них: параллельный разговор без прерывания основного (`/side`, `/btw`), **получает контекст главного треда**, живёт дальше и **возвращается в основной по @-mention**.

У нас: `openNewThread` и вкладки чатов есть — параллельные разговоры возможны. Нет двух вещей: **наследования контекста** при создании и **обратной ссылки** на побочный чат из основного.

→ **VibeIDE, `фича`, приоритет ниже:** сам сценарий у нас закрыт иначе — для «отвлечься и разведать» есть маршрут ролей и авто-разведчик, которые возвращают итог в тот же тред, не плодя вкладок. Прежде чем копировать, стоит понять, решает ли это нашу боль или чужую.

### 3. Cloud Agent Hooks — не переносится напрямую

Пять новых событий (prompts, responses, thoughts, subagents, compaction, stopping, turn completion) для инспекции, применения политик и самокорректирующихся workflow.

→ **Не применимо как есть, причина одной строкой:** это хуки для **облачных** агентов (чужая инфраструктура, где иначе не подступиться), а у нас агент работает локально, и точки контроля уже стоят в самом цикле — `agentTurnChecks` (детерминированные проверки хода), предохранители с залипанием, `verifyGatePolicy`, дизайн-хук на завершении хода, брейкеры. Заводить поверх этого универсальную шину событий значит строить второй слой абстракции над тем, что уже работает.

**Что стоит подсмотреть, а не копировать:** у них хуки **единообразны** — один механизм на все события. У нас каждая проверка встроена в цикл отдельно, и добавление новой требует правки `chatThreadService`. Если таких точек станет заметно больше — это аргумент за общий механизм. Сегодня их пять-шесть, порог не пройден.
