# Прерывание турна и подмешивание контекста

← [Knowledge Index](../README.md) · связано: [modesAndPolicies.md](modesAndPolicies.md)

Что происходит при abort посреди хода агента и как добавить контекст к следующему хопу, не прерывая выполнение.

---

## [баг] HTTP 400 «duplicate tool_call id» после прерывания на середине tool-call

**Контекст:** пользователь прерывает модель посреди хода (чтобы дополнить контекст), затем отправляет сообщение — провайдер отвечает `HTTP 400: invalid params, duplicate tool_call id: call_...` (2026-06).

**Суть:** сборка сообщений для OpenAI-протокола — `prepareMessages_openai_tools` в `browser/convertToLLMMessageService.ts` — на каждый tool-result дописывает `tool_call` в `tool_calls[]` ближайшего assistant-сообщения и пушит `role:'tool'`. **Дедупликации по `id` не было.** Прерывание на середине tool-call оставляет в истории недо-завершённый/повторно сыгранный `tool_call` (abort-путь в `chatThreadService` фиксирует частичный ход + маркер `interrupted_streaming_tool`); на следующем запросе тот же `id` попадает в `tool_calls[]` дважды (или дублируется tool-result) → провайдер отклоняет весь запрос. Лечилось только тем, что пользователь руками останавливал процесс и слал отдельное сообщение про ошибку.

**Применение:** в `prepareMessages_openai_tools` заведён `seenToolCallIds = new Set<string>()`; повторный `tool_call id` → `continue` (пропускаем всю пару tool_call + tool-result) + `vibeLog.warn`. Санитайзинг на границе отправки корректен независимо от апстрим-причины: провайдер требует уникальные `tool_call id` в одном assistant-сообщении. **Дальше (durable):** не плодить дубль в истории на самом abort-пути (`chatThreadService`), чтобы Set был лишь страховкой.

## [архитектура] «Подмешать контекст к следующему хопу» (inject без прерывания)

**Контекст:** во время многохопного хода агента пользователь хочет добавить данные, но сейчас единственный путь — прервать (abort) и отправить новое сообщение (что и провоцирует баг выше). Нужна возможность поставить контекст в очередь, чтобы агент подхватил его на следующем хопе сам.

**Суть (дизайн):**
- **Данные:** per-thread буфер `pendingInjection` в `ChatThreadState` (рядом со `stagingSelections`) — текст (+ опц. selections/images).
- **Точка инъекции:** многохоповый цикл в `chatThreadService` (вверху каждой итерации, где читаются `messages` и до `prepareLLMChatMessages`). Если буфер не пуст — добавить его как **реальное user-сообщение** в позиции «после tool-результатов текущего хопа, перед следующим LLM-вызовом» (валидная позиция; не ломает пары tool_call↔result), пометить флагом (видно в транскрипте «добавлено в ходе выполнения»), очистить буфер.
- **UX (реализовано):** пока агент работает, **Enter** в инпуте кладёт текст в очередь (`addPendingInjection`); раньше Enter при выполнении был no-op. Escape остаётся abort. Основной Enter при простое не меняется. Файл — `react/src/sidebar-tsx/SidebarChat.tsx` (`onInject` + ветка в keydown).
- **Индикация очереди (реализовано, 2026-06-22):** заметки сразу видны **закреплённой полоской над инпутом** (фон-акцент «в очереди», `Pin` + счётчик), каждая с ✕ (`removePendingInjection(threadId, index)` — отмена до дренажа). Тоаст убран — полоска его заменяет. Когда дренаж превратит буфер в реальное user-сообщение, `pendingInjections` очищается → полоска исчезает, сообщение становится обычным в транскрипте (индикация «в очереди» снимается). Рендерится из реактивного `chatThreadsState...pendingInjections`.
- **Края:** если ход завершился с непустым буфером — остаток не теряется: дренаж стоит вверху КАЖДОЙ итерации, поэтому на следующем запуске он подмешается (как доп. user-сообщение). Авто-отправка остатка отдельным турном сразу по завершении — опциональное улучшение.

**Применение:** реализовано (2026-06-18). Метод `IChatThreadService.addPendingInjection(threadId, text)`; дренаж `_drainPendingInjections` в цикле `_runChatAgent` (перед чтением `chatMessages`). Закреплённая полоска-индикация очереди + ✕-удаление (`removePendingInjection`) добавлены 2026-06-22 (см. выше). До этой фичи обходной путь был abort + сообщение (с фиксом дедупа `tool_call id` 400 больше не возникает).

## [баг/правило] Слабая модель завершает ход ТЕКСТОМ вместо `vibe_complete` (цикл автопилота)

**Контекст:** модель (MiniMax/deepseek через агрегатор) пишет «Готово / задача выполнена / шагов не осталось» текстом вместо вызова `vibe_complete` — автопилот шлёт корректирующий нудж по кругу, ход не закрывается (2026-06).

**Суть:** машинерия уже есть (`chatThreadService` ~6634): детект «ход текстом без тула» → нудж + `forceToolUse` (`tool_choice:'required'`, `vibeide.agent.forceToolUseOnNudge`, дефолт on) + implicit-complete по исчерпании бюджета. **Но `tool_choice:'required'` работает только в native-tool режиме.** Слабые модели обычно в **XML-fallback** (нет `specialToolFormat` → native-тулзы и `tool_choice` не шлются) → форсить нечем, а текст нуджа «вызови `vibe_complete`» не сопоставляется у такой модели с эмитом XML-тега → снова проза → цикл.

**Применение:** нудж сделан **mode-aware** — если у модели `!caps.specialToolFormat` (XML-режим), к текстовому корректирующему нуджу добавляется точная форма для вывода:
```
<vibe_complete>
<summary>что сделано, 1–3 предложения</summary>
</vibe_complete>
```
Только для текстового кейса (не question/empty). `let corrective` + `xmlCompleteHint` в `chatThreadService` (~6654). Не трогаем «авто-вызов за модель» — форк осознанно этого не делает. Совет «усилить system-prompt текстом» (от самой модели) — поверхностный: контракт уже в описании `vibe_complete`; реальный пробел был именно XML-форма для слабых моделей.

### Рецидив 2026-07-31: нудж читается как «продолжай работать» → модель ВЫДУМЫВАЕТ работу

**Симптом (жалоба владельца):** MiniMax завершает задачу, получает нудж — и вместо `vibe_complete` отвечает «понял, автопилот, пошёл делать дальше» и **начинает придумывать работу из воздуха**. Живой случай: после закрытой задачи модель принялась сочинять содержимое `.vibe/servers.json`, беря поля и порядок «из головы» (формат она не знала — спеки тогда ещё не было).

**Корень — в самом тексте нуджа, не в машинерии.** Текстовая ветка (`chatThreadService` ~7367) построена так:

> «…Если задача **НЕ закончена — продолжай**, вызвав нужный инструмент. Если задача ПОЛНОСТЬЮ выполнена — вызови `vibe_complete` (…). Не пиши «Готово» просто текстом… **Если не хватает данных — прими разумное решение сам и продолжай.**»

Три дефекта формулировки, каждый бьёт именно по слабой модели:

1. **Ветка «продолжай» стоит первой.** Слабый ридер берёт первую императивную инструкцию как основную, а условие «если НЕ закончена» теряет.
2. **Последняя фраза — прямая санкция на фантазию.** «Не хватает данных → прими разумное решение сам и продолжай» задумывалась против переспрашивания, но читается как «выдумай недостающее». Она же ещё и самая свежая в контексте, то есть весит больше остальных.
3. **`forceToolUseNextTurn` требует ЛЮБОЙ инструмент** (`tool_choice: 'required'`). Модель, не связавшая нудж с `vibe_complete`, обязана вызвать хоть что-то — и вызывает случайное, что выглядит как «начал новую работу».

**Итог:** механизм отрабатывает штатно (ход не завис, инструмент вызван), но семантика противоположна намерению — вместо закрытия задачи начинается выдуманная.

**Фикс (реализован 2026-07-31, `chatThreadService` ~7367):** текстовая ветка нуджа переписана — ветка завершения идёт **первой и как умолчание**; открывается с «ход не закрывается текстом — только вызовом инструмента»; появился явный блок ЗАПРЕЩЕНО (придумывать работу, о которой не просили; создавать файлы «на всякий случай»; выдумывать данные, которых нет в проекте); ключевая новая строка — **«не знаешь, что делать дальше — значит работа закончена: вызывай `vibe_complete`»** (именно этот случай порождал фабрикацию); «прими разумное решение сам» заменено на выбор **из вариантов, уже известных из проекта**.

**Что осознанно НЕ сделали:** сужение `forceToolUse` до одного `vibe_complete`, хотя инцидент к этому подталкивал. Нудж срабатывает и на ходах, где работа реально осталась, — принудительный вызов завершения закрыл бы живую задачу за модель. Это отказ хуже исходного дефекта и притом молчаливый. Решение зафиксировано комментарием в коде рядом с `forceToolUseNextTurn`, чтобы не пересматривалось вслепую.

**Не проверено живьём:** формулировка не прогонялась на MiniMax — нужен прогон, где модель завершает задачу и получает нудж. До этого фикс считается «зарегистрирован, не доказан».

## [архитектура/правило] Живой UI-статус в треде — транзиентом, НЕ персистентным сообщением (инвариант «последнего сообщения»)

**Контекст:** нужен живой индикатор «субагент/роль сейчас работает» прямо в треде чата, между стартом и финишем (VA.6, killer-запрос). Первая идея — «сообщение-плейсхолдер, обновляемое на статусах». Аудит `wf_365c8028-33b` флагнул риск `addAssistantNotice` во время активного стрима (2026-07-11).

**Суть:** вставлять сообщение в `thread.messages` во время активного хода — **опасно**. Стрим-путь и одобрения тулов полагаются на то, что `messages[messages.length-1]` — это конкретное сообщение хода:
- `_swapOutLatestStreamingToolWithResult` (chatThreadService.ts) заменяет **последнее** сообщение результатом тула;
- `approveLatestToolRequest` / `rejectLatestToolRequest` читают `messages[length-1]` как `tool_request`.
Любой notice, вставленный в окно между `tool_request` и его результатом/одобрением, сдвигает хвост → эти пути молча делают no-op (`return false` / `return`) → turn ломается (одобрение «проваливается», результат тула теряется). Стриминговый ответ, наоборот, живёт в `streamState.llmInfo` (не в `messages`) и коммитится `_addMessageToThread` (append) только в конце — поэтому «живой текст» безопасен, а вот вставки в `messages` — нет.

**Применение (два правила):**
1. **Живое состояние → транзиентный рендер, а не сообщение.** Индикатор ролей сделан хуком `useSubagentActivity(threadId)` (`react/src/util/services.tsx`, подписка на `onSubagentStatusChanged` → `getByParentThread`) и элементом `subagent-activity` в массиве `chatItems` (`SidebarChat.tsx`, рядом с loading-indicator/stall-banner). Ничего не пишется в `thread.messages` → инвариант неприкосновенен. Это же место — куда класть любой будущий live-баннер (Virtuoso `followOutput` сам пинит низ).
2. **Персистентный notice — только при простое хода.** Если display-only сообщение всё же нужно (итог роли, отчёт маршрута), постить его **только когда `streamState[threadId].isRunning === undefined`**; иначе буферизовать и флашить на `onDidChangeStreamState` при переходе в idle (`VibeSubagentChatNoticeContribution._post`/`_maybeFlush`). START-notice убран вовсе — его роль выполняет живой индикатор, а в опасное окно теперь попадает только отложенный терминальный итог.

## [архитектура] Пробуждение агента фоновой командой — почему очередь и отправка НЕ взаимозаменяемы

**Контекст:** 2026-08-11. `run_command run_in_background=true` существовал с самого начала, но был
чисто **pull**: промис исполнения выбрасывался (`void terminalToolService.runCommand(...)`), и
единственным способом узнать о завершении был вызов `read_background_output` — то есть только
внутри хода, который агент делает и так. Команда, закончившаяся, пока агент молчал, для него не
существовала до следующего сообщения человека.

**Суть.** `IToolsService.onDidBackgroundCommandExit` (фоновая ветка дожидается `resPromise`) →
пара `background_id → threadId` пишется в `_runToolCall` (единственное место, где известны оба) →
`chatThreadService._onBackgroundCommandExit` решает, **как** сказать.

Развилка здесь не косметическая, и ошибка в любую сторону ломает разное:

- **Тред занят → только `addPendingInjection`.** `_addUserMessageAndStreamResponse` на занятом
  треде **прерывает** текущий ход (`abortRunning` / `forceResetChatState`, см. выше). Завершившаяся
  сборка убила бы ровно ту работу, которая её и ждала.
- **Тред простаивает → только отправка.** Одна очередь зависла бы навсегда: авто-досылка
  `_autoSendPendingInjectionsAsNewTurn` вызывается из воронки `_setStreamState`, а у простаивающего
  треда перехода состояния не будет — ждать его некому.

Тред запоминается **на момент запуска**, а не берётся текущим на момент выхода: человек
переключает вкладки чата, пока идёт сборка, и «текущий» оказался бы чужим.

**Молчание — тоже поведение.** Команда, убитую агентом, событие не рождает: `kill_background_command`
удаляет запись, watcher видит пропажу и выходит. Агент и так знает, что он убил; заметка была бы
шумом. Вывод в заметку не кладётся — читать его решает агент, он знает, чего ждал.

**Грабля, пойманная на себе до компиляции:** первая версия удаляла запись фоновой команды по
нормальному выходу — и тем самым ломала `read_background_output`, который адресуется по `id` ровно
тогда, когда вывод и нужен. Запись живёт, ставится отметка `exitedAt`.

**Побочно вылечен давний дефект опроса:** персистентный терминал переживает команду, поэтому
`isRunning` считался по существованию терминала и был `true` навсегда. Теперь у завершения есть
настоящий момент.

**Не проверено живьём.** Рецепт смоука: `./run-dev.sh --compile` → в чате
`run_command` с `run_in_background=true` на `sleep 20 && echo done` → закрыть ход и ждать молча.
Ожидание: примерно через 20 секунд в треде появляется заметка «[Фоновая команда] … завершилась» и
агент делает ход сам. Второй прогон — послать команду и сразу дать агенту долгую работу: заметка
обязана прийти БЕЗ прерывания этой работы.
