# Спецификация: детектор нейрослопа и правки проекта `.vibe/slop.json` (VibeIDE)

← [Документация](../README.md)

> **Как этим пользоваться.** Скопируйте этот файл целиком своей LLM и попросите:
> *«По этой спецификации собери мне `.vibe/slop.json`: в проекте термины … , правило … нам не подходит»*.
> Модель вернёт готовый JSONC. Здесь есть всё, что нужно для валидного файла. Выходить в интернет
> и читать исходники VibeIDE не нужно.

Канонический источник — разбор в `src/vs/workbench/contrib/vibeide/common/textSlop/slopCatalog.ts`
и детектор в `textSlop.ts` рядом. Этот файл описывает тот же формат человеческим языком.

---

## 1. Что это

Нейрослопом здесь называются приметы машинного письма.
Про словарь: он разросся в текстах моделей (`бесшовный`, `синергия`, `delve`).
Про обороты: пустые фразы и риторические заготовки вроде «это не X — это Y».
Про голос: ассистент, который надеется, что помог, и безымянные «исследования показывают».
Про форму: одинаковый ритм и оформление вместо структуры.
Одна примета ничего не доказывает, их набор узнаётся за пару фраз.

VibeIDE читает прозу **детерминированным детектором**: одни и те же правила, одна и та же арифметика,
каждая находка — со строкой, найденным куском и способом исправить. Модель не участвует, ключ не нужен.

**Каталог правил общий с VibeIDEA** (русская и английская части) и приезжает со сборкой. В проект он не
копируется: засеянная копия заморозила бы сегодняшние списки. Проект говорит только, чем он от каталога
отличается, — файлом `.vibe/slop.json`. Один и тот же текст в обоих продуктах получает одни и те же
находки и один счёт; это стерегут общие тестовые векторы.

Где работает детектор:

| Где | Что делает |
|---|---|
| Инструмент агента `vibe_text_slop_check` | аргумент `path` (файл проекта) или `text` (сам текст); ответ — счёт и находки |
| Дизайн-детектор, правило `copy-slop` | тексты живой страницы читаются теми же списками, одна находка на элемент; и в `design_review`, и в авто-замере после хода |
| Роли агента только для чтения | `critic`, `code-reviewer` и другие судящие роли могут звать инструмент: бриф рецензента в навыке `anti-slop` велит прогнать правку детектором |

Правки из `.vibe/slop.json` действуют везде, где работает детектор.

## 2. Как начать

1. **Проверить текст.** Попросите агента: *«проверь README на нейрослоп»*. Он позовёт
   `vibe_text_slop_check` с путём файла. Открытый в редакторе файл проверяется таким, каким его видно,
   вместе с несохранёнными правками.
2. **Сказать, чем проект отличается от каталога.** Засеянный `.vibe/slop.json` пуст. В него пишут
   выключенные правила, настоящие термины проекта и свои правила (формат ниже).
3. **Чистить текст по навыку.** Навык `anti-slop` из `.vibe/skills/` описывает порядок правки:
   переписать, проверить детектором, отдать свежему рецензенту. Пайплайн `de-slop` из
   `.vibe/pipelines.json` делает то же двумя шагами: автор правит тексты, изменённые в рабочей копии,
   рецензент другого семейства моделей судит правку.

Файл под `.vibe/ignore` и под правилами пути агента (`.vibe/constraints.json`, `.vibe/permissions.json`)
инструмент не читает: находки цитируют текст, поэтому это такое же чтение, как любое другое.
Файл больше 1 МБ и текст длиннее миллиона знаков не проверяются: детектор рассчитан на прозу, а на таком
объёме задержал бы окно. Длинный текст проверяют частями, аргументом `text`.

## 3. Формат `.vibe/slop.json`

JSONC: комментарии и висячие запятые разрешены. Все поля необязательны.

```jsonc
{
  "version": 1,
  // Правила каталога, которые в этом проекте не действуют. Id правила написан в каждой находке.
  "disable": ["F5", "RU-D1"],
  // Настоящие термины проекта: находка, чей текст ЦЕЛИКОМ совпал с таким словом, не считается.
  // Звёздочка в конце слова — любое окончание.
  "allow": ["экосистем*", "платформ*"],
  // Свои правила в формате каталога. Правило с id из каталога заменяет его целиком.
  "rules": [
    { "id": "P1", "lang": "ru", "kind": "phrases", "severity": "minor",
      "name": "Канцелярит отдела", "fix": "Скажите, кто что делает.",
      "items": ["в разрезе", "в части касающейся", "осуществ* деятельност*"] },
    // Правило с id каталога заменяет его целиком, вместе со списком: так меняют вес и состав правила.
    { "id": "RU-W5", "lang": "ru", "kind": "words", "severity": "minor",
      "name": "Слова-пустышки", "fix": "Вычеркните.", "items": ["реально", "по сути", "как бы"] }
  ],
  // С какого счёта текст проходит проверку в этом проекте (по умолчанию 90).
  "passScore": 85
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `version` | число | версия формата; сейчас `1` |
| `disable` | список строк | id правил, которые не действуют; регистр не важен |
| `allow` | список строк | слова и фразы проекта в записи каталога (`*` в конце слова, `ё` ловит и `е`) |
| `rules` | список правил | свои правила; одинаковые id внутри файла — работает первое |
| `passScore` | число | порог прохода |

Файл читается при **каждой** проверке: правка действует со следующей, перезапуск не нужен.

**Битое правило** отбрасывается с предупреждением, остальные работают.
Битым считается правило без `id`, с незнакомым `kind` или `severity`, без того, что искать, или с
регуляркой, которая не компилируется.
Предупреждения приходят в ответе инструмента последней строкой «Предупреждения: …».
Файл, который не разбирается как JSONC, не применяется вовсе, и детектор работает по каталогу.

## 4. Правило

| Поле | Обязательно | Что значит |
|---|---|---|
| `id` | да | уникальный идентификатор; находка называет его |
| `kind` | да | вид правила, см. ниже |
| `severity` | да | вес: `note`, `minor`, `major`, `blocker` |
| `lang` | нет | какие абзацы правило читает: `ru`, `en`, `any` (по умолчанию `any`) |
| `name` | нет | имя в находке; по умолчанию `id` |
| `fix` | нет | подсказка «как исправить» в находке |
| `items` | для `words`, `phrases`, `opener` | список слов или фраз |
| `patterns` | для `regex`, `density` | регулярные выражения, запись ниже |
| `caseSensitive` | нет | различать регистр; по умолчанию нет |
| `minCount` | нет, для `density` | с какого числа вхождений правило считает частоту; по умолчанию 3 |
| `thresholdPer1000` | нет, для `density` | с какой частоты на тысячу слов абзацев этого языка это находка |

Виды:

- **`words`** и **`phrases`** — список. Совпадение целым словом: `рост` не находится внутри `проросток`.
  Звёздочка в конце слова — любое окончание (`синерги*` ловит «синергия», «синергией»), пробел —
  любой пробельный промежуток, `ё` в списке ловит и `е`, апостроф — оба вида. Разница между видами
  только в смысле: слово или оборот.
- **`opener`** — слова в **начале предложения**, за которыми идёт запятая, двоеточие или пробел:
  «Кроме того, …» в начале — находка, «и кроме того» посреди фразы — нет.
- **`regex`** — регулярные выражения по всему тексту. Флаги: без учёта регистра (если не
  `caseSensitive`), Юникод, `^` и `$` — границы строк.
- **`density`** — приём, обычный один раз и ставший привычкой: `patterns` считаются по тексту, и
  находка одна на документ, если вхождений не меньше `minCount` и частота на тысячу слов не ниже
  `thresholdPer1000`. Находка указывает на первое вхождение и перечисляет строки остальных.
- **Проверки в коде** — `invisible`, `rhythm-uniform`, `rhythm-fragments`, `decorative-bold`,
  `heading-stub`, `title-case`. Логика живёт в детекторе, у правила только имя, вес и подсказка. Свои
  такие правила смысла не имеют; объявить заново правило каталога этого вида — способ сменить его
  вес или подсказку.

**Запись регулярок.** Файл общий с VibeIDEA, где шаблоны компилирует Java, поэтому запись — Java,
в той части, которая есть и в JavaScript:

- `\w`, `\d`, `\b` видят **все письменности**, как в Java с `UNICODE_CHARACTER_CLASS`:
  `\bсинерги\w*` находит «Синергия» в обоих продуктах. VibeIDE переводит эти классы для своего движка сам.
- Буквы любого языка — `\p{L}`, письменность — `\p{sc=Cyrillic}`: так пишется в обоих движках.
  Запись `\p{IsCyrillic}` есть только в Java.
- Нельзя: посессивные квантификаторы (`*+`, `++`), атомарные группы `(?>…)`, флаги внутри шаблона
  `(?i)`, `\A`, `\Z`, `\Q…\E`, `\h`, `\R`, пересечения классов `[a-z&&[^b]]`. В JavaScript их нет,
  и VibeIDE отбросит такое правило с предупреждением.

## 5. Строка, которую надо оставить

С находкой можно не согласиться. Директива в самом тексте:

```markdown
<!-- slop-ignore RU-W2 — цитата из договора, её не переписывают -->
```

- Директива в конце строки покрывает эту строку и следующую.
- Директива на отдельной строке покрывает абзац под ней (до пустой строки).
- Id можно перечислить через запятую; `ALL` выключает все правила.
- Причина после тире не обязательна для детектора, но нужна читателю: подавление без причины через
  месяц никто не сможет ни снять, ни оправдать.

## 6. Как считается

**Что не читается.** Блоки кода (```` ``` ```` и `~~~`), код в обратных кавычках, строки с отступом в четыре
пробела, цитаты (`>`), адреса ссылок и голые URL, фронтматтер, HTML-комментарии и текст в кавычках
(`"…"`, `“…”`, `«…»`, `„…“`): это чужие слова, подписи интерфейса или примеры. Текст ссылки —
проза и читается. Невидимые символы (`U1`) ищутся и в коде: пробел нулевой ширины в сниппете
сломает того, кто его скопирует.

**Переводы строк.** Файл, сохранённый с переводами строк Windows, читается так же, как с обычными:
фронтматтер остаётся фронтматтером, номера строк те же.

**Язык.** Каждый абзац относится к русскому или английскому по обычным словам в нём; имена в
camelCase, аббревиатуры, числа и пути не голосуют. В абзаце меньше чем из четырёх обычных слов
язык берётся по документу. Правило с `lang: ru` читает только русские абзацы, `en` — английские,
`any` — все. Длинное тире поэтому — примета английской прозы и обычная грамматика русской.

**Одна проблема — одна находка.** Если несколько правил нашли один и тот же кусок, считается одно,
самое тяжёлое: «является неотъемлемой частью» — раздувание значимости, и слово «неотъемлемой» внутри
не становится второй находкой.
При равном весе остаётся правило каталога.
Поэтому своё правило, которое ищет слово из списка каталога с тем же весом, находок не даст.
Чтобы находка стала своей, поднимите вес своего правила или замените правило каталога своим с тем же `id`.

**Счёт.** Текст начинает со 100. Первая находка правила стоит по весу, каждая следующая того же
правила — меньше, и одно правило не может снять больше трёх своих первых цен:

| Вес | Первая находка | Каждый повтор | Потолок правила |
|---|---|---|---|
| `note` | 1 | 0.5 | 3 |
| `minor` | 5 | 2 | 15 |
| `major` | 15 | 5 | 45 |
| `blocker` | 30 | 10 | 90 |

Текст **проходит** при счёте от 90 (или от `passScore` проекта) и без находок тяжелее `minor`:
одна находка `major` не пропускает текст при любом счёте.

**Ответ инструмента** — вердикт первой строкой, затем находки от тяжёлой к лёгкой, не больше тридцати:

```text
Нейрослоп: 85/100 (проход — от 90), не проходит, находок: 1
Не пропускают: RU-W2
- строка 1:1 [RU-W2] Пустые фразы (major): «Стоит отметить» → Удалите. Если предложение умирает без этой фразы — оно и было этой фразой.
```

Это настоящий ответ на текст *«Стоит отметить, что сборка занимает две минуты на ноутбуке разработчика.»*

Подсказка после стрелки берётся из правила; у правила без `fix` стрелки нет.

**Счёт — пол, а не вердикт.** До 100 можно дойти, написав текст настолько пресный, что в нём нечего
найти. Детектор не читает смысл: выдуманную цифру, выпавшую оговорку и сломанный довод он не видит.
Их видит рецензент — для этого навык `anti-slop` и пайплайн `de-slop`.

## 7. Тексты страницы (`copy-slop`)

Дизайн-детектор прогоняет видимый текст каждого элемента страницы через списки и шаблоны каталога
(виды `words`, `phrases`, `opener`, `regex`; ритм и оформление читают документы, а не кнопку).
Одна находка на элемент — по самой тяжёлой примете: заголовок с тремя штампами переписывают один раз.

Правило вкусовое и пол качества не пробивает. Проект может принять его как идентичность в
`.vibe/design/design.md`, раздел «Детектор»: строка `- copy-slop — слоган бренда`. Старые id
`marketing-filler` (прежнее правило VibeIDE) и `marketing-promise` (прежнее правило VibeIDEA)
по-прежнему принимаются и означают `copy-slop`. Правки `.vibe/slop.json` действуют и здесь.

## 9. Чего детектор не делает

- Не переписывает текст: он называет находку и способ исправить, правит человек или агент.
- Не судит об авторстве: находка говорит о шаблоне в тексте, а не о том, кто его написал.
- Не видит смысла: выдумку, сдвиг смысла и выхолащивание ловит рецензент, а не правила.
- Не читает код: комментарии в исходниках — забота гейтов проекта.
