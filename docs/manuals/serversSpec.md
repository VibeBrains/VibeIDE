# Спецификация формата `.vibe/servers.json` (VibeIDE)

← [Документация](../README.md)

> **Как этим пользоваться.** Скопируйте весь этот файл целиком своей LLM и попросите:
> *«По этой спецификации собери мне `.vibe/servers.json` для моего проекта: посмотри package.json,
> docker-compose и структуру папок, определи сервисы и порядок их запуска».*
> Модель вернёт готовый JSONC, который кладётся в `.vibe/servers.json` в корне рабочей папки.
> Это самодостаточный документ: всё, что нужно для генерации валидного конфига, — ниже.

Канонический источник схемы — TypeScript-типы в
`src/vs/workbench/contrib/vibeide/common/vibeServer/vibeServersFile.ts`. Этот файл описывает тот же формат человеческим языком.

---

## 1. Что это и зачем

`servers.json` — описание **дев-стека проекта**, которое кладётся в репозиторий. Оно заменяет самописный `dev.sh`, который обрастает в любом монорепо: какие сервисы поднимать, в каком порядке, чего дожидаться перед стартом следующего.

- Формат — **JSONC**: допускаются `//`-комментарии и висячие запятые.
- Файл живёт в рабочей папке: `<проект>/.vibe/servers.json`.
- **Отсутствие файла = сегодняшнее поведение.** Проект без него сохраняет единственный автоопределённый сервер и настройки `vibeide.vibeServer.*` — ничего из описанного здесь не запускается.
- **Одна опечатка не роняет стек:** битая запись пропускается с предупреждением, остальные работают. Проблема верхнего уровня (не JSON, нет массива `servers`) отключает файл целиком.

## 2. Структура файла

```jsonc
{
  "version": 1,
  "servers": [
    { /* запись */ }
  ]
}
```

## 3. Поля записи

### Обязательные

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | Уникальный ключ в пределах файла. По нему ссылаются `dependsOn`, логи и UI. Повтор id → запись пропускается |
| `command` | string | Команда запуска, выполняется через системную оболочку |

### Что это за запись

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `name` | string | — | Человеческое имя для UI |
| `kind` | `"service"` \| `"task"` | `service` | **service** — долгоживущий процесс, работает пока не остановят. **task** — одноразовая команда, которая должна **успешно завершиться до** старта зависящих от неё (демон докера, миграции, кодоген) |
| `active` | boolean | `true` | `false` оставляет запись задокументированной, но вне стека |
| `note` | string | — | Комментарий для людей |

Моделирование предусловия как **данных**, а не кода, — то, что держит знание про конкретные инструменты (colima, minikube, compose) вне IDE.

### Где и с чем запускать

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `dir` | string | корень проекта | Рабочая папка относительно корня |
| `env` | объект | — | Переменные окружения |
| `envFile` | string | — | Файл переменных относительно `dir`, например `.env.local` |
| `pathPrepend` | string[] | — | Папки в начало `PATH` — пин тулчейна: `"/opt/homebrew/opt/node@20/bin"` |

### Готовность

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `port` | number | — | Порт, который слушает сервис. **Объявляется явно**, а не вычитывается из вывода: разбор URL из stdout не работает, когда стартуют три сервера сразу |
| `readyCheck` | см. ниже | `port` для service, `exit` для task | Как понять, что готов |
| `readyPath` | string | `/` | Путь, который опрашивается при `readyCheck: "http"` |
| `readyPattern` | string (regex) | — | Совпадение со строкой вывода при `readyCheck: "log"` |
| `readyTimeoutMs` | number | `60000` | Таймаут готовности |

Значения `readyCheck`:

| Значение | Готов, когда |
|---|---|
| `port` | TCP-соединение на `port` проходит |
| `http` | GET на `readyPath` вернул не-5xx |
| `log` | `readyPattern` совпал со строкой вывода |
| `exit` | процесс завершился с кодом 0 — **единственное осмысленное для task** |
| `spawn` | сразу после запуска (fire-and-forget помощники) |

> **Запущенный процесс — ещё не готовый.** Angular принимает соединения через минуты после старта, поэтому по умолчанию для сервисов проверяется сокет, а не «процесс не упал». Для тяжёлых фронтендов ставьте `readyTimeoutMs` 420000, для бэкенда — 180000.

### Порядок и пропуск

| Поле | Тип | Смысл |
|---|---|---|
| `dependsOn` | string[] | Id, которые должны быть **готовы** до старта этой записи. Порядок запуска выводится отсюда, а не из порядка в массиве |
| `skipIf` | string | Команда-проба: завершилась с кодом 0 → запись пропускается («уже запущено, делать нечего»). Осмысленно только для task |

> **Неизвестный id в `dependsOn` отключает запись**, цикл зависимостей — тоже (обе ситуации попадают в предупреждения). Проверяйте, что все id существуют.

### Поведение вокруг запуска

| Поле | Тип | Смысл |
|---|---|---|
| `autoStart` | boolean | Стартовать вместе с проектом. Подчиняется подтверждению доверия командам |
| `previewPath` | string | Путь, открываемый в превью вместо `/` |
| `stopCommand` | string | Дополнительная команда при остановке (`docker compose down`). Best-effort: её падение не фатально |

---

## 4. Правила, которые чаще всего нарушают

1. **Инфраструктура — это `task`, а не сервис.** Докер, БД, миграции описываются как `kind: "task"` + `readyCheck: "exit"` + `skipIf`, иначе стек будет ждать от них порт, которого нет.
2. **Порядок задаётся `dependsOn`,** а не позицией в массиве.
3. **Не выдумывайте порты и команды** — берите из `package.json`, `docker-compose.yml`, конфигов. Чего не знаете — спросите у человека, а не угадывайте.
4. **`skipIf` для того, чтобы повторный запуск был дешёвым:** `docker info` перед `colima start` избавляет от минуты ожидания на каждом старте.

## 5. Примеры

### Монорепо: докер + API + два фронтенда

```jsonc
{
  // dev stack
  "version": 1,
  "servers": [
    { "id": "colima", "kind": "task", "command": "colima start",
      "readyCheck": "exit", "skipIf": "docker info" },

    { "id": "api", "dir": "api", "command": "yarn dev", "port": 3000,
      "readyTimeoutMs": 180000, "dependsOn": ["colima"],
      "pathPrepend": ["/opt/homebrew/opt/node@20/bin"],
      "previewPath": "/dashboard", "stopCommand": "docker compose down" },

    { "id": "admin", "dir": "admin", "command": "npm start", "port": 4200,
      "readyTimeoutMs": 420000 },

    { "id": "app", "dir": "app", "command": "npm start -- --port 8100",
      "port": 8100, "readyTimeoutMs": 420000 }
  ]
}
```

### Одиночный Vite — минимум

```jsonc
{
  "version": 1,
  "servers": [
    { "id": "web", "command": "npm run dev", "port": 5173, "autoStart": true }
  ]
}
```

### Готовность по логу и по HTTP

```jsonc
{
  "version": 1,
  "servers": [
    // сервер печатает "Ready in 1.2s" и не сразу открывает порт
    { "id": "next", "command": "npm run dev", "port": 3000,
      "readyCheck": "log", "readyPattern": "Ready in" },

    // health-эндпоинт честнее, чем открытый сокет
    { "id": "backend", "dir": "server", "command": "go run ./cmd/api",
      "port": 8080, "readyCheck": "http", "readyPath": "/healthz" },

    // миграции обязаны пройти до старта фронта
    { "id": "migrate", "kind": "task", "dir": "server",
      "command": "make migrate", "readyCheck": "exit", "dependsOn": ["backend"] }
  ]
}
```

## 6. Проверка результата

Откройте панель **Vibe Server**: записи видны списком, порядок — из зависимостей, состояние каждой обновляется по мере готовности. Битые записи не исчезают молча — причина показывается предупреждением (неизвестная зависимость, повтор id, цикл).

Связанное: [vibeEnvironment.md](vibeEnvironment.md) — про папку `.vibe` в целом, [providersSpec.md](providersSpec.md) — такая же спека для `.vibe/providers.json`.
