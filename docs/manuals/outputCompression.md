# Сжатие вывода команд: что видит агент и как вернуть подробность

Мануал «как этим пользоваться». Настройки перечислены в конце.

## Зачем

Больше половины того, что агент читает после запуска команды, ему не нужно: триста строк зелёных
тестов вокруг четырёх упавших, прогресс сборки вокруг одной ошибки, четыреста совпадений `rg`,
говорящих одно и то же. Каждая такая строка — оплаченные input-токены и вытесненный из окна
контекст задачи.

VibeIDE сжимает вывод **до того, как его прочитает модель**, и с недавних пор делает это
**обратимо**: подробность можно вернуть, не перезапуская команду.

## Что происходит с выводом

Три ступени, в этом порядке:

1. **Профиль по типу команды.** Из команды определяется семейство — git, тесты, линтер или
   тайпчекер, сборка, поиск, `ls`/`find`, установка пакетов, docker — и применяется свёртка,
   написанная под его форму вывода. Для `npm run <script>` семейство решает **имя скрипта**:
   `npm run typecheck` разбирается как линтер, `npm run build` — как сборка.
2. **Общий конденсер.** Схлопывает повторяющиеся строки (`[× N]`) и остатки прогресс-шума.
3. **Размерный кламп.** Страховка на нераспознанный гигантский вывод.

**Строки ошибок, провалов и итоговые сводки сохраняются дословно на всех трёх ступенях.**
Это закреплено тестом, который прогоняет через каждый профиль вывод с ошибкой посередине и
проверяет, что она дошла.

Что именно сворачивается:

| Семейство | Что остаётся | Что сворачивается |
|---|---|---|
| Тесты | падения, стеки, итоговая строка | прохождения (их число есть в сводке) |
| Линтер, тайпчек | **все ошибки дословно** | повторяющиеся предупреждения — в группу по правилу с примером и счётчиком |
| Сборка | диагностики, сводки | `Compiling…`, `[3/57]`, копирование, линковка |
| Поиск (`grep`/`rg`) | первые совпадения в каждом файле | остальные — числом на файл |
| git | конфликты, ошибки, счётчики | длинные списки файлов, прогресс передачи |
| Установка | что изменилось, итог | «уже установлено», загрузки, распаковка |

## Как вернуть свёрнутое

Сжатый вывод заканчивается меткой:

```
[vibe#o3: 230 строк свёрнуто; полный вывод — expand_output ref="o3"]
```

Агент может развернуть его инструментом `expand_output`:

- `expand_output(ref="o3")` — весь вывод целиком;
- `expand_output(ref="o3", query="FAILED")` — только строки, содержащие подстроку.

Второй способ обычно и нужен: вернуть в контекст четыреста строк ради одной — это ровно та трата,
ради устранения которой сжатие и делалось.

**Почему это лучше повторного запуска.** Раньше единственным способом достать подробность был
перезапуск команды. Он стоит времени, повторяет побочные эффекты (сборка, установка, миграция)
и на недетерминированном прогоне даёт **другой** вывод — то есть отвечает не на тот вопрос.

**Границы.** Архив живёт в памяти окна и хранит последние два десятка выводов: вывод команд — это
рабочая шелуха сессии, и писать её на диск значило бы копить чужие токены и пароли из логов там,
где никто этого не ждёт. Закрыли окно — архив пуст. Ссылка, которую вытеснили новые команды,
отвечает объяснением, а не пустотой: «устарела» и «ничего не нашлось» — разные ответы.

Короткий вывод не архивируется и не сжимается вовсе: разворачивать там нечего.

## Если сжатие мешает

Выключается целиком или по частям:

| Настройка | Что делает |
|---|---|
| `vibeide.terminal.condenseOutput` | общий конденсер; `false` отключает вторую ступень |
| `vibeide.terminal.compressProfiles` | профили по типу команды; `false` оставляет только общий проход |
| `vibeide.tools.compressMcpOutput` | сжатие вывода MCP-инструментов |
| `vibeide.tools.maxTerminalOutputChars` | размерный кламп — последняя страховка |

Сколько сэкономлено за сессию, показывает команда **«VibeIDE: Экономия на сжатии вывода»**
(отдельно терминал и MCP).

## Проверить, что работает

Запустите в чате что-нибудь заведомо шумное — например прогон тестов — и посмотрите на хвост
ответа: там должна быть метка `[vibe#…]`. Попросите агента развернуть её с фильтром по слову из
вашего вывода: вернуться должны точные строки, а не пересказ.
