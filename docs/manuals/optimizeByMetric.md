# Оптимизация под метрику — как начать

← [Дерево документации](../README.md)

> **Кому это нужно:** у вас есть задача без порога «правильно» — «сделай быстрее», «урежь
> сборку», «подними покрытие», «срежь расход токенов». Код и так работает; вопрос в числе,
> которое надо сдвинуть. Здесь — как настроить замер и что при этом происходит.

## Зачем отдельный механизм

VERIFY-GATE отвечает **одним битом**: сборка зелёная или нет. Для «ускорь эту функцию» такого
ответа не существует — там нет момента, когда становится «правильно». Есть число, которое было
одним, а стало другим, и вопрос «стало ли лучше».

Без замера на этот вопрос отвечает впечатление от диффа: «меньше аллокаций — значит быстрее».
Это гипотеза. Механизм ниже заменяет её измерением.

## Шаг 1. Команда замера

Единственная обязательная настройка:

```jsonc
// .vscode/settings.json проекта
{
  "vibeide.agent.optimize.command": "npm run bench"
}
```

Требование к команде одно: **она должна напечатать число**. Как именно — вы выбираете на шаге 2.

Команда запускается в корне рабочей области. Пока она не задана, инструмент замера честно
скажет агенту, что мерить нечем, и попросит вас её задать, — вместо того чтобы выдумать
собственный бенчмарк.

## Шаг 2. Как достать число из вывода

Два варианта, оба явные. Догадок по произвольному тексту нет намеренно: неверно прочитанная
метрика хуже отсутствующей.

**Число последней строкой** — вариант по умолчанию, настройка пустая:

```
$ npm run bench
Running 200 iterations...
42.7ms
```

Единицы после числа допускаются (`42.7ms`, `1.2 s`, `95%`). А вот разделитель тысяч — нет:
`1,234` в одних странах тысяча двести тридцать четыре, в других — одна целая двести тридцать
четыре тысячных, и молча выбранное толкование ошибается в тысячу раз. Печатайте `1234`.

**Поле JSON** — когда бенчмарк умеет машиночитаемый вывод:

```jsonc
{
  "vibeide.agent.optimize.metric": "results.mean"
}
```

```
$ npm run bench
{"results":{"mean":42.7,"runs":200}}
```

## Шаг 3. Направление и порог

```jsonc
{
  // "lower" — время, размер, число ошибок. "higher" — покрытие, пропускная способность.
  "vibeide.agent.optimize.direction": "lower",

  // Доля от базы, ниже которой изменение считается дрожанием замера.
  "vibeide.agent.optimize.noiseThreshold": 0.02,

  // Бюджет времени на один замер. Одинаковый для всех попыток — см. ниже, почему.
  "vibeide.agent.optimize.timeoutMs": 300000
}
```

**Порог шума** стоит подобрать под свой бенчмарк. Запустите его несколько раз подряд без
единой правки и посмотрите разброс: если числа гуляют на 5 %, порог в 2 % будет принимать
шум за улучшение. Ставьте чуть выше наблюдаемого разброса.

## Как это выглядит в работе

Попросите агента, например: «ускорь разбор конфига, мерь `npm run bench`». Дальше:

1. Агент снимает **базу** — до единой правки. Это число «как было».
2. Меняет **одну** вещь и меряет снова.
3. Замер выносит вердикт, и агент ему подчиняется:
   - **лучше порога** — правка остаётся, база сдвигается;
   - **хуже** — правка откатывается;
   - **в пределах шума** — тоже откатывается: недоказуемая правка не стоит своего риска;
   - **замер ничего не напечатал** — это **не** «стало хуже»; агент чинит измеритель, а не
     делает вывод из пустоты.
4. После трёх попыток подряд без улучшения агент останавливается и рассказывает, что пробовал.

Порядок описан засеваемым скиллом `optimize-by-metric` — он лежит в `.vibe/skills/` вашего
проекта, его можно править под себя.

## Два правила, которые защищают честность цикла

**Бюджет времени одинаков для всех замеров.** Иначе выигрыш приходит от более долгого прогона,
а не от лучшего решения, и попытки перестают быть сравнимыми. Поэтому `timeoutMs` — общий, а не
на каждую попытку свой.

**Агенту запрещено править измеритель** — бенчмарк, его конфигурацию, размер входных данных.
Метрика, которую можно подкрутить, не измеряет ничего. Запрет прописан в скилле; если хотите
жёсткой гарантии, закройте путь бенчмарка правилом `deny_write` в ограничениях проекта — тогда
это станет не просьбой, а фактом.

## Частые случаи

**Бенчмарк печатает несколько чисел.** Выберите одно и печатайте его последним, либо перейдите
на JSON и укажите поле. Метрика должна быть одна — «улучшилось два числа из трёх» не решается
автоматически.

**Замер долгий.** Поднимите `timeoutMs`, но помните: это бюджет **каждой** попытки, а попыток
будет десяток. Часовой бенчмарк делает цикл непригодным — сделайте быструю версию для цикла и
полную для финальной проверки.

**Метрика улучшилась, но поведение изменилось.** Это не улучшение, а обмен, и решать его вам.
Скилл требует от агента сказать об этом прямо, даже когда число стало лучше. Проверять
поведение — по-прежнему работа тестов и VERIFY-GATE: замер отвечает только за «насколько», а не
за «правильно ли».

**Хочется откатывать автоматически.** Сейчас вердикт выносит замер, а откат делает агент —
чекпоинтами со снимком рабочей папки. Автоматической связки нет намеренно: сначала цикл стоит
обкатать на своём проекте.
