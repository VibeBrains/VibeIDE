# Спецификация формата `.vibe/pipelines.json` (VibeIDE)

> **Как этим пользоваться.** Скопируйте весь этот файл целиком своей LLM и попросите:
> *«По этой спецификации собери мне `.vibe/pipelines.json` с пайплайном, который <…>».*
> Модель вернёт готовый JSON, который кладётся в `.vibe/pipelines.json` в корне рабочей папки.
> Это самодостаточный документ: всё, что нужно для валидного файла, — ниже.

---

## 1. Что это и зачем

Пайплайн — **последовательность шагов**, где каждый шаг выполняет отдельный агент со своей ролью, а
следующий подхватывает то, что сделал предыдущий. Типичное: спроектировать → реализовать → проверить.

Отличие от одного длинного запроса к агенту: у каждого шага **своя роль** (значит свой набор
инструментов и свои права), свой бюджет токенов и шагов, а результат каждого шага виден в журнале
прогонов отдельной записью.

## 2. Как передаются артефакты

- Следующему шагу передаются **пути файлов**, которых касались предыдущие шаги, и **ход работы**:
  предыдущий шаг — его резюме целиком, более ранние — по одной строке (до 300 символов) на шаг.
  Содержимое файлов не вставляется: на третьем шаге любой настоящей задачи это переполнило бы
  контекст, причём молча. Агент читает нужные файлы сам — инструменты у него есть.
- **Резюме шага — конец его ответа, до 2000 символов.** Вывод, вердикт ревьюера и список файлов
  стоят в конце ответа, и начало, обрезанное по длине, теряло бы именно их.
- **После волны** (§4, «Волны») следующий шаг получает резюме каждого её шага под своим
  заголовком «Шаг N/M · роль»: у волны нет одного «предыдущего шага».
- **Судящим ролям — ещё и дифф прогона** (§4, «Дифф прогона»): что изменилось в проекте с начала
  пайплайна.
- В строке шага — как он закончился (не удался, пропущен, остановлен; успех не отмечается) и вердикт
  ревьюера, если шаг проверялся. Шаг, которому известно только последнее слово, заново решает то, что
  первый шаг уже решил, — а решения, принятые порознь, противоречат друг другу.
- **Пути накапливаются целиком, пересказ — коротко.** Четвёртый шаг может открыть файл, созданный
  первым, и знает, что первый решил; длинный пересказ каждого шага превратил бы промпт в дневник,
  поэтому ранние шаги урезаются до строки.
- **Шаг эскалации, пропущенный гейтом** (§4, «Каскад отдельным шагом»), ничего не сделал, и следующий шаг
  его не видит: «предыдущим шагом» для него остаётся принятый черновик.
- Шагу можно сказать `"ignorePreviousArtifacts": true` — он не получит ничего от предыдущих: ни путей,
  ни хода работы, ни диффа прогона. Это для «свежего взгляда»: проверяющий, который не должен идти
  по следам автора.

Так выглядит задание третьего шага (`code-reviewer` после `planner` и `backend-dev`):

```text
Найди дефекты в изменениях

Ход работы до этого:
- planner: план в docs/plan.md — три этапа, миграция отдельным шагом [ревью anthropic/claude-opus-5: принято]

Предыдущий шаг (backend-dev) сообщил: реализовал этапы 1–2, третий упёрся в миграцию

Файлы, затронутые предыдущими шагами (прочитайте нужные сами): docs/plan.md, src/orders.ts
```

## 3. Что происходит при провале шага

По умолчанию пайплайн **останавливается**: иначе третий шаг работает в предположении, что второй
удался, и выдаёт результат, похожий на работу, но стоящий на пустом месте. Оставшиеся шаги
записываются со статусом «пропущен» — чтобы в отчёте было видно, почему хвост не выполнялся, а не
казалось, будто пайплайн был короче.

Шаг, который действительно независим, помечается `"continueOnFailure": true` — вручную и осознанно.

Шаг эскалации, который гейт пропустил, потому что черновик приняли, — **не провал**: хвост пайплайна
выполняется, а прогон считается пройденным целиком.

Пока пайплайн идёт, его видно уведомлением: какие шаги работают сейчас. Кнопка **«Стоп»** в нём
останавливает все шаги, которые идут, — волну целиком; запросы к моделям обрываются сразу, а не
дописываются до конца. Остановленный прогон не запускает следующих шагов, даже с `continueOnFailure`;
шаги, которые успели остановиться, записываются со статусом «остановлен». Потолки шага (`maxTokens`,
`maxSteps`) останавливают только сам шаг.

### Продолжение прерванного прогона

Прогон, остановленный «Стопом», упавший на шаге или брошенный закрытым окном, можно продолжить: при следующем запуске
того же пайплайна команда предлагает «Продолжить с шага N» или «Запустить заново».

- Сделанные шаги не повторяются; волна доделывает только недоделанных участников.
- Шаг эскалации, пропущенный гейтом, сделанным не считается: вердикт гейта в журнале не хранится, и при
  продолжении такой шаг выполняется — так же и у VibeIDEA.
- Итоги и файлы сделанных шагов получают следующие шаги — так же, как при непрерывном прогоне.
- Продолжать нечего, если с тех пор изменились шаги пайплайна (роли, порядок, волны) или ни один шаг не закончился.
- Решает человек, а не IDE: файлы проекта с тех пор могли измениться.
- Дифф прогона для судящих шагов после продолжения меряется от момента продолжения: снимок начала прерванного прогона
  к тому времени уже снят.
- Журнал — `.vibe/local/pipeline-runs.jsonl` (не в git): строка на запись, последняя строка прогона главная; хранятся
  200 последних прогонов за 30 дней, идущий не удаляется. Прогон окна, молчащего больше 90 секунд, считается брошенным.

## 4. Структура файла

```jsonc
{
  "version": 1,
  "pipelines": [
    {
      "id": "feature",
      "name": "Фича под ключ",
      "description": "Спроектировать, реализовать, проверить",
      "steps": [
        { "role": "planner",      "task": "Разбей задачу на шаги и запиши план в docs/plan.md" },
        { "role": "backend-dev",  "task": "Реализуй по плану", "acceptance": "Проект собирается" },
        { "role": "code-reviewer","task": "Найди дефекты в изменениях", "ignorePreviousArtifacts": false }
      ]
    }
  ]
}
```

### Корень

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `version` | число | нет | Версия формата. Сейчас `1`. |
| `pipelines` | массив | **да** | Список пайплайнов. |

### Пайплайн

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | строка | **да** | Уникальный идентификатор, по нему пайплайн запускается. |
| `name` | строка | нет | Человеческое имя для списка. |
| `description` | строка | нет | Пояснение. |
| `roles` | объект | нет | Модель для каждой роли: шаг без своего `model` идёт на модели своей роли (§4, «Модели ролей»). |
| `steps` | массив | **да** | От 1 до 20 шагов. |

### Шаг

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `role` | строка | **да** | Роль агента (см. §5). Неизвестная роль — ошибка шага. |
| `task` | строка | **да** | Что сделать. |
| `acceptance` | строка | нет | Критерий готовности, передаётся агенту дословно. |
| `maxTokens` | число | нет | Потолок токенов на шаг. Не указан — умолчание субагента. |
| `maxSteps` | число | нет | Потолок вызовов инструментов на шаг. |
| `continueOnFailure` | булево | нет | Выполнять, даже если предыдущий шаг провалился. |
| `ignorePreviousArtifacts` | булево | нет | Не передавать этому шагу ничего от предыдущих: ни путей, ни хода работы, ни диффа прогона. |
| `model` | строка | нет | Модель шага в виде `провайдер/модель`. Не указана — модель роли из `roles` пайплайна, а без неё — та, что резолвится для роли. Своя модель шага сильнее `roles`. |
| `escalateTo` | строка | нет | Сильная модель, на которой шаг повторяется **один раз**, если не удался. Формат тот же. |
| `escalation` | `true` | нет | Шаг эскалации: выполняется, только если гейт **не принял** результат предыдущего шага (§4, «Каскад отдельным шагом»). Значение — только булево: строка `"true"` или число — ошибка шага. В волне запрещён. Поле общее с VibeIDEA. |
| `reviewWith` | строка | нет | Модель, которая проверяет результат шага. Формат тот же. |
| `offPeak` | `true` | нет | Запускать шаг только вне пика цен его модели (`cost.timeOfDay` в `providers.json`). **Требует собственного `model` шага** — без него шаг отвергается; модель роли из `roles` не считается. Пока модель в пике, прогон ждёт; в уведомлении время запуска и кнопки «Запустить сейчас» и «Отменить прогон». У модели нет цены по часу — шаг запускается сразу с записью в журнал. Поле общее с VibeIDEA, семантика одна. |
| `paths` | список строк | нет | Куда шагу можно писать, синтаксис `.gitignore` относительно корня проекта. Не указано — куда пускает роль; у роли `qa` умолчание — только тесты (см. §5). Свой список **заменяет** умолчание роли. |
| `denyPaths` | список строк | нет | Куда шагу писать нельзя, проверяется раньше `paths`. Умолчание роли не снимает, а сужает. |
| `wave` | строка | нет | Метка волны: шаги, стоящие **подряд** с одной меткой, выполняются **одновременно**, а следующий шаг ждёт последнего из них (§4, «Волны»). Поле и правила общие с VibeIDEA. Образец — `review-wave` в засеваемом `pipelines.json`. |

Вместо «провайдер/модель» в `model`, `escalateTo`, `reviewWith` и в моделях `roles` можно поставить **логическое имя** — со знака `@`: `"model": "@fast"`. Шагу с `offPeak` имя тоже годится: расписание цены берётся у модели, в которую оно развернулось. Имена задаёт блок `"routes"` в файлах `.vibe/providers` (как у VibeIDEA, см. `providersSpec.md` §4.4) и настройка `vibeide.model.routes` поверх них. Имя разворачивается в момент запуска шага. Имени, которого нет, или запрещённого (`null`) подстановки не будет: шаг останавливается, и в итоге сказано, какого имени не нашлось и какие есть — работа не той моделью дороже остановки.

### Модели ролей: `roles`

Поле пайплайна `roles` задаёт модель каждой роли один раз, а не на каждом шаге. Поле общее с VibeIDEA.

```jsonc
{
  "id": "cascade-review",
  "roles": {
    "code-reviewer": { "model": "minimax/MiniMax-M3" },
    "critic":        { "model": "anthropic/claude-fable-5-1" }
  },
  "steps": [
    { "role": "code-reviewer", "task": "Найди дефекты в изменениях последнего коммита" },
    { "role": "critic", "escalation": true, "task": "Черновик ревью выше неполон. Назови, что в нём пропущено" }
  ]
}
```

| Что | Как |
|---|---|
| Ключ | Роль из §5. Неизвестная роль — пайплайн пропускается с предупреждением. |
| Значение | Объект `{ "model": "провайдер/модель" }` или логическое имя `{ "model": "@fast" }`. Пара `{ "provider": "anthropic", "model": "claude-fable-5-1" }` — синоним, прежнее написание VibeIDEA. |
| Неполный адрес | Провайдер без модели, модель без провайдера (`"claude-fable-5-1"`), значение не объектом — пайплайн пропускается: иначе шаг молча ушёл бы на модель по умолчанию. |
| Шаг без своего `model` | Идёт на модели своей роли из `roles`. Роли нет в `roles` — на модели роли по умолчанию, как раньше. |
| Шаг со своим `model` | Своя модель сильнее `roles`. |
| `offPeak` | Требует собственного `model` шага: модель из `roles` не считается. |
| Пишущая роль (`backend-dev`, `frontend-dev`, `qa`…) | VibeIDE принимает: шаг на своей модели у нас — агент с инструментами и файлами. Загрузка предупреждает, что VibeIDEA такой пайплайн пропустит: там модель разрешена только ролям без записи. |
| `roles` не объектом (массив, строка) | Поле игнорируется с предупреждением, пайплайн работает. |

### Каскад: черновик дешёвой моделью, сильная — если не вышло

`model` + `escalateTo` на одном шаге дают каскад: дешёвая модель делает черновик, и если шаг **не удался**, он повторяется на сильной.

**Гейтом служит исход самого шага**, а не мнение модели о себе. Спросить модель, достаточно ли хорош её ответ, — значит получить ответ в форме «да». Черновик отклоняется, если:

- прогон не удался;
- красная проверка проекта (VERIFY-GATE) — команда из настройки `vibeide.agent.verifyGate.command`, в режиме `warn` или `enforce`: эскалацию шаг и так заказал полем `escalateTo`, а красная проверка и значит «не вышло»;
- хук `pipelineStepEnd` из `.vibe/hooks.json` ответил отказом — кодом выхода `2` (`docs/manuals/hooksSpec.md`).

Проверка идёт там, где лежит работа черновика: в рабочей папке, а при изоляции деревьями — в дереве шага, пока его ветка не влита. Проверки одного прогона идут по одной: две сборки в одной папке пишут одни и те же файлы и ломают друг друга. Хук спрашивают, только если проверка прошла или её нет.

`acceptance` гейтом не служит: машинной проверки произвольного текста нет. Критерий получают агент и ревьюер шага — так же и у VibeIDEA.

```json
{
  "role": "coder",
  "task": "Починить падающий тест",
  "acceptance": "npm test зелёный",
  "model": "zai/glm-5.3-flash",
  "escalateTo": "anthropic/claude-opus-5"
}
```

**Эскалация оплачивается СВЕРХ черновика, а не вместо него.** Поэтому каскад — это ставка на то, как часто дешёвой модели достаточно: при разрыве цен в 10–15× он выигрывает даже при трети эскалаций, при разрыве в полтора раза — проигрывает почти всегда. Проверять догадку не нужно: команда **«VibeIDE: Экономика каскада»** показывает долю эскалаций, реальные траты, оценку «если бы всё делала сильная модель» и порог, выше которого каскад перестаёт окупаться.

### Каскад отдельным шагом: `escalation`

Второй способ записать каскад — форма VibeIDEA, общая для обоих продуктов. Дорогая модель — не поле шага,
а **отдельный шаг** с `"escalation": true` сразу после черновика. Он выполняется, только если гейт **не
принял** черновик. Образец — `cascade-review` в засеваемом `pipelines.json` и пример в «Моделях ролей» выше.

**Гейт — хук `pipelineStepEnd`** из `.vibe/hooks.json` (`docs/manuals/hooksSpec.md`). Его спрашивают в
конце **каждого успешного шага**; в данных — файлы, которые шаг изменил (`changedFiles`), и его итог.

| Ответ хуков о шаге | Вердикт | Следующий шаг с `"escalation": true` |
|---|---|---|
| Хоть один хук ответил кодом `0`, никто не отказал | принят | пропускается |
| Код `2` или отказ JSON-ом в формате Claude Code | не принят | выполняется |
| Хуки выключены, папка не доверена, хуков `pipelineStepEnd` нет | нет вердикта | выполняется |
| Все хуки сломаны (другой код, таймаут, не запустились) | нет вердикта | выполняется |

Как ведёт себя прогон:

- **Без гейта эскалация выполняется всегда.** Принимать черновик нечем, а пропуск дорогого шага — решение,
  которое кто-то должен принять.
- **Вердикт относится к одному шагу:** его потребляет следующий шаг, каким бы он ни был. Обычный шаг между
  черновиком и эскалацией гасит «принято», и эскалация выполнится.
- **Лестница.** Шаг, пропущенный гейтом, передаёт вердикт дальше: в цепочке «дешёвая → средняя → дорогая»
  одно «принято» о черновике снимает обе ступени. Не принят черновик — идёт средняя, и уже её вердикт решает
  судьбу дорогой. *Здесь VibeIDE сознательно расходится с VibeIDEA:* там вердикт гасится на пропущенном
  шаге, и дорогая ступень выполняется.
- **Упавший черновик** — провал, как у любого шага: шаг эскалации пропускается вместе с хвостом. Чтобы он
  выполнился после провала, ему нужен `continueOnFailure`.
- **Пропуск гейтом — не провал:** хвост пайплайна идёт, прогон считается пройденным целиком, в уведомлении
  шаг не числится заминкой. Следующий шаг получает итог принятого черновика как итог предыдущего.
- **После волны** вердикт общий: принято, если приняли **все** шаги волны, которые хук оценил; не оценил
  ни одного — вердикта нет. Сам шаг `escalation` в волне запрещён.
- **Продолжение прерванного прогона:** вердикт гейта не хранится, и пропущенный гейтом шаг при продолжении
  выполняется.
- **Журнал аудита:** каждый пропуск пишется событием `pipeline_escalation_skipped` — видно не только
  «сколько раз приняли», но и «сколько дорогих шагов не запустили».
- **Экономика каскада:** черновик перед шагом `escalation` помечается черновиком каскада, а сам шаг —
  эскалацией от него, поэтому команда «VibeIDE: Экономика каскада» считает и такую лестницу. Волна перед
  шагом `escalation` так не размечается: у неё много прогонов, и эскалацию не от чего отсчитать.

**Два каскада рядом:**

| | `escalateTo` (поле шага) | `"escalation": true` (отдельный шаг) |
|---|---|---|
| Где записан | на самом шаге: модель повтора | следующим шагом после черновика |
| Чем отклоняется черновик | провал прогона, красная проверка проекта (VERIFY-GATE), отказ хука | только отказ хука о предыдущем шаге |
| **Нет вердикта** (нет хука, хуки выключены, только сломанные) | **черновик остаётся** ответом шага, сильная модель не вызывается | **эскалация выполняется** |
| Упавший черновик | шаг повторяется на `escalateTo` | шаг эскалации пропускается, если нет `continueOnFailure` |
| Что получает сильная модель | то же задание шага | своё задание и итог черновика как итог предыдущего шага |
| Ступеней | одна | сколько угодно шагов подряд |
| В волне | работает | запрещён |
| VibeIDEA | не читает | читает, гейт тот же |

Умолчания противоположны намеренно. У `escalateTo` черновик **уже и есть ответ** шага, а повтор — исключение
по отказу: без судьи черновик стоит. У `escalation` дорогой шаг **записан в пайплайн**, а пропуск — исключение
по приёмке: без судьи шаг выполняется.

Если шаг с `escalateTo` стоит прямо перед шагом `escalation`, хук о его черновике спрашивают один раз: когда
черновик принят, он и есть результат шага, и тот же ответ решает судьбу шага эскалации.

### Критика: результат читает вторая модель

`reviewWith` добавляет к шагу ревьюера: после **успешного** прогона результат смотрит другая модель и говорит, стоит ли он. Проверять провалившийся шаг незачем — это сообщит пользователю то, что он и так знает, и будет стоить лишний вызов.

```json
{
  "role": "backend-dev",
  "task": "Добавить эндпоинт /orders",
  "acceptance": "тесты и линтер зелёные",
  "model": "zai/glm-5.3-flash",
  "reviewWith": "anthropic/claude-opus-5"
}
```

**Ревьюер должен быть из другого семейства.** Модель, которую просят проверить собственный ответ, соглашается сама с собой, а два прогона одного семейства делят одни и те же слепые пятна. VibeIDE сверяет провайдеров и **предупреждает в логе**, если исполнитель и ревьюер у одного — это слабая замена «другому семейству» (один провайдер отдаёт несколько), но ловит случай, когда упражнение теряет смысл целиком.

Ревьюер запускается ролью `code-reviewer` — она **только на чтение**, поэтому критика не может незаметно превратиться во вторую реализацию.

**Ревьюер не читает пересказ исполнителя.** Он получает задачу шага, критерий готовности, список затронутых файлов и **дифф шага** — что именно шаг изменил, — и проверяет по нему и по файлам. Пересказ «сделал, всё проверил» — это история разработки: прочитав её первой, ревьюер проверяет утверждение, а не работу. Вернуть пересказ можно настройкой `vibeide.pipeline.reviewerSeesStepSummary` (по умолчанию выключена) — она для сравнения режимов: у каждого вердикта в логе и в результате прогона отмечено, видел ли ревьюер пересказ. Сравнительного замера на наших задачах пока нет.

**Вердикт обязан быть машиночитаемым.** Ревьюера просят закончить строкой `ВЕРДИКТ: принято` или `ВЕРДИКТ: доработать`. Проза не годится: «в целом неплохо, но…» — это принято или нет? Если строки нет, вердикт считается **нераспознанным** и шаг остаётся как есть: угадывать значило бы либо переделывать по комплименту, либо принимать по жалобе.

**Замечания идут двумя блоками.** «По задаче» — сделано ли то, что просит задача, целиком, не сужена ли она и не заменена ли другим. «По качеству» — годится ли код, чтобы строить на нём дальше. Вместе их не ранжируют: чистый код, который тихо сделал половину задачи, в общем списке выглядит хорошим результатом.

При вердикте «доработать» замечания уходят **автору шага, в его же переписку** — и на этом всё. Автор помнит, почему код такой; новый исполнитель с замечаниями в задании чинит симптом и ломает причину. В задании на доработку задача не повторяется (она уже в переписке), а просят по каждому замечанию сначала одной строкой назвать причину, потом исправить; ослабить или удалить проверку в тесте — не исправление. Если переписку автора продолжить нельзя, шаг падает с понятной причиной, а не отдаётся молча новому исполнителю. Файлы, затронутые автором до доработки, остаются в результате шага. Две модели могут спорить бесконечно, а платите вы за каждый обмен; вердикт едет в отчёте, поэтому результат, который так и не убедил ревьюера, видно, а не переделывается молча. Следующий шаг узнаёт об этом из хода работы: «требовал доработки — шаг переделан один раз, повторно не проверялся».

Каскад и критика сочетаются: `model` + `escalateTo` + `reviewWith` — черновик дешёвой, эскалация при провале, ревью сильной моделью из другого семейства. Доработку после ревью делает тот же прогон, что дал результат: после эскалации — прогон сильной модели.

Неверный формат ссылки на модель (`glm-5.3-flash` без провайдера) — **ошибка шага**, а не молча пропущенное поле: одна и та же модель живёт у нескольких провайдеров по разным ценам, и угадывать её — значит угадывать чужими деньгами.

### Волны: шаги одновременно

Шаги, которые стоят **подряд** и несут одну метку `wave`, выполняются одновременно. Следующий шаг
начинается, когда закончился последний из них.

```jsonc
{
  "id": "review-and-build",
  "steps": [
    { "role": "planner", "task": "Раздели работу на сервер и интерфейс, план в docs/plan.md" },
    // Волна «build»: два пишущих шага, у каждого свой каталог.
    { "role": "backend-dev",  "task": "Сервер по плану",    "wave": "build", "paths": ["server/**"] },
    { "role": "frontend-dev", "task": "Интерфейс по плану", "wave": "build", "paths": ["web/**"] },
    // Волна «review»: судящие роли ничего не пишут, их можно ставить рядом без paths.
    { "role": "code-reviewer", "task": "Найди дефекты",   "wave": "review" },
    { "role": "security",      "task": "Найди уязвимости", "wave": "review" },
    { "role": "critic", "task": "Сведи замечания: что чинить обязательно, что можно отложить" }
  ]
}
```

Как идёт волна:

- **Все шаги волны получают одно и то же** — то, что было известно до неё: пути, ход работы, дифф.
  Работы соседа шаг не видит — её ещё нет.
- **Следующий шаг** получает резюме каждого шага волны под своим заголовком «Шаг N/M · роль» и пути
  всех изменённых файлов.
- **Провал любого шага волны — провал**, как у одиночного шага: дальше идут только шаги с
  `continueOnFailure`. Шаг волны с `continueOnFailure` запускается и после провала предыдущих.
- **Волна стартует целиком или не стартует:** если хоть одна её роль упирается в дневной лимит или
  сработал защитный предохранитель, не запускается ни один шаг, а все записываются «пропущен» с причиной.
- **«Стоп» останавливает все шаги волны.**
- **Хук `pipelineStepEnd`** спрашивают о каждом шаге волны отдельно, с полем `wave` в данных. Шаг
  `escalation` после волны пропускается, только если хук принял все шаги волны, которые оценил.
- **В строке активности чата** каждый шаг подписан: «Шаг 5/6 · волна «review» · Роль «Security»
  работает…». Шаг пайплайна виден там всегда, какой бы ни была его роль.
- **Каскад и ревью на самом шаге в волне работают** (`escalateTo`, `reviewWith`); каскад отдельным шагом
  (`escalation`) — нет, см. ниже.

Что отвергает загрузка — пайплайн пропускается с причиной, а не выполняется иначе, чем написано:

- **Метка вернулась после другого шага.** Волна — подряд идущие шаги, а не набор, разбросанный по файлу.
- **`escalation` внутри волны** — такой шаг зависит от вердикта гейта о шаге перед ним, а шаги волны
  независимы и стартуют разом. Поставьте его отдельным шагом после волны. Шаг с меткой волны, у которого
  соседей с той же меткой нет, идёт как обычный, и `escalation` у него работает.
- **`offPeak` внутри волны** — такой шаг ждал бы конца пика один и развёл бы старт волны во времени.
- **Два пишущих шага, чьи места записи нельзя доказуемо развести.** Доказательство строгое, и всё,
  что оно доказать не может, считается пересечением:
  - пишущая роль без `paths` пишет куда угодно (у `qa` без своих `paths` — тесты на любой глубине);
  - каждый шаблон `paths` должен начинаться с каталога: `server/**`, `web/public/`, `src/app.ts`.
    Шаблон, который начинается с `**` или звёздочки, и шаблон без `/` внутри (`*.md`, `README.md`,
    `docs/`) действуют на любой глубине и пересекаются со всем;
  - каталоги пересекаются, если один лежит внутри другого или они совпадают, без учёта регистра;
  - `denyPaths` и строки с `!` в доказательстве не участвуют: они только сужают.

Что загрузка только называет предупреждением: волна из одного шага (он идёт как обычный) и судящий
шаг рядом с пишущим — он увидит работу соседа недоделанной, ревью лучше ставить следующей волной.

### Дифф прогона: судящим шагам

Судящая роль читает файлы, но git у неё нет: она видит, какие файлы стали, и не видит, какими они
были. Поэтому перед первым шагом пайплайн снимает снимок рабочей папки, а судящему шагу отдаёт
`git diff` от этого снимка — отдельным блоком в конце задания.

- **Кто получает:** шаги ролей `explore`, `planner`, `code-reviewer`, `security`, `critic`, если перед
  ними что-то выполнялось и у них нет `ignorePreviousArtifacts`. Ревьюер `reviewWith` получает дифф
  своего шага — что изменил именно проверяемый шаг.
- **Что внутри:** все изменения с начала прогона, новые и удалённые файлы тоже. Удалённый файл —
  одним заголовком, без старого текста. Файлы, которые агенту закрыты `.vibe/ignore`,
  `.vibe/constraints.json` или `.vibe/permissions.json`, в дифф не попадают — блок говорит, сколько их.
  Секреты маскируются.
- **Сколько:** до половины `maxTokens` шага (по оценке 4 символа на токен), без потолка — до 40 000
  символов. Файлы идут целиком; не поместившийся хвост отрезается по границе файла, а блок говорит,
  сколько файлов показано из скольких. Шаг знает, что видит не всё, и остальное читает сам.
- **При изоляции деревьями** (`vibeide.subagent.worktree`) работа шага, чья ветка не влита, лежит не
  в папке — судящий шаг получает и дифф такой ветки от места, где она ответвилась.
- **Папка не под git** — блок так и говорит: дифф недоступен.

Снимки лежат в git под `refs/vibe/pipelines/<прогон>/…` — отдельно от снимков чекпоинтов, которые
чистятся через час, — и удаляются в конце прогона. Снимки прогона, который оборвало закрытое окно,
удаляет следующий прогон со снимками, когда им больше суток.

## 5. Доступные роли

```
explore  implement-step  recover-or-skip
orchestrator  planner  designer  frontend-dev  backend-dev  code-reviewer  qa  security  critic
```

Роль определяет набор инструментов: роли только для чтения физически не могут править файлы — это
не просьба в промпте, а список разрешённых инструментов.

Только для чтения: `explore`, `orchestrator`, `planner`, `code-reviewer`, `security`, `critic`.

**`critic`** — судит черновик другой модели: называет неверные допущения, пропущенные случаи и
расхождения с задачей, говорит, годится ли черновик, и ничего не переписывает.

**`qa`** пишет, но по умолчанию **только в тесты**: `**/test/**`, `**/tests/**`, `**/testSrc/**`,
`**/testData/**`, `**/__tests__/**`, `**/spec/**`, `*Test.kt`, `*Test.java`, `*Tests.kt`, `*Test.php`,
`*.test.ts`, `*.test.tsx`, `*.test.js`, `*.spec.ts`, `*.spec.tsx`, `*.spec.js`, `test_*.py`,
`*_test.py`, `*_test.go`. Тестировщик без записи не оставит теста, а с записью всюду «заодно чинит»
проверяемый код — и тест с исправлением становятся одним действием, которое никто не проверил. Если
тесты в проекте лежат иначе, укажите шагу свои `paths`: они заменят это умолчание. Умолчание
действует и в пайплайне, и когда `qa` зовёт оркестратор.

### Общий файл с VibeIDEA

`.vibe/pipelines.json` из набора читают VibeIDE и VibeIDEA.

**Совпадает:**

- модель шага строкой `провайдер/модель` и логическое имя `@fast` в `model` шага;
- `roles` пайплайна — модель роли для шагов без своей; пара `provider` + `model` — синоним в обоих;
- каскад отдельным шагом `"escalation": true`: тот же гейт `pipelineStepEnd` после каждого успешного шага,
  то же «нет вердикта — эскалация выполняется», тот же вердикт после волны;
- роли `critic` и `qa` с правилами выше;
- волны: те же правила загрузки, включая запрет `escalation` и `offPeak` в волне.

**Различается:**

| | VibeIDE | VibeIDEA |
|---|---|---|
| Модель у пишущей роли (на шаге или в `roles`) | разрешена: шаг — агент с инструментами | пайплайн пропускается: шаг на своей модели — прямой запрос без инструментов |
| Логическое имя в `roles` | разворачивается | пока не понимает — пайплайн пропускается |
| Лестница из нескольких шагов `escalation` | «принято» о черновике снимает все ступени | вердикт гасится на пропущенном шаге, следующая ступень выполняется |
| `escalation` не булевым значением | ошибка шага | — |
| Каскад полем шага `escalateTo`, ревью `reviewWith` | есть | не читаются |
| `"context": "shared"` | поля нет: каждый шаг в своей переписке | есть; в волне запрещён |
| Дифф прогона | получают судящие роли (инструменты есть, git — нет) | получает шаг на своей модели, у которого нет инструментов |
| Шаблон `paths` вида `docs/` | папка `docs` на любой глубине, как в `.gitignore` | только в корне |

`ignorePreviousArtifacts` выключает дифф в обоих, а `docs/**` оба продукта читают одинаково.

Пишите общий файл в пересечении: модели — только ролям без записи, каскад — шагом `escalation`, логические
имена — только в `model` шага.

## 6. Устойчивость к опечаткам

Один сломанный пайплайн **не отключает файл целиком**: он пропускается с предупреждением, остальные
работают. Пропускается пайплайн без `id`, с пустым `steps`, с дублирующимся `id`, с шагом без `role`
или `task`, а также длиннее 20 шагов. Ещё — с неизвестной ролью или неполным адресом модели в `roles` и с
`escalation`, заданным не булевым значением.

Одно поле пропускается, а пайплайн работает: `roles`, заданный не объектом. Об этом — предупреждение.

## 7. Чек-лист валидного файла

- [ ] Корень — объект с массивом `pipelines`.
- [ ] У каждого пайплайна есть уникальный `id` и непустой `steps`.
- [ ] У каждого шага есть `role` из списка §5 и непустой `task`.
- [ ] Шагов не больше 20.
- [ ] Шаги идут в том порядке, в котором должны выполняться.
- [ ] Шаги одной волны стоят подряд, в волне нет `offPeak` и `escalation`, а у пишущих шагов волны `paths` начинаются с разных каталогов.
- [ ] В `roles` — только роли из §5, у каждой `{ "model": "провайдер/модель" }`.
- [ ] Шаг `"escalation": true` стоит сразу после черновика, а в `.vibe/hooks.json` есть хук `pipelineStepEnd` — без него эскалация выполняется всегда.
