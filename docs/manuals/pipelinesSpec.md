# Спецификация формата `.vibe/pipelines.json` (VibeIDE)

> **Как этим пользоваться.** Скопируйте весь этот файл целиком своей LLM и попросите:
> *«По этой спецификации собери мне `.vibe/pipelines.json` с пайплайном, который <…>».*
> Модель вернёт готовый JSON, который кладётся в `.vibe/pipelines.json` в корне рабочей папки.
> Это самодостаточный документ: всё, что нужно для валидного файла, — ниже.

---

## 1. Что это и зачем

Пайплайн — **последовательность шагов**, где каждый шаг выполняет отдельный агент со своей ролью, а
следующий подхватывает то, что сделал предыдущий. Типичное: спроектировать → реализовать → проверить.

Отличие от одного длинного запроса к агенту: у каждого шага **своя роль** (значит свой набор
инструментов и свои права), свой бюджет токенов и шагов, а результат каждого шага виден в журнале
прогонов отдельной записью.

## 2. Как передаются артефакты

- Следующему шагу передаются **пути файлов**, которых касались предыдущие шаги, и **ход работы**:
  предыдущий шаг — его резюме целиком, более ранние — по одной строке (до 300 символов) на шаг.
  Содержимое файлов не вставляется: на третьем шаге любой настоящей задачи это переполнило бы
  контекст, причём молча. Агент читает нужные файлы сам — инструменты у него есть.
- В строке шага — как он закончился (не удался, пропущен, остановлен; успех не отмечается) и вердикт
  ревьюера, если шаг проверялся. Шаг, которому известно только последнее слово, заново решает то, что
  первый шаг уже решил, — а решения, принятые порознь, противоречат друг другу.
- **Пути накапливаются целиком, пересказ — коротко.** Четвёртый шаг может открыть файл, созданный
  первым, и знает, что первый решил; длинный пересказ каждого шага превратил бы промпт в дневник,
  поэтому ранние шаги урезаются до строки.
- Шагу можно сказать `"ignorePreviousArtifacts": true` — он не получит ничего от предыдущих. Это для
  «свежего взгляда»: проверяющий, который не должен идти по следам автора.

Так выглядит задание третьего шага (`code-reviewer` после `planner` и `backend-dev`):

```text
Найди дефекты в изменениях

Ход работы до этого:
- planner: план в docs/plan.md — три этапа, миграция отдельным шагом [ревью anthropic/claude-opus-5: принято]

Предыдущий шаг (backend-dev) сообщил: реализовал этапы 1–2, третий упёрся в миграцию

Файлы, затронутые предыдущими шагами (прочитайте нужные сами): docs/plan.md, src/orders.ts
```

## 3. Что происходит при провале шага

По умолчанию пайплайн **останавливается**: иначе третий шаг работает в предположении, что второй
удался, и выдаёт результат, похожий на работу, но стоящий на пустом месте. Оставшиеся шаги
записываются со статусом «пропущен» — чтобы в отчёте было видно, почему хвост не выполнялся, а не
казалось, будто пайплайн был короче.

Шаг, который действительно независим, помечается `"continueOnFailure": true` — вручную и осознанно.

## 4. Структура файла

```jsonc
{
  "version": 1,
  "pipelines": [
    {
      "id": "feature",
      "name": "Фича под ключ",
      "description": "Спроектировать, реализовать, проверить",
      "steps": [
        { "role": "planner",      "task": "Разбей задачу на шаги и запиши план в docs/plan.md" },
        { "role": "backend-dev",  "task": "Реализуй по плану", "acceptance": "Проект собирается" },
        { "role": "code-reviewer","task": "Найди дефекты в изменениях", "ignorePreviousArtifacts": false }
      ]
    }
  ]
}
```

### Корень

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `version` | число | нет | Версия формата. Сейчас `1`. |
| `pipelines` | массив | **да** | Список пайплайнов. |

### Пайплайн

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | строка | **да** | Уникальный идентификатор, по нему пайплайн запускается. |
| `name` | строка | нет | Человеческое имя для списка. |
| `description` | строка | нет | Пояснение. |
| `steps` | массив | **да** | От 1 до 20 шагов. |

### Шаг

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `role` | строка | **да** | Роль агента (см. §5). Неизвестная роль — ошибка шага. |
| `task` | строка | **да** | Что сделать. |
| `acceptance` | строка | нет | Критерий готовности, передаётся агенту дословно. |
| `maxTokens` | число | нет | Потолок токенов на шаг. Не указан — умолчание субагента. |
| `maxSteps` | число | нет | Потолок вызовов инструментов на шаг. |
| `continueOnFailure` | булево | нет | Выполнять, даже если предыдущий шаг провалился. |
| `ignorePreviousArtifacts` | булево | нет | Не передавать этому шагу артефакты предыдущих. |
| `model` | строка | нет | Модель шага в виде `провайдер/модель`. Не указана — та, что резолвится для роли. |
| `escalateTo` | строка | нет | Сильная модель, на которой шаг повторяется **один раз**, если не удался. Формат тот же. |
| `reviewWith` | строка | нет | Модель, которая проверяет результат шага. Формат тот же. |

### Каскад: черновик дешёвой моделью, сильная — если не вышло

`model` + `escalateTo` на одном шаге дают каскад: дешёвая модель делает черновик, и если шаг **не удался**, он повторяется на сильной.

**Гейтом служит исход самого шага** — провал прогона, невыполненный `acceptance`, красный VERIFY-GATE, — а не мнение модели о себе. Спросить модель, достаточно ли хорош её ответ, — значит получить ответ в форме «да».

```json
{
  "role": "coder",
  "task": "Починить падающий тест",
  "acceptance": "npm test зелёный",
  "model": "zai/glm-5.3-flash",
  "escalateTo": "anthropic/claude-opus-5"
}
```

**Эскалация оплачивается СВЕРХ черновика, а не вместо него.** Поэтому каскад — это ставка на то, как часто дешёвой модели достаточно: при разрыве цен в 10–15× он выигрывает даже при трети эскалаций, при разрыве в полтора раза — проигрывает почти всегда. Проверять догадку не нужно: команда **«VibeIDE: Экономика каскада»** показывает долю эскалаций, реальные траты, оценку «если бы всё делала сильная модель» и порог, выше которого каскад перестаёт окупаться.

### Критика: результат читает вторая модель

`reviewWith` добавляет к шагу ревьюера: после **успешного** прогона результат смотрит другая модель и говорит, стоит ли он. Проверять провалившийся шаг незачем — это сообщит пользователю то, что он и так знает, и будет стоить лишний вызов.

```json
{
  "role": "backend-dev",
  "task": "Добавить эндпоинт /orders",
  "acceptance": "тесты и линтер зелёные",
  "model": "zai/glm-5.3-flash",
  "reviewWith": "anthropic/claude-opus-5"
}
```

**Ревьюер должен быть из другого семейства.** Модель, которую просят проверить собственный ответ, соглашается сама с собой, а два прогона одного семейства делят одни и те же слепые пятна. VibeIDE сверяет провайдеров и **предупреждает в логе**, если исполнитель и ревьюер у одного — это слабая замена «другому семейству» (один провайдер отдаёт несколько), но ловит случай, когда упражнение теряет смысл целиком.

Ревьюер запускается ролью `code-reviewer` — она **только на чтение**, поэтому критика не может незаметно превратиться во вторую реализацию.

**Ревьюер не читает пересказ исполнителя.** Он получает задачу шага, критерий готовности и список затронутых файлов — и проверяет по файлам. Пересказ «сделал, всё проверил» — это история разработки: прочитав её первой, ревьюер проверяет утверждение, а не работу. Вернуть пересказ можно настройкой `vibeide.pipeline.reviewerSeesStepSummary` (по умолчанию выключена) — она для сравнения режимов: у каждого вердикта в логе и в результате прогона отмечено, видел ли ревьюер пересказ. Сравнительного замера на наших задачах пока нет.

**Вердикт обязан быть машиночитаемым.** Ревьюера просят закончить строкой `ВЕРДИКТ: принято` или `ВЕРДИКТ: доработать`. Проза не годится: «в целом неплохо, но…» — это принято или нет? Если строки нет, вердикт считается **нераспознанным** и шаг остаётся как есть: угадывать значило бы либо переделывать по комплименту, либо принимать по жалобе.

При вердикте «доработать» шаг выполняется **ещё один раз** с замечаниями ревьюера в задании — и на этом всё. Две модели могут спорить бесконечно, а платите вы за каждый обмен; вердикт едет в отчёте, поэтому результат, который так и не убедил ревьюера, видно, а не переделывается молча. Следующий шаг узнаёт об этом из хода работы: «требовал доработки — шаг переделан один раз, повторно не проверялся».

Каскад и критика сочетаются: `model` + `escalateTo` + `reviewWith` — черновик дешёвой, эскалация при провале, ревью сильной моделью из другого семейства. Доработку после ревью делает та модель, что дала результат.

Неверный формат ссылки на модель (`glm-5.3-flash` без провайдера) — **ошибка шага**, а не молча пропущенное поле: одна и та же модель живёт у нескольких провайдеров по разным ценам, и угадывать её — значит угадывать чужими деньгами.

## 5. Доступные роли

```
explore  implement-step  recover-or-skip
orchestrator  planner  designer  frontend-dev  backend-dev  code-reviewer  qa  security
```

Роль определяет набор инструментов: роли только для чтения физически не могут править файлы — это
не просьба в промпте, а список разрешённых инструментов.

## 6. Устойчивость к опечаткам

Один сломанный пайплайн **не отключает файл целиком**: он пропускается с предупреждением, остальные
работают. Пропускается пайплайн без `id`, с пустым `steps`, с дублирующимся `id`, с шагом без `role`
или `task`, а также длиннее 20 шагов.

## 7. Чек-лист валидного файла

- [ ] Корень — объект с массивом `pipelines`.
- [ ] У каждого пайплайна есть уникальный `id` и непустой `steps`.
- [ ] У каждого шага есть `role` из списка §5 и непустой `task`.
- [ ] Шагов не больше 20.
- [ ] Шаги идут в том порядке, в котором должны выполняться.
