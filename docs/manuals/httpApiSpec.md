# Входящий HTTP API VibeIDE — спецификация

> **Как этим пользоваться.** Скопируйте весь этот файл целиком своей LLM и попросите:
> *«По этой спецификации напиши мне <скрипт для CI / шаг GitHub Actions / крон-задачу>, который
> запускает агента VibeIDE с задачей <…> и продолжает ту же сессию на следующем шаге».*
> Это самодостаточный документ: всё, что нужно для корректного вызова, — ниже.

---

## 1. Что это

VibeIDE умеет принимать задачи для агента по HTTP: «дёрнуть агента из CI, бота или крона».
Каждый вызов запускает агента в открытой IDE и возвращает `sessionId`, по которому следующий
вызов продолжает **ту же** сессию.

**Это исполнение кода на компьютере владельца.** Поэтому:

- сервер слушает **только** `127.0.0.1` — никогда внешний адрес;
- каждый запрос требует токен;
- по умолчанию всё выключено.

## 2. Включение

1. Настройка `vibeide.httpApi.enabled` = `true`.
2. Необязательно: `vibeide.httpApi.port` — номер порта. `0` (по умолчанию) означает «любой
   свободный»; выбранный порт пишется в журнал и показывается вместе с токеном.
3. Токен создаётся сам при первом включении и хранится в защищённом хранилище ОС — **не** в
   настройках, потому что настройки синхронизируются между машинами и попадают в демонстрацию
   экрана. Посмотреть: команда **«VibeIDE: Показать токен HTTP API»**.

IDE должна быть запущена: задачу выполняет агент в открытом окне.

## 3. Аутентификация

Каждый запрос обязан нести заголовок:

```
Authorization: Bearer <токен>
```

Слово `Bearer` регистронезависимо, сам токен — нет.

Дополнительно проверяется заголовок `Host`: он обязан указывать на эту машину
(`localhost`, `127.0.0.1`, `[::1]`, с портом или без). Это защита от DNS rebinding — приёма, при
котором открытая владельцем веб-страница резолвит собственный домен в `127.0.0.1` и обращается к
вашему порту из браузера. Обычные клиенты (`curl`, `fetch` из скрипта) ставят правильный `Host`
сами, ничего делать не нужно.

## 4. Методы

### `GET /health`

Проверка живости. Ответ `200`:

```json
{ "ok": true, "version": 1 }
```

### `POST /run`

Запуск задачи. Тело — JSON, не больше **1 000 000 байт**.

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `task` | строка | да | Что сделать. Пустая строка и пробелы отклоняются. |
| `sessionId` | строка | нет | Продолжить эту сессию. Без поля — новая сессия. |
| `wait` | булево | нет | `true` — ответить только когда прогон закончится. По умолчанию `false`. |

Без `wait` ответ приходит сразу, код `200`:

```json
{ "sessionId": "<id>", "status": "started" }
```

Дальше за прогоном следят через `GET /run/<sessionId>` (ниже).

С `wait: true` ответ приходит, когда прогон закончился, — тот же объект, что отдаёт
`GET /run/<sessionId>`, но без меток времени:

```json
{ "sessionId": "<id>", "status": "completed", "answer": "<итоговый ответ агента>" }
```

| Статус в ответе | Код |
|---|---|
| `completed`, `aborted` | `200` |
| `failed` | `500` |
| `awaiting_approval`, `running` | `202` |

Код `202` значит, что ответ пришёл раньше конца прогона. Так бывает в двух случаях:

- агент попросил разрешения на действие (`"status": "awaiting_approval"`): ответить может только
  человек, и на это могут уйти часы — держать соединение столько бессмысленно;
- прогон идёт дольше десяти минут (`"status": "running"`).

В ответе есть `sessionId`, дальше опрашивайте `GET /run/<sessionId>`.

**Неизвестный `sessionId` не является ошибкой:** начнётся новая сессия, её id придёт в ответе.
Сессия могла быть очищена пользователем, и отказ оставил бы конвейер без выхода.

### `GET /run/<sessionId>`

Где стоит последний прогон сессии, запущенный через HTTP API. `sessionId` — латиница, цифры и
дефис, не длиннее 64 символов; иное — `400`.

Ответ `200`:

```json
{
  "sessionId": "<id>",
  "status": "completed",
  "answer": "<итоговый ответ агента>",
  "startedAt": "2026-10-01T12:00:00.000Z",
  "updatedAt": "2026-10-01T12:03:41.512Z",
  "finishedAt": "2026-10-01T12:03:41.512Z"
}
```

| Поле | Тип | Когда есть | Смысл |
|---|---|---|---|
| `sessionId` | строка | всегда | Сессия, она же id чата в IDE. |
| `status` | строка | всегда | Статус прогона, таблица ниже. |
| `answer` | строка | после конца, если агент что-то ответил | Последний ответ модели в этом прогоне. Служебные заметки IDE (причина остановки, отчёты проверок) ответом не считаются. |
| `answerTruncated` | `true` | ответ длиннее 100 000 символов | `answer` обрезан; полный текст — в чате IDE. |
| `error` | строка | `failed` | Причина ошибки. |
| `startedAt` | строка ISO 8601 | всегда | Когда прогон начался. |
| `updatedAt` | строка ISO 8601 | всегда | Когда статус менялся последний раз. |
| `finishedAt` | строка ISO 8601 | после конца | Когда прогон закончился. |

Статусы:

| `status` | Конец? | Смысл |
|---|---|---|
| `started` | — | Бывает только в ответе `POST /run` без `wait`: прогон принят. |
| `running` | нет | Агент работает. Сюда же относится пауза провайдера по лимиту запросов: IDE продолжит сама. |
| `awaiting_approval` | нет | Агент ждёт разрешения человека в IDE (или в Telegram). После разрешения прогон продолжается; после отказа — `aborted`. |
| `completed` | да | Агент закончил. Ответ — в `answer`. |
| `failed` | да | Ошибка: провайдер, нет модели, сработал предохранитель, окно IDE закрыли или перезагрузили. Причина — в `error`. |
| `aborted` | да | Прогон остановил человек: кнопка «Стоп», `/stop` в Telegram, отказ в разрешении, сброс состояния чата. Ещё так отвечает ожидающий `POST /run` с `wait: true`, если ту же сессию продолжил следующий `POST /run`: прежний прогон прерван, а `GET` показывает уже новый. |

Конечный статус больше не меняется. Новый `POST /run` с тем же `sessionId` начинает новый
прогон, и `GET` показывает уже его.

`404` — прогона этой сессии нет в памяти: его не запускали через HTTP API, он закончился больше
часа назад, или IDE перезапускалась.

## 5. Коды ответов

| Код | Когда |
|---|---|
| `200` | Принято (`started`), выполнено (`completed`), остановлено (`aborted`), или статус прогона найден (`GET /run/<sessionId>`) |
| `202` | `POST /run` с `wait: true` ответил раньше конца: прогон ждёт разрешения или идёт дольше десяти минут; дальше — опрос `GET /run/<sessionId>` |
| `400` | Тело не JSON, не объект, `task` пуст, или `sessionId` в пути `GET /run/…` недопустим |
| `401` | Нет заголовка `Authorization`, не `Bearer`, или неверный токен |
| `403` | Запрос не с этой машины, либо недопустимый `Host` |
| `404` | Неизвестный путь (известны `GET /health`, `POST /run`, `GET /run/<sessionId>`), либо прогона сессии нет в памяти |
| `413` | Тело больше миллиона байт |
| `500` | Прогон завершился ошибкой |
| `503` | API включён, но токен не настроен, либо нет окна IDE, готового принять задачу |

## 6. Примеры

Запустить задачу:

```bash
curl -sS -X POST http://127.0.0.1:7391/run \
  -H "Authorization: Bearer $VIBE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"task":"прогони тесты и почини падения"}'
```

Запустить, дождаться конца опросом и забрать ответ:

```bash
API=http://127.0.0.1:7391
AUTH="Authorization: Bearer $VIBE_TOKEN"

SESSION=$(curl -sS -X POST "$API/run" -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"task":"собери проект"}' | jq -r .sessionId)

# Ждём, пока прогон не выйдет из running/awaiting_approval
until STATUS=$(curl -sS "$API/run/$SESSION" -H "$AUTH" | jq -r .status) && \
      [ "$STATUS" != "running" ] && [ "$STATUS" != "awaiting_approval" ]; do
  sleep 10
done

curl -sS "$API/run/$SESSION" -H "$AUTH" | jq -r '.status, .answer // .error'
[ "$STATUS" = "completed" ] || exit 1
```

Продолжить ту же сессию следующим шагом конвейера — **после** того, как прошлый прогон
закончился: новый `POST /run` в сессию с идущим прогоном прерывает его, как новое сообщение в
чате.

```bash
curl -sS -X POST "$API/run" -H "$AUTH" -H "Content-Type: application/json" \
  -d "{\"task\":\"опиши, что изменилось\",\"sessionId\":\"$SESSION\",\"wait\":true}" | jq -r .answer
```

## 7. Ограничения

- **Задачи выполняет одно окно.** Включённый API регистрирует каждое окно IDE, но запросы
  обслуживает одно — открытое раньше других. Остальные в резерве: когда это окно закрывают,
  перезагружают или выключают в нём API, запросы переходят к следующему. Задача выполняется в
  открытом в этом окне проекте. Пока окно перезагружается и других окон нет, порт несколько секунд
  не отвечает.
- **Статусы прогонов живут в памяти IDE.** Перезагрузка окна их не стирает, перезапуск IDE —
  стирает: после него `GET /run/<sessionId>` отвечает `404`. Закончившийся прогон хранится час,
  незакончившийся без новостей — сутки; помнятся не больше 500 сессий, сверх этого уходит та, что
  дольше всех не менялась.
- **Прогон умирает вместе со своим окном.** Если окно, выполнявшее прогон, закрыли или
  перезагрузили, статус становится `failed` с причиной, а ожидающий `POST /run` получает ответ сразу.
- **Ответ — текст последнего сообщения модели**, не больше 100 000 символов. Файлы, которые агент
  изменил, смотрите в репозитории.

## 8. Чего API намеренно не делает

- **Не работает по сети.** Слушается только петлевой адрес; настройки «слушать снаружи» нет и не
  будет — она превратила бы исполнение кода на личной машине в сетевую услугу.
- **Не отдаёт токен по HTTP.** Токен выдаётся только в интерфейсе IDE.
- **Не запускает агента без открытой IDE.** Прогон выполняет окно; если окно не ответило за десять
  минут и даже не начало прогон, вызывающий получает `failed` с явной причиной, а не молчание.
